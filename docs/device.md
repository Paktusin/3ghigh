# Работа с устройством: установка и проверки

## Проверки целостности при установке

Проверено на живом устройстве: Audi MMI 3G High, вариант 9307/9308, режим
user-defined SWDL с принудительной перезаписью. В этом режиме компоненты
отмечаются вручную и ставятся выборочно, так что каждый опыт занимает секунды —
`DBInfo.txt` весит 206 байт, каталог `LABEL` 2521 байт.

### Алгоритмы

| Поле | Где | Алгоритм |
|---|---|---|
| `CheckSum` у записи File | `metainfo2.txt` | **обычный CRC-32** (полином 0x04C11DB7, init и xorout 0xFFFFFFFF, отражённый) |
| `CheckSum`…`CheckSumN` у записи Dir | `metainfo2.txt` | **несколько CRC-32 по кускам** — правило ниже |
| `MD5` | `*.conf` | обычный MD5 всего файла |
| `check=qa` | `*.conf` | **три MD5 по 102 400 байт** со смещений 0, `size/2` и `size − 102400 − 1`; файл короче пробы читается целиком, и все три значения совпадают |
| `MetafileChecksum` | `metainfo2.txt` | не опознан |
| `checkcrc` = `fdefcrc` | `*.conf`, `*.pkg` | **одно и то же значение в двух местах**, алгоритм не опознан |

Формула проверена сплошь: `src/checksum.js` сверяет **все 24 компонента**
европейского набора, и все сходятся — и суммы, и размеры.

**У каталога сумм несколько.** Запись Dir несёт `CheckSum`, `CheckSum1`,
`CheckSum2`… — по одной на кусок `CheckSumSize` (в наборе везде 209 715 200,
то есть 200 МБ). У GDB их одиннадцать, у GDB2 восемь, у SDS две.

Правило, по которому куски нарезаются, выведено и проверено на нетронутом
наборе — сходятся **все 18 каталогов и каждый их кусок**:

> файлы в порядке имён без учёта регистра читаются **одним потоком**, CRC копится
> сквозь них; кусок закрывается, когда от **текущего файла** прочитано
> `CheckSumSize` байт; конец файла сбрасывает этот счётчик, но кусок **не**
> закрывает; последний неполный кусок пишется в конце.

Отсюда две неочевидности, на которых ломаются правдоподобные модели:

| Каталог | Что получается |
|---|---|
| `GDB`, `XAC`, `LIT` (большой файл первым) | кусок 0 обрывается ровно на 200 МБ образа, а `.conf` попадает в **последний** кусок |
| `SDS` (`.conf` сортируется первым) | кусок 0 **длиннее предела**: 478 байт `.conf` плюс полные 200 МБ образа |
| `TMC`, `LABEL`, `PIT` | один кусок — оба файла целиком, они меньше предела |

Две модели, которые сюда не подходят и были отброшены: «склеить всё и нарезать
по 200 МБ» (совпадает только когда большой файл идёт первым — то есть на GDB
случайно сходится, а на SDS нет) и «окно на каждый файл со стопом на обрезанном»
(верно для первых кусков, неверно для последнего везде).

Практическое следствие: **правка в глубине тома меняет не первую сумму.** Наши
изменения записей тайлов GDB лежат на ~347 МБ, то есть в `CheckSum1`. Пока
`mkmeta.js` и `checksum.js` считали только `CheckSum`, такая правка проходила
мимо проверки и сорвалась бы уже на устройстве.

Последний случай и вывел правило: сумма `SDS` сходится ровно на длине
209 715 200 + 478, где 478 — размер `SDS.conf`.

`filesize` при этом всегда полный, без обрезания.

### Три пробы `check=qa`

Смещения выведены перебором и сходятся на всех 19 компонентах с `.conf`:

```
#1  0
#2  size / 2                (целочисленно)
#3  size − 102400 − 1
```

У третьей пробы чтение кончается за байт до конца файла. Это ошибка на единицу
в коде производителя, но воспроизводить её обязательно — иначе значение не
сойдётся. Единственный файл короче пробы — `Label.DB` на 2048 байт; у него все
три значения равны MD5 целого файла.

До этого `relocate.js` писал в `.conf` первое значение трижды. Исправлено, но
на исход установки это не повлияло (см. раздел о переносе).

### `checkcrc` и `fdefcrc` — одно число

В `.pkg` есть секция `[crcs]` со строкой на компонент:

```
fdefcrc=XAC_ECE,11cca311
```

и в `XAC.conf` стоит `checkcrc=11cca311`. Это одно значение, продублированное
в манифесте и в описании компонента. Алгоритм не найден. Проверено и не
подошло: CRC-32 всего файла данных, первых и последних 100 КБ, склейки трёх
проб `check=qa`, строки MD5; CRC-32 самого `.conf` целиком, без строки
`checkcrc`, без `\r`; варианты CRC-32 bzip2, MPEG-2, POSIX, JAMCRC. При
переносе тайлов оба значения остаются старыми.

Зато известно, **как** они используются при установке: сверяются друг с другом.
Оригинальные данные с одним лишь испорченным `checkcrc` в `.conf` дают
`Errorcode 141` на 99%; изменённые данные при нетронутых `.conf` и `.pkg`
ставятся без вопросов. То есть установщик требует `checkcrc == fdefcrc`, но ни
одно из них с данными не сличает. Сверяет ли их с данными движок при работе —
открыто, и чисто проверить это нельзя: правка `fdefcrc` в `.pkg` рушит
`.pkg.sig`, а судьба подписи для загрузчика базы не выяснена.

Отсюда же: `Errorcode 141` — не только «не сошёлся `CheckSum`», как записано в
таблице ошибок ниже, а любая из установочных сверок.

### Что проверяется, а что нет

| Проверка | Соблюдается? | Чем установлено |
|---|---|---|
| `CheckSum` компонента | **да** | изменённый `DBInfo.txt` со старой суммой — Errorcode 141 |
| Целостность `metainfo2.txt` | **да**, по умолчанию | правка 8 байт суммы — «Meta info could not be opened» |
| `skipMetaCRC` на уровне релиза | **отключает** её | те же файлы плюс флаг в `[common]` — установка прошла |
| `[AudiSignature]` | **нет** | `metainfo2.txt` изменён, подпись осталась старой, всё встало |
| `skipFileCopyCrc` на уровне носителя | не действует | флаг стоит в корневом `metainfo2.txt`, но `CheckSum` всё равно проверился |
| `skipFileCopyCrc` на уровне релиза | **снимает проверку данных** | пересобранный контейнер XAC3 давал 141 на 100% установки; с флагом в `[common]` ветки релиза встал |
| `MD5`, `check=qa`, `checkcrc` в `.conf` против данных | **нет** | `Label.DB` изменён, `LABEL.conf` оставлен оригинальным, сумма каталога пересчитана — установка прошла |
| `checkcrc` в `.conf` против `fdefcrc` в `.pkg` | **да** | данные и `metainfo2.txt` оригинальные, в `XAC3.conf` изменены только восемь символов `checkcrc` — `Errorcode 141` на 99% |

Errorcode 141 означает несовпадение контрольной суммы компонента. Нарушение
целостности самого метафайла даёт другую ошибку, ещё на этапе открытия.

### Практический вывод

Метаданные и данные можно править — на уровне установки достаточно держать в
блоке `[common]` ветки релиза три строки:

```
EnableUserDefinedSWDLMode = "true"
skipMetaCRC = "true"
skipFileCopyCrc = "true"
```

Первые две есть в австралийском наборе, третью пришлось добавить самим. Все три
работают только на уровне релиза: те же флаги в корневом `metainfo2.txt` ни на
что не влияют.

После этого `MetafileChecksum` не сверяется, подпись роли не играет, а суммы
компонентов пересчитываются обычным CRC-32. Значит доступны и правка состава
`filedef` в `.pkg`, и изменение размеров компонентов, и подмена данных.

Подгонять байты под старую контрольную сумму, как я предполагал до опытов,
не требуется.

На уровне **установки** действующие проверки — `CheckSum` компонента в
`metainfo2.txt` и равенство `checkcrc`/`fdefcrc`. Но это не значит, что данные
можно править как угодно: при **чтении** движок сверяет контрольную сумму каждой
записи каталога FLDB (см. ниже), и правка файла по месту без её пересчёта
подвешивает инициализацию. Установка пройдёт, база — нет.

## Правила работы с устройством

Список выстрадан опытами на живой машине. Каждое правило стоило отдельного
захода, а нарушение первых двух вывело навигацию из строя на вечер.

### `DBInfo.txt` не трогать никогда

Файл задаёт идентификатор базы: парт-номер, версию ПО и `SystemName`. К этой
паре привязана активация FSC (`userflags=fsc@40025` в манифесте пакета). Правка
`SystemName` — даже с сохранением обязательной длины в 13 символов — срывает
активацию, и карты блокируются примерно через десять минут работы.

Отсюда же понятно, зачем поле объявлено как «mandatory 13 characters»: длина
фиксирована именно ради сверки.

Для любых опытов идентификатор базы должен оставаться байт в байт прежним.
Менять можно только содержимое компонентов.

### `DBInfo.txt` и `config.nfm` не ставить выборочно

У всех компонентов стоит `DeleteDestinationDirBeforeCopy = "true"`, и у
большинства назначение — собственный каталог:

```
XAC3  ->  /mnt/nav/db/pkgdb/XAC3
GDB   ->  /mnt/nav/db/pkgdb/GDB
```

Но у этих двух файл лежит **в корне базы**:

```
DBINFO  ->  /mnt/nav/db/DBInfo.txt
CONFIG  ->  /mnt/nav/db/config.nfm
```

Если устройство понимает «удалить каталог назначения» буквально, установка любого
из них сносит `/mnt/nav/db/` целиком вместе со всем `pkgdb`. На устройстве это не
проверялось, но поведение согласуется с наблюдаемым. Ставить их только в составе
полной установки.

### Реестр тайлов обязан совпадать с данными

Изъятие тайлов из контейнера без правки `XAC-STRUKTUR` в `.xah` **подвешивает
инициализацию**: прогресс доходит примерно до четверти и замирает.

Наблюдение верное, а первое объяснение («загрузчик ждёт данные по смещениям из
реестра») — нет. Как выяснилось позже, любая правка содержимого контейнера по
месту делает устаревшей контрольную сумму записи в каталоге FLDB (`+0x20`), и
движок отвергает файл при чтении — см. «Алгоритм суммы каталога FLDB». Изъятие
тайлов меняет контейнер точно так же. Согласовывать `.xah` с данными всё равно
нужно, но одного этого мало: суммы каталога надо пересчитывать.

### Автоотметка в меню ничего не проверяет

В режиме user-defined блок сам отмечает часть компонентов. Сравнивает он поле
`version` из `metainfo2.txt`, а не содержимое, поэтому изменённый компонент с тем
же номером версии не отметится. Проверять факт записи на носитель надо размером
файла, а не отметкой. Нужный компонент отмечается вручную.

### При активаторе standard mode не ставит базу вовсе

Активатор снимает не только проверку FSC. Он убивает `vdev-logvolmgr` через
десять секунд после появления `/mnt/lvm/acios_db.ini`, и описатель до сверки не
доживает. Побочно это лишает SWDL источника сведений о версии установленной
базы: сравнивать не с чем.

На экране это «?» напротив `AUDI_MMI3G_ECE` вместо `Y` или `N` — состояние
неизвестно. **В режиме СТАНДАРТ такой пакет пропускается целиком.** Отказа нет,
установка проходит и рапортует об успехе, но на раздел не попадает ничего — ни
XAC, ни GDB, ни LIT.

Дальше это неотличимо от рассогласования реестра с данными: свежий раздел после
`delNavHDD.sh`, пустой `pkgdb`, инициализация замирает на четверти. Три захода
подряд с одинаковым симптомом оказались одним отказом, а не тремя.

Значит с активатором ставить только в user-defined, руками проставив `Y` на
`Application` во **всех** подпунктах четырёх пакетов:

```
AUDI_MMI3G_ECE   NaviPersistence   MapStyles   TMCConfig
```

После перевода всех подпунктов в `Y` «?» у верхнего уровня сменится на `Y`.

Две оговорки по этим четырём:

* у `TMCConfig` в ветке MMI3G файловых записей нет вовсе — только
  `DeviceDescription`, `VendorInfo` и `updateOnly`. Пункт пустой, отмечается для
  порядка и ничего не пишет;
* `NaviPersistence` и `MapStyles` объявлены `updateOnly = "true"` и потому не
  отмечаются сами никогда. При этом релиз объявляет
  `scriptPost = "/HBpersistence/navi/db/clearLastCityHistory.sh"` со своим
  `scriptPostCRC` — то есть скрипт из `NaviPersistence` вызывается после
  установки. Назначение у него в `/HBpersistence`, который переинициализация
  раздела не трогает, так что от прошлой установки он остаётся; но в полную
  установку включать его надо.

Механика «?» выведена из действия активатора и согласуется с наблюдаемым; само
поведение стандартного режима взято из форумного руководства и совпало с тремя
нашими заходами.

### Ошибки

| Что на экране | Когда | Значение |
|---|---|---|
| `Errorcode 141` | на 100% копирования | не сошлась `CheckSum` компонента |
| `Errorcode 140` | во время обновления | по форумному руководству — обновление поверх старой базы; предотвращается удалением раздела заранее, значение точно не выяснено |
| `Errorcode 150` | сразу, до начала копирования | **файловая система в режиме read-only** (форумная трактовка, «unqualified SSD» — про внутренний nav-раздел, не про карту). Точная причина read-only у нас **не установлена**. Отброшено: замок LOCK на карте (`XAC3` записался, а установщик на карту и не пишет) и нехватка места (у компонента `DeleteDestinationDirBeforeCopy` — старый каталог сносится до записи, объём тот же). Первое, что пробовать, — перезагрузка (раздел монтируется заново на запись); при повторе — `delNavHDD.sh` |
| `Meta info could not be opened` | до начала | нарушена целостность `metainfo2.txt`, нет флага `skipMetaCRC` |
| «?» напротив пакета | в списке компонентов | стоит активатор, версия установленной базы не читается; в режиме СТАНДАРТ пакет будет пропущен молча |
| инициализация замирает | после установки | `NDL Initialisation` начинается и не заканчивается: движок не принял базу. Причины разные — от пустого `XAC` до перенесённых тайлов; различать по `sloginfo` |

### Восстановление

В инженерном меню есть консоль `main/nav/databaseupdate/Console` с диагностикой
и обслуживанием базы. Два пункта, которые стоит знать:

**Список сведений о базе** показывает, видит ли устройство базу вообще:

```
no valid acios_db found on DVD-drive
no valid acios_db found on HDD
no valid acios_db found on SD0
no valid acios_db found in HBpersistence
Database info 01/01/70.00:03:36
```

`acios_db` — внутреннее имя навигационной базы в прошивке, в файлах набора
такого слова нет. Нулевая дата означает, что база не опознана вовсе, а не
повреждена частично.

**`delNavHDD.sh`** переинициализирует раздел навигации:

```
starting navigation partition reinit...
stopping application...
please reboot to read new initialized partition
afterwards install navigation database
```

Это и есть правильное восстановление: раздел создаётся заново, после чего
**обязательна перезагрузка**, и только потом установка базы. Удаление базы через
обычный пункт меню такого эффекта не даёт — остатки в корне `/mnt/nav/db/`
могут сохраняться.

Форумное руководство советует нажимать `Delete Nav HDD Partition` дважды — выйти
по `return` и повторить, — затем подождать минуту и только тогда перезагружаться.
Зачем нужен второй заход, не выяснено; вреда от него нет.

После переинициализации может потребоваться заново применить FSC.

## Перенос тайлов: первый заход на живой машине

Опыт, к которому шла вся работа: два тайла Ватикана `VA00`/`VA01` перенесены
в Никосию (33.36 в.д., 35.17 с.ш.) инструментом `relocate.js`, набор собран
`mkmeta.js`, на устройство поставлены только `XAC` и `XAC3` поверх рабочей
базы. Три сборки подряд, все три — **инициализация замирает на 28%**:

| Сборка | Что менялось | Итог |
|---|---|---|
| 1 | инструмент как был | 28% |
| 2 | исправлены три пробы `check=qa` в `.conf` | 28% |
| 3 | то же плюс растр `.ras` не трогается (`--no-ras`) | 28% |
| 4 | то же, но назначение — 25 км внутри Италии, а не Кипр | 28% |
| 5 | `--zero`: сдвиг 0, растр не тронут, переписаны только две связи `NACHBARN` — контейнер отличается от рабочего на 4 байта | 28% |
| 6 | Кипр с исправленными суммами каталога FLDB (`out/cyprus`) | 28% |
| 7 | то же, но `--no-nachbarn`: соседи не тронуты, граф симметричен (`out/cyprus-nonb`) | 28% |

Четвёртая сборка закрыла самую неприятную версию: дело **не в том, что на
Кипре пусто у GDB, LIT и CTY**. Тайлы, переехавшие внутрь плотного итальянского
покрытия, замирают так же.

> **Поправка, отменяющая вывод этого раздела.** Здесь стояло: «значит базу ломает
> сама правка, и дорога через один XAC не закрыта принципиально». Это неверно.
> Все семь сборок — **частичные установки** (только `XAC` и `XAC3`), а такая
> установка сносит `/HBpersistence/navi/db/acios_db.ini` и не создаёт его заново.
> Без описателя навигация встаёт на 28 % при любом содержимом. Сборка 5 это и
> показывала: контейнер отличался от рабочего на **четыре байта** — и всё равно
> 28 %. Тогда это выглядело как «ломает любая правка», а на деле правка была ни
> при чём. Разгадка — в разделе «Разгадка: зависание на 28%».

Откат каждый раз — те же два компонента с оригинальной карты, двадцать минут.
Ни раздел, ни остальная база не страдают.

### Где именно замирает

Это выяснилось не по данным, а по `sloginfo`, снятому в сломанном и рабочем
состояниях. Рабочее:

```
00:00:15  start: NDL Initialisation
00:00:18  mark: StateOfOperation FULLY_OPERABLE
00:00:19  end: NDL Initialisation
00:00:44  [Startup] OperationManager#setNavigationInitialized( true )
00:00:47  [Startup] OperationManager#setMapInitialized( true )
```

Сломанное:

```
00:00:14  start: NDL Initialisation
          — и всё. Ни mark, ни end.
00:00:25  [Startup] OperationManager#setNavigationInitialized( false )
```

`NDL Initialisation` — навигационный слой данных в родном коде QNX. Он
начинает инициализацию и не заканчивает её никогда; всё, что дальше, не
наступает. В рабочем состоянии этот шаг занимает четыре секунды. Полоса на 28%
— это Java-оболочка, которая ждёт событие от NDL. Загрузка процессора при
этом 6%: NDL не крутится, а ждёт.

Пара строк `start`/`end: NDL Initialisation` — самый быстрый способ понять,
дошла ли база до движка. Их достаточно грепнуть.

### Что отсеяно

Два полных дампа, сломанный и рабочий, отличаются ровно одним: в рабочем
смонтирован `/SDS` и движок держит открытыми 30 файлов базы, в сломанном —
`/SDS` нет и открыты два файла, каталог и стили карты. Оба различия — следствие
незавершённой инициализации, не причина. Всё остальное одинаково:

| Версия | Чем закрыта |
|---|---|
| активатор мешает | `vdev-logvolmgr` получает `Signal (15)` ровно через 10 с после старта в обоих состояниях |
| нет `acios_db.ini` | нет и на рабочей базе — норма при активаторе |
| потерян FSC | нет и на рабочей базе |
| nav-раздел переполнен | 97% в обоих состояниях |
| `/mnt/lvm` не смонтирован | не смонтирован и на рабочей базе |
| `check=qa` испорчен | исправлен — сборка 2, тот же исход |
| лишние ячейки в `.ras` | не пишутся — сборка 3, тот же исход |

Про открытые файлы одна оговорка: `pidin` — снимок через десять минут после
загрузки. «Открыл, прочитал и бросил» выглядит в нём так же, как «не открывал».

### Что при этом узнали о данных

**254 тайла из 3777 не имеют ни одной ячейки в общем растре `.ras`.** Растр
хранит один номер тайла на ячейку, и ячейку забирает сосед. Ватикан целиком
внутри римских тайлов, поэтому `VA00`/`VA01` — среди этих 254. Первая версия
`relocate.js` дописывала им десять ячеек на новом месте; это единственная
правка переноса, которая создавала ссылку, а не двигала существующую. На исход
не повлияла.

**Соседство почти всегда взаимно.** Из 18 195 направленных связей `NACHBARN`
односторонних пять, и все пять — российские тайлы на краю покрытия:
`RU0M -> RU8D`, `RUB3 -> RUBW`, `RUBN -> RUBL`, `RUC6 -> RUC2`, `RUCC -> RUCB`.
Перенос добавляет ещё две: у `IT1H` и `IT3S` остаются ссылки на уехавшие
`VA00`/`VA01` без обратных. Инструмент оправдывает это 586 «паромными» парами
с несоприкасающимися рамками — но те взаимны, а эти нет.

**Уровни `XAC-STRUKTUR L1..L4` — степени детализации одного тайла, а не
пространственная иерархия.** Рамки одного тайла на разных уровнях почти
совпадают, на L3/L4 просто меньше объектов. Значит переносить все уровни
тайла разом — правильно, вложенность этим не ломается.

**Ватикан — анклав в буквальном смысле данных.** Рамка `VA00` целиком лежит
внутри рамки `IT1H` (тайл около градуса на градус). Перенос вынимает вложенный
тайл из накрывающего, оставляя у накрывающего ссылку на него.

### Четыре байта — и тот же отказ

Пятая сборка меняет картину. От рабочей базы она отличается двумя номерами
соседей в `.xah`; граф с пятью односторонними связями движок терпит, а от двух
новых валится намертво — в это не верится. Зато так ведёт себя проверка
целостности: ей безразлично, четыре байта или четыре мегабайта. И все косвенные
признаки те же: ни одного открытого файла базы, спокойные потоки `ndr`, ЦП 6%.
Это не разборщик, споткнувшийся о данные, это отказ на входе.

Значит где-то есть сумма, которая накрывает содержимое `.xah` и которую мы не
пересчитываем. И она давно на виду: **в каждой записи каталога FLDB поле
`+0x20 u32` — контрольная сумма файла**, алгоритм не опознан (см. `src/fldb.js`).
`relocate.js` правит байты файлов по месту и каталог не трогает — после любого
переноса сумма у `.xah` и у четырёх тайлов устаревает. Единственная из наших
правок, которую мы даже не считали правкой.

Поле зависит от содержимого: у 45 одинаковых `.plz` сумма одна при разных
именах и смещениях, у четырёх тайлов Ватикана — четыре разные. Перебор
стандартных алгоритмов на 18 образцах из трёх контейнеров не дал ни одного
совпадения: CRC-32 с восемью полиномами × отражение × четыре затравки × два
финала × вход как есть / байты словами наоборот / полубайтами / задом наперёд;
CRC-16 в старшей и младшей половине; FNV-1/1a, djb2, sdbm, Jenkins OAAT, ELF,
SuperFastHash, MurmurHash2/2A; Adler-32, Fletcher-32, суммы байт/слов, XOR.
Либо алгоритм собственный, либо на входе не только содержимое.

Прежде чем лезть в код — проверка, нужно ли: оригинальный контейнер `XAC` с
одним изменённым битом в поле суммы записи `EJ211.xah` (`out/fldbtest`).
Данные нетронуты; повисло — поле сверяется; поднялось — поле инертно, и
виновата семантика правок.

### Разбор бинаря: что уже видно

Прошивка распакована (`fw/`, поезд K0257_6_D1, вариант 41). `tools/extract_ndr.sh`
достаёт `ndr` (413 КБ, SH-4 ELF) и `MMI3GApplication` (30 МБ) из
`ifs-root.ifs` без потерь.

Что прочитано прямо из кода:

* **База проверяется поблочно.** В `MMI3GApplication` строки
  `CIFFDataBlock::CreateForDecoding: illegal Checksum / illegal Header /
  %ld Elements`. Значит у каждого блока данных своя контрольная сумма, и
  движок сверяет её при чтении. Это объясняет, почему падают все сборки, включая
  правку соседства на 4 байта: правим содержимое блока, сумма остаётся старой.
* **Сумма — не табличный CRC.** В `ndr` по адресу `0x807a0c8` — процедура
  контрольной суммы: побитовый шаг с полиномом `0x04C11DB7` вперемешку со
  сложением-накоплением, по 4-байтовым словам плюс хвост побайтно. Стандартные
  CRC (все полиномы × отражения × затравки × финалы) её не воспроизводят —
  проверено на 18 образцах из трёх контейнеров; собственный CRC-32 бинаря
  (не-отражённый, тот же полином) тоже мимо.
* Процедура вызывает методы C++-объектов, поэтому по статическому дизассемблеру
  (capstone в SH-режиме к тому же путает пулы литералов с кодом) её надёжно не
  восстановить. Нужен декомпилятор SuperH — Ghidra (ставится `brew install
  ghidra`).

Открыто: какой именно уровень сумм держит инициализацию — поле в каталоге FLDB
(`+0x20`, тоже не опознано) или внутренняя сумма блока CIFF. Разделяет их опыт
`out/fldbtest`: оригинальный контейнер с одним изменённым битом в поле каталога.

### Важная поправка: сумму каталога движок при загрузке не проверяет

Установка исправленной сборки (оба компонента, суммы каталога верны) — и всё
равно 28%. Разбор `ndr` объясняет почему: функцию суммы `FUN_0807a0b8` вызывают
ровно два места, оба CIFF — кодирование (`FUN_0807a16c`) и декодирование
(`FUN_0807a1e0`). Больше никто. То есть сумму записи каталога FLDB (`+0x20`)
пишет офлайновый сборщик базы тем же алгоритмом, но `ndr` при чтении её **не
сверяет**. А тайлы, как показал поиск, не обёрнуты в CIFF.

Значит контрольные суммы к зависанию на 28% отношения не имеют. Пересчитывать
их всё равно правильно (для установки `CheckSum` компонента в `metainfo2.txt`
проверяется — иначе Errorcode 141), но преградой на загрузке была не они.
Зависание **смысловое**: нав-ядро не принимает тайл, перенесённый с исходного
места. Подтверждается сборкой 4 — перенос на 25 км внутри Италии висел так же,
то есть дело не в пустом Кипре, а в самом переносе. Следующий шаг — снять
`sloginfo` уже с этого состояния (есть строки вида `ndl load error 2: ...`) и
проверить, не рассогласование ли это XAC с GDB: GDB со своим пространственным
индексом остался на старом месте, а мы ставим только XAC.

Итог по сборкам 5 и 7 важнее любой из них по отдельности: `--zero` меняет

загрузчик там, и его на эту сумму мы не проверяли.

### Алгоритм суммы каталога FLDB — восстановлен

Ghidra декомпилировала `ndr`, функция `FUN_0807a0b8` — это и есть контрольная
сумма записи каталога (поле `+0x20`):

```
acc = 0
для каждого 4-байтового BE-слова W:
    step = acc << 1;  если acc & 0x80000000 → step ^= 0x04C11DB7
    acc = (0xC7 + step + W) mod 2^32
для каждого хвостового байта b:
    acc = (acc + b) mod 2^32
вернуть acc
```

Гибрид: побитовый шаг CRC с полиномом `0x04C11DB7` плюс аддитивное накопление,
константа шага `0xC7`, начальное `0`. Сверено со **всеми 7852** записями, у
которых сумма считается целиком; сошлись все записи XAC, XAC2, XAC3. Три
исключения — гигабайтные индексы `LIT2/3/4`.

Про эти три «видимо, ограничение длины» проверено и **отвергнуто**: сплошной
перебор ВСЕХ границ слов (по 537 млн у `LIT2`, 158 млн у `LIT4`) не дал ни
одного префикса, дающего заводское значение; не сошлись и счёт до конца файла,
и счёт по всему файлу вместе с обёрткой FLDB.

| запись | в каталоге | счёт по всей длине | префиксов, дающих цель |
|---|---|---|---|
| `EJ211Ga.LIT` (том 1) | `8b8f6413` | `8b8f6413` — сходится | — |
| `EJ211Ga.LI2` | `311e0068` | `9a2e718b` | 0 |
| `EJ211Ga.LI4` | `411b1a98` | `d26d4452` | 0 |

Значит правило у них другое, и ответ надо искать в коде сборщика, а не в
цифрах. Пока оно не найдено, `src/mklit.js` сумму этого компонента не трогает
вовсе — заводское значение остаётся на месте.

Код в `src/fldb.js` (`checksum`, `refreshChecksum`). `relocate.js` теперь
пересчитывает сумму каждой тронутой записи — четырёх тайлов в XAC3 и `.xah` с
`.ras` в XAC — потому что правит файлы по месту, а каталог этого сам не
замечает. Это и была единственная правка, которую мы раньше вовсе не делали.

**Слой CIFF — это та же сумма, но не в тайлах.** Ghidra декомпилировала
`CIFFDataBlock::CreateForDecoding` (`ndr` `FUN_0807a1e0`). Раскладка блока:
сумма u32 в `+0x00`, длина u32 в `+0x10` (>= 0x14, <= размера буфера), сама
сумма считается по `[блок+4, длина−4]` — и вызывает **ровно ту же**
`FUN_0807a0b8`, что и каталог FLDB. То есть отдельного алгоритма тут нет.
Но поиск самосогласованных CIFF-блоков в тайлах `.xac` и в `.xah` не дал ни
одного: эти файлы не обёрнуты в CIFF, CIFF живёт в других данных (GDB/LIT). Для
переноса тайлов, значит, достаточно суммы каталога — второго слоя внутри тайлов
нет.

**Разрешено позже.** Вопрос стоял так: не устаревшая ли сумма каталога держит
инициализацию на 28%. Ответ — **нет**. Ни сумма каталога, ни поблочная сумма
`CIFFDataBlock::CreateForDecoding: illegal Checksum` к зависанию отношения не
имеют: его вызывал пропадающий при частичной установке `acios_db.ini`. Сборка
`out/limassol` с оригинальным XAC и правильными суммами висела точно так же,
а после возврата описателя навигация поднялась без единой правки данных.

читателях. Набор под эту проверку собирает `src/mkgen.js`.

### Сборка

```
node src/mkgen.js out/gen-malta --tiles MJ00
node src/mkmeta.js out/gen-malta --keep-pkg
```

Что внутри. У мальтийского тайла `MJ00` все пять блоков версии 5 собраны
заново из графа: наша раскладка записей, наша таблица, наши координаты.
Геометрия сохранена точно — 47 119 рёбер из 47 119, сборка прекращается, если
хоть одно не сошлось. Наших байт в файле **50,3 %**; остальное — разделы имён,
номеров домов и растра, они перенесены как есть.

Почему Мальта. Это единственная страна в один тайл, остров, сам по себе:
соседи у него только паромные, и ничей чужой маршрут через него не идёт.

Почему диффа больше нигде нет. Наши блоки короче заводских, и каждый раздел
дополнен нулями до прежней длины. Длина файла та же, смещения разделов те же —
значит не тронуты ни реестр `XAC-STRUKTUR`, ни таблицы уровней, ни `NACHBARN`,
ни растр `.ras`. Меняется один контейнер `XAC2`, внутри него один файл и его
сумма в каталоге FLDB.

### Порядок на машине

1. Поставить `XAC2` из `out/gen-malta`.
2. **Обязательно** выполнить `tools/write_fixacios.sh`: частичная установка
   сносит `/HBpersistence/navi/db/acios_db.ini`, и без него навигация встаёт
   на 28 % при любом содержимом — к данным это отношения не имеет.
3. Снять `sloginfo` и убедиться, что есть строка `end: NDL Initialisation`.

### Что считать ответом

| Что делаем | «наши байты читаются» | «не читаются» |
|---|---|---|
| навигация поднимается | `end: NDL Initialisation` в журнале | зависание, и `acios_db.ini` при этом на месте |
| маршрут через весь остров (границы пяти блоков) | строится | «маршрут не найден» там, где на заводской базе строился |
| ввод адреса на Мальте | работает как раньше | — (разделы имён мы не трогали, изменение здесь означало бы промах мимо цели) |

Прежняя оговорка про межблочные векторы **снята**: тайл теперь пересобирается
целиком, номера записей раздаются сразу всем его блокам, и ссылка через
границу блока находит новую цель. У `MJ00` воспроизведены **47 594 ребра из
47 594**, в том числе 542 межблочных. Значит смотреть надо не поездку внутри
квартала, а маршрут через весь остров: он пересекает границы всех пяти блоков.

Что осталось непроверенным этим набором — связи с соседними тайлами. Свои
нульвекторы мы переносим, но встречные ссылки соседей ведут на старые
смещения внутри пересобранного тайла. У Мальты соседи только паромные, так
что на маршрут по острову это не влияет.

Откат — тот же компонент `XAC2` с заводской карты.

Это не самостоятельный набор, а заводской с тремя изменёнными компонентами, и
остальные семнадцать на разделе обязаны быть заводскими. Зависимости разные по
жёсткости:

| компонент | от чего зависит | насколько жёстко |
|---|---|---|
| `XAC` | общий индекс `.xah` описывает **все** тайлы базы, включая лежащие в `XAC2` и `XAC3`; сквозная нумерация `firstBlock` пересчитана по всем 15 108 строкам, счётчик `XACDB HEADER` — 44 744 на всю базу | **жёстко**: незаводские `XAC2`/`XAC3` означают расхождение реестра с данными |

на разделе остались компоненты от прежних опытов (перенесённые тайлы в `XAC3`,
пересобранная Мальта в `XAC2`, урезанный `GDB2`), проверять по такому раздела
нечего — любой отказ одинаково объясняется и нашими байтами, и рассогласованием
с чужими, а различить их нельзя.

Проверяется это пробой `tools/write_probe.sh`: в `var/ndr/pkgdb_listing.txt`
лежит список `/mnt/nav/db/pkgdb` с размерами, и незаводские компоненты видно по
размеру файла.

### Установка частичная, и по-другому не выйдет

В заводском `MMI3G/metainfo2.txt` под `AUDI_MMI3G_ECE` двадцать компонентов
данных, в нашем — **три**: `XAC_ECE`, `GDB_ECE`, `LIT2_ECE`. Остальные
семнадцать на устройстве остаются заводскими, и именно это и нужно: свои у нас
есть только эти три.

Отсюда следствие, к данным отношения не имеющее: частичная установка сносит
`/HBpersistence/navi/db/acios_db.ini` и не создаёт его заново, а без описателя
навигация встаёт на 28 % при любом содержимом — это и было разгадкой семи
зависаний (см. «Разгадка: зависание на 28%»). Поэтому `write_fixacios.sh` —
не перестраховка, а часть порядка.

Полная установка означала бы образ на все 21,4 ГБ: семнадцать нетронутых
компонентов пришлось бы скопировать из заводского набора (`mkmeta.js` собрал бы
манифест и на них). Смысла в этом нет — ставится всё равно то же самое, — а
восстановит ли полная установка описатель сама, мы не проверяли. Известный
рабочий путь один: частичная установка плюс `write_fixacios.sh`.

записью проверяет, что все пути из него существуют. Наши три файла названы
ровно так, как их ждёт описатель, снятый с исправной машины
(`logs/fix-0918-2126/acios_db.ini.было`):

```
ANY: /mnt/nav/db/pkgdb/XAC/kN221EUx01_0.db     — наш контейнер XAC
ANY: /mnt/nav/db/pkgdb/GDB/EJ211_v37a.gdb      — наш том GDB
ANY: /mnt/nav/db/pkgdb/LIT2/EJ211Ga_L2.db      — наш том LIT2
```

Остальные четырнадцать путей (`XAC2`, `XAC3`, `LIT`, `LIT3`, `LIT4`, `GDB2`,
`TMC`, `PIT`, `TER×2`, `CTY×3`, `LABEL`) ведут в компоненты, которые мы не
трогаем, и на разделе остаются заводскими. Значит после установки описатель
сходится целиком — переписывать его не придётся, хватит вернуть тот же файл.

   `MapStyles`, `TMCConfig`): в режиме СТАНДАРТ пакет пропускается целиком и
   установка молча рапортует об успехе, не записав ничего.
2. **Обязательно** `tools/write_fixacios.sh` — карту вставлять БЕЗ захода в
   меню обновления.
3. `sloginfo` — искать `end: NDL Initialisation`.

### Что считать ответом

| что смотрим | «наш образ читается» | «не читается» |
|---|---|---|
| навигация поднимается | `end: NDL Initialisation` | зависание при живом `acios_db.ini` |
| карта на Кипре | дороги нарисованы на всех масштабах | пусто |
| маршрут Лимасол → Никосия | строится по A1 | «маршрут не найден» |
| ввод адреса на Кипре | город и улица находятся, дом подставляется | список пуст |
| поиск точек интереса на Кипре | заправки, гостиницы, рестораны | ничего не найдено |
| Исландия | пропала, так и задумано | — |
| остальная Европа | дороги на месте, а карта пустая — `GDB` у нас только кипрский | — |

Важная оговорка про Европу: том `GDB` мы кладём **свой целиком**, и в нём есть
только Кипр. Поэтому за пределами острова карта станет пустой, хотя маршрут по
`XAC` там по-прежнему считается. Это цена одного образа, а не ошибка; вернуть
европейскую картинку — поставить заводской компонент `GDB` (2,0 ГБ).

### Чего образ не проверяет

* **суммы каталога у `LIT2`** — правило для гигабайтных записей неизвестно,
  заводское значение оставлено как есть (см. выше);
* **старых родителей блоков-доноров** — они по-прежнему указывают на наши
  блоки, и поиск в Эгейском море вернёт кипрские точки;
* **грубых уровней `XAC`** (`L2…L4`) — данных у нас нет, у тайла стоит
  «данных нет»;
* **соседей `NACHBARN`** — у `IS01` остались исландские связи.

Откат — те же три компонента с заводской карты.


### Установка 23 сентября: 28 % при живом описателе, и почему это ничего не доказывает

Образ поставлен (`XAC`, `GDB`, `LIT2`), затем выполнен `write_fixacios.sh`,
затем голова перезагружена. Итог — **полоса снова встала на 28 %**.

Что при этом известно точно:

| проверка | результат |
|---|---|
| описатель базы | **был восстановлен**: `fix.log` того же дня — файла не было, все 17 путей нашлись, `acios_db.ini` записан (923 байта) |
| `sloginfo` | `start: NDL Initialisation` есть, `end:` **нет ни одного** |
| жалобы ядра | **ни одной**: ни `ndl load error`, ни `dbm_*`, ни `illegal Checksum` |
| проба до конца | не дошла: маркер `.done` не записан, зелёного экрана не было — сорвалась после журнала, на снятии `/HBpersistence` |

Журнал в `logs/2026-09-23-cypimage-hang/`.

**Почему из этого не следует, что дело в наших данных.** База под образом
заводской не была: навигацию на устройстве к заводскому виду никогда не
возвращали, и на разделе лежат компоненты от прежних опытов — перенесённые
тайлы в `XAC3`, пересобранный `XAC2`, урезанные `GDB2` и `LABEL`. А наш `XAC`
несёт общий индекс `.xah`, описывающий **все** тайлы базы, со сквозной
нумерацией блоков на всю базу. То есть реестр заведомо не сходится с данными
соседних контейнеров, и этого одного достаточно для молчаливого отказа.

Отсюда вывод не про данные, а про подход: **заплата в чужой слот непроверяема
на незаводской базе**, а привести базу к заводскому виду — это те самые 21 ГБ
установки, которых мы и хотим избежать. Значит правильный ход — не чинить
заплату, а собрать свой образ целиком (см. «Цель» в README): в нём нет ничего,
что должно сойтись с чужим.


## Финальный образ: все файлы свои, данные только кипрские

Цель проекта в её окончательном виде. Ни одного заводского байта данных:
контейнер `XAC`, том `GDB` и контейнер `LIT` собраны с нуля.

```
node src/mkcyprus.js out/cyprus
node src/setcheck.js out/cyprus --donor CY00
node src/mkmeta.js out/cyprus --keep-pkg
tools/write_maps.sh cyprus
```

### Что внутри и сколько весит

| компонент | наш | заводской | что в нём |
|---|---|---|---|
| `XAC` | **1,52 МБ** | 2,0 ГБ | индекс `.xah` (592 КБ), растр `.ras` (31 КБ), тайл `CY00` (935 КБ), заглушка уровня 2, имена 45 городов |
| `GDB` | **7,63 МБ** | 2,0 ГБ | 87 698 дорог во всех 12 уровнях |
| `LIT` | **0,73 МБ** | 2,1 ГБ | 22 676 точек интереса, 64 листа, своё дерево; том обёрнут в FLDB так же, как заводской |
| `StyleDB`, `NaviPersistence` | 4,7 МБ | 4,7 МБ | перенесены как есть: это не данные покрытия |
| **весь образ** | **15 МБ** | 21,4 ГБ | |

Имена файлов внутри компонентов оставлены заводскими
(`kN221EUx01_0.db`, `EJ211_v37a.gdb`, `EJ211Ga_L1.db`) — их поимённо

### Чего в образе нет и почему

| не кладём | почему |
|---|---|
| `XAC2`, `XAC3` | наш индекс их не упоминает: в реестре один тайл |
| `LIT2`…`LIT4` | каталог лежит в первом томе и адресует только его |

| `CTY`, `TER` | трёхмерные здания и рельеф: не разбирали |
| `PIT`, `TMC` | от покрытия не зависят, заводские остаются |

Заводские файлы этих компонентов останутся лежать на разделе, но читать их
никто не будет: реестр о них не знает.
