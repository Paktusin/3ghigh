# ATLAS — компоненты CTY и TER

## ATLAS (компоненты CTY и TER) — контейнерный формат разобран

Формат оказался самоописывающимся, и разбор пошёл легко.

### Общая раскладка раздела

```
+0   u8 длина + имя, добито 0xCC до 16 байт
+16  u32 LE  размер раздела
+20  04 02 01 00   версия
```

Строки везде с префиксом длины: `06 "HEADER"`, `05 "Orion"`, `05 "Atlas"`,
`08 "REVISION"`, `05 "INDEX"`, `09 "CONTAINER"`. Заполнитель — `0xCC`.

### Разделы файла

```
+0      HEADER      — магия, "Orion", "Atlas", метки
+4096   REVISION
+8192   INDEX       — записи по 8 байт: u32 константа + u32, растущий шагом 8
далее   CONTAINER   — основная единица данных, их тысячи
```

### Контейнер и его сигнатура

Каждому контейнеру предшествует 16-байтовая сигнатура:

```
01 23 45 67 89 ab cd ef fe dc ba 98 76 54 32 10
```

Затем идёт обычный заголовок раздела с именем `CONTAINER`, а внутри —
**строка с типом содержимого**, тоже с префиксом длины.

### Типы содержимого различают компоненты

Проверено по первым 64 МБ каждого файла:

| Файл | Сигнатур | Типы содержимого |
|---|---|---|
| `TER/72_Europe.4_2.0.ATLAS` (1907 МБ) | 11 480 | **`SoarTerrain` × 11 051** |
| `CTY/…1665a.4_2.0.ATLAS` (2000 МБ) | 2 796 | **`Map` × 2539**, `Root` × 1 |

Это в точности совпадает с классами, найденными в прошивке:
`CAtlasSoarTerrainContainer`, `CAtlasSurfaceContainer`, `CAtlasBaseContainer`
(модуль `common\isdb\atlas\`). То есть `TER` несёт рельеф, `CTY` — карту, а
формат контейнера у них общий.

**Что дальше.** Разобрать содержимое контейнера `Map` — там должны лежать
города и поверхности, которых Кипру не хватает для поиска адреса. Контейнеры
небольшие (у `TER` в среднем около 12 КБ), так что образцов много и они
обозримы.

### Схема контейнера — формат описывает сам себя

Внутри контейнера лежит **таблица типов**: перечень того, что в нём есть, с
количествами. Записи двух видов:

```
тег 2:  <len> имя  <u32 количество>   — массив записей этого типа
тег 1:  <len> имя                     — поле внутри типа
```

У контейнера `Map` (50 912 байт) объявлено:

```
AbsolutePoint         3        VertexArray           1
ImagePointer          1        Material              1
TexturePoint       3567        Color              3570
```

а полями идут `Longitude`, `Height`, `Red`, `Blue`, `Type`, `VertexIndex`,
`Ambient`, `Specular`, `Primitives`, `Materials`, `TextureCoordinates`,
`Colors`, `ReferencePosition`, `Lod`, `Geometry`, `UniqueGeometry`, `Building`,
`BuildingPart`, `Group`, `Atom`, `Item`, `ContainerHandle`.

### Поправка: `CTY` — это трёхмерные здания, а не справочник городов

Раньше в этих записях `CTY` значился как «города, поиск адреса по городу». Судя
по схеме, это неверно: `Building`, `BuildingPart`, `VertexArray`, `VertexIndex`,
`Material`, `Ambient`, `Specular`, `TextureCoordinates`, `Lod`, `Height` — это
**трёхмерные модели зданий** с геометрией, материалами и уровнями детализации.
То есть объёмный вид города и приметные здания, которые MMI рисует при
приближении.

У `Root`-контейнера дополнительно объявлены `MapDescription`, `MapLayer`,
`MaximumScale`, `Contents`, `Layers` — то есть описание слоёв и масштабов.

**Следствие для проекта.** Трёхмерные здания не нужны ни для рисования дорог,
ни для маршрута, ни для поиска адреса — то есть `CTY` не обязателен для того,
чтобы карта поехала. Но **из набора он не исключается**: решение пользователя —
делать Кипр полным, со зданиями, рельефом и точками интереса, а не минимально
ездибельным. Поиск адреса при этом всё равно надо искать в другом компоненте.

Заодно это объясняет, почему рельеф лежит отдельно: `TER` несёт 11 051
контейнер `SoarTerrain`, и именно он рисует зелёный остров с холмами, который
виден на фотографии экрана.

## TER целиком: Orion, индекс, раскладка SOAR (разобрано по коду, 18.10)

Всё ниже прочитано в прошивке (`out/ndr/MMI3GApplication`, адреса VA) и
сверено с данными с двух концов. Где догадка — сказано.

### Поправка к «Общей раскладке» выше

Сигнатура `0123456789abcdef fedcba9876543210` стоит **в конце** раздела и входит
в его размер, а не перед контейнером. Раздел: имя (16), u32 размер (+16),
версия `04 02 01 00` (+20), тело, добивка `0xCC`, сигнатура. Обход по размерам
даёт для `TER` ровно 733 399 разделов: HEADER, REVISION, 428 INDEX,
732 969 CONTAINER, конец точно на 1 999 994 640. `TER2` — HEADER и 140 846
CONTAINER, без индекса.

### HEADER — `COrionDatabase::create` (`0x08cdff5c`), `validate` (`0x08cdfc54`)

| смещение | что | проверка в коде |
|---|---|---|
| +0x00 | `06 HEADER` | имя сверяется |
| +0x10 | u32 размер раздела | `== 4096` |
| +0x14 | версия 4.x | `[0x14]==4 && [0x15]<5` |
| +0x18 | `'l'` (порядок байт) | обязательно |
| +0x1a | число ресурсов базы: **2** | копируется в описатель |
| +0x1b | номер этого ресурса: TER 0, TER2 1 | копируется в описатель |
| +0x20 | `05 Orion` | движок, сверяется |
| +0x28 | 8 байт, одинаковые у TER и TER2 (`71 06 5d 82 91 7c 7f 11`) | не читается — догадка: код базы |
| +0x30 | `05 Atlas` | модель; `CGAtlasController::open` требует `"Atlas"` |
| +0x40 | u64 метка времени (общая) | ресурс с той же меткой садится в тот же слот («Adding resource … to existing Atlas database slot») |
| +0x48 | u64 **сумма размеров всех ресурсов** = 2 214 189 520 = 1 999 994 640 + 214 194 880 | копируется |
| +0x50 | u64 размер этого файла | копируется |
| +0x58 | u64 **база файла в общем адресном пространстве**: TER 0, TER2 1 999 994 640 | копируется |

Сумм и CRC в HEADER и REVISION код не считает.

### REVISION — там же

Размер `== 4096` (ассерт `DatabaseRevision->Size == 4096`), версия 4.x. Поля:
+0x1c u32 = 10 288 — **размер корня индекса**, +0x20 u64 = 8192 — **смещение
корня**. Код кладёт их в базу (+0x3c, +0x34/+0x38).

### INDEX — `COrionIndex::create` (`0x08ce1688`), поиск `0x08ce1a1c`

```
+0x18  u8   тип: 1 — записи ведут на дочерние INDEX, 2 — на контейнеры
+0x19  u8   log2 числа записей n (корень 9 → 512, листья 11 → 2048)
+0x1a  u8   01 (не читается; назначение неизвестно)
+0x1b  n × u64  ключ (ручка контейнера)
       n × u64  смещение раздела (сквозное по ресурсам)
       n × u32  размер раздела
```

Записи не битовые: это три **столбца**, а не восьмибайтные записи (прежнее
«u32 константа + u32 шагом 8» — это края столбцов, увиденные со сдвигом). Поиск
двоичный по ключу. Сверка разбором всего индекса:

* корень: 427 разных листьев (ключи `0x5000000000000000 + 2048·i`), хвост
  512−427 записей — повтор последнего листа;
* листья: **873 814 записей с ручками `0x5000000000000000 + 0…873 813` подряд**,
  отсортированы, без дыр; 732 969 указывают в `TER` и попадают ровно в начала
  всех 732 969 контейнеров с совпадающим размером (расхождений 0), 140 845 —
  в `TER2` (смещение ≥ 1 999 994 640, т. е. база TER2 + местное);
* 682 записи-добивки с ключом `0x5FFFFFFFFFFFFFFF` ведут на один контейнер в
  самом конце `TER2` (400 байт) — служебный, см. ниже. Это и есть 140 846-й
  контейнер TER2, которого нет среди обычных ручек.

Ручка лежит и в шапке контейнера: +0x18 u64. Значит TER2 — **не расширение,
а вторая половина одной базы**: на нём 140 845 рабочих контейнеров и
служебный. Без TER2 в заводском виде не грузится описание рельефа.

### Служебный контейнер `SoarTerrainDescription` — `CAtlasSoarTerrainModule::loadServiceContainer` (`0x08ca58c4`)

Код запрашивает ручку `0x5FFFFFFFFFFFFFFF` (константа по `0x09815b48`) и
**сверяет ручку в загруженном контейнере с запрошенной**. Поля и проверки:

| поле | значение | проверка |
|---|---|---|
| TerrainIndexMode | 1 | `== 1`, иначе «Invalid terrain index mode» |
| WGSScaling | 3.0 (float) | — (назначение не выяснено) |
| TerrainDepth | 16 | width = height = `1 << depth`, иначе «Invalid terrain width height» |
| TerrainWidth, TerrainHeight | 65 536 | см. выше |
| LongitudeBegin / LatitudeBegin | −120 000 000 / 243 858 334 | — |
| LongitudeEnd / LatitudeEnd | 426 141 666 / 790 000 000 | — |
| ContainerSize | 8192 | `1 ≤ x ≤ 65 534`, иначе «Invalid container size» |

Единица координат — 1e-7° (догадка, но сходится: квадрат lon −12…42.6°,
lat 24.4…79° — вся Европа, стороны равны: 546 141 666 и 546 141 666).

### Ручка ↔ номер точки — `CGInterleavedSoarTerrain` (`0x0935411c`, `0x09354c80`), `CGAtlasGetContainerTask` (`0x08c8eb72…`)

* ручка контейнера = `(номер_точки >> 13) | 0x5000000000000000`, номер внутри
  контейнера = номер − база; 2^13 = ContainerSize;
* база контейнера в задаче загрузки считается **из запрошенной ручки**:
  `(ручка & 0x0FFF…F) · ContainerSize` (`dmulu` по `0x08c8ebde`), не из байт
  контейнера;
* высота читается как int16 и переводится в float, рядом u16 (ошибка SOAR —
  догадка по именам полей `Heights`, `Errors`, `Radia`).

### Номер точки — чередующиеся квадродеревья SOAR (Lindstrom–Pascucci)

Вершина в коде — 16 байт `{u64 номер, i32 x, i32 y}`, треугольник — четыре
вершины `[V0, V1 (вершина угла), V2, V3 (середина V0–V2)]`. Деление
(`0x09353fc4`, `0x09354310`, середина — `0x093574d8`):

```
ребёнок 1 = [V0, V3, V1, середина(V0,V1)], номер = 4p + ((2p + q + 2) & 3) − 7
ребёнок 2 = [V1, V3, V2, середина(V1,V2)], номер = 4p + ((2p + q + 3) & 3) − 7
p = номер V1, q = номер V3   (64-битная арифметика)
```

Корневые четыре треугольника лежат в объекте (их строит `0x093549fc`, место
их заполнения в коде **не найдено**). Начальные номера восстановлены перебором
и проверены данными: углы 0…3, центр 4, середины краёв 5…8 — среди всех
раскладок с номерами −8…11 только такие (с точностью до симметрии) дают
однозначные и плотные номера. Для сетки (2^n+1)² последний номер ровно
`(5·4^n + 4)/3` (проверено n = 1…7 полным перебором, тест
`src/atlascut.test.js`). При n = 16: 7 158 278 828 → `⌈7 158 278 829 / 8192⌉ =
873 814` контейнеров — **ровно заводское число**, и последний контейнер
неполный (2733 точки, 208 байт).

Поворот сетки относительно карты (восемь вариантов) определён по данным:
размеры контейнеров с точками самого мелкого уровня. Только у варианта
«X сетки = W − широта, Y сетки = долгота» все девять проб в открытом море
дали контейнер 208 байт, а все девять проб на суше — 3,6…13,3 КБ; у остальных семи
вариантов море и суша вперемешку. Карта Кипра, нарисованная по размерам
контейнеров (точка → номер → контейнер → 208 байт или нет), даёт остров с
Троодосом, Киренийским хребтом, Карпасом и турецким берегом на своих местах.

### Море — один и тот же контейнер

565 462 контейнера из 873 814 (65 %) — **побайтно одинаковые 208 байт**, кроме
ручки в +0x18: пустое море. Ещё 187 по 208 байт отличаются одним постоянным
полем (11 видов; догадка — ровная поверхность не на нуле: озёра, плато).

### Отвергнуто

* «Записи индекса битово упакованы» — нет, три столбца (ключ, смещение,
  размер), см. выше; «u32 константа + u32 шагом 8» — край столбцов со сдвигом.
* «Сигнатура перед контейнером» — она в конце каждого раздела (INDEX и
  CONTAINER), внутри его размера.
* «TER2 — необязательное расширение» — нет: в нём 16 % рабочих контейнеров и
  единственный служебный, без которого модуль рельефа не стартует.
* «Ручка контейнера = номер тайла X/Y/уровень» (по строкам
  `getContainerId(X, Y, Level)`) — это путь `Surface`-слоя (подложка-картинка),
  у `SoarTerrain` ручка — номер блока из 8192 точек SOAR.
* Семь из восьми поворотов сетки (см. выше): у них средний размер контейнера
  в море 3,2…5,5 КБ против 208 байт у верного.

## Сборка кипрского TER — `src/atlascut.js`

`node src/atlascut.js out/ter-cyprus [--box lon0,lat0,lon1,lat1] [--copies]`

* Рамка по умолчанию lon 32.0…34.9, lat 34.3…36.0 (Кипр + ~20 км).
* Обходятся все треугольники SOAR, задевающие рамку, и берутся контейнеры с их
  точками деления — это заодно все предки (DAG) кипрских точек: 1135
  контейнеров, 2,9 МБ (вместе со 187 особыми 208-байтовыми).
* Сохраняются **все 873 814 ручек** (номер точки прошивка считает из ручки) и
  заводская раскладка шапки/ревизии/индекса — корень не меняется, в листьях
  переписаны столбцы смещений и размеров. Прочие ручки указывают на **один**
  заводской морской контейнер.
* Две половины, как у завода: `TER` (шапка, ревизия, индекс 17,5 МБ, данные)
  и `TER2` (шапка + служебный контейнер, 4496 байт). В шапках +0x48 сумма,
  +0x50 свой размер, +0x58 база TER2 = размер TER. `.conf` обоих — через
  `src/conf.js`.
* Итог: **19,6 МБ + 4,4 КБ вместо 2,1 ГБ**. Сверка `check()`: ручки подряд,
  по каждому смещению CONTAINER своего размера, у настоящих ручка в шапке своя
  и байты совпадают с заводскими (1322 из 1322); карта по собранному файлу —
  остров на месте, за рамкой море.

Риски (не проверено на машине):

* Общий морской контейнер несёт ручку другого контейнера. Задача загрузки
  берёт базу из запрошенной ручки, сверку ручки мы видели только в
  `loadServiceContainer` — но весь путь не прочитан. Если рельеф поломается,
  `--copies` кладёт копию на каждую ручку со своей ручкой в шапке (193 МБ).
* За рамкой рельеф — нулевое море, на краю рамки над Турцией будет обрыв.
* При установке поверх старого раздела без TER2 из образа старый TER2 с той же
  меткой времени сел бы в слот вторым ресурсом — поэтому TER2 кладётся свой.
