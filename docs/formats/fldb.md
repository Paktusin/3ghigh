# Контейнер FLDB

## Контейнер FLDB

Файлы XAC, LIT, TMC, LABEL. Числа little-endian.

| Смещение | Размер | Значение |
|---|---|---|
| 0x00 | u32 | 0x220 — начало области каталога |
| 0x08 | u32 | Unix-время сборки |
| 0x0C | u32 | количество файлов |
| 0x10 | u32 | 0x24 = 36, размер записи каталога |
| 0x14 | 4 б | сигнатура `FLDB` |
| 0x20 | | текстовый блок `!dbinfo0001 ... !enddbinfo` |
| 0x220 | | каталог |

Запись каталога, 36 байт:

| Смещение | Размер | Значение |
|---|---|---|
| +0x00 | u32 | смещение данных |
| +0x04 | u32 | размер |
| +0x08 | char[24] | имя, дополнено нулями |
| +0x20 | u32 | контрольная сумма |

Данные выровнены по 2048 байт. Раскладка детерминирована: `src/repack.js`
пересобирает контейнер **побайтно идентично** — проверено на контейнерах TMC,
XAC3 и LABEL.

Начало каталога подтверждается полем 0x00, которое и содержит 0x220. Правильность
раскладки проверяется тем, что у файлов с одинаковым содержимым совпадает и
контрольная сумма: у всех 45 файлов `.plz` она одна, у всех 45 `.poi` тоже одна.

**Не разобрано:** алгоритм контрольной суммы. Проверены 75 вариантов (все
стандартные полиномы CRC32 во всех комбинациях init/reflect/xorout, Adler-32,
Fletcher-32, FNV, djb2, sdbm, Jenkins, суммы и XOR по словам) — совпадений нет.
Не подошла и атака по НОД на парах сообщений одинаковой длины: наибольший общий
делитель нулевой степени, то есть это не линейный CRC. То же поле встречается
как `checkcrc` в `.conf` и как `fdefcrc` в `.pkg`.

Практического препятствия это не создаёт: при установке поле не проверяется, а
при пересборке существующих данных переносится как есть.

### Ошибка, которую стоит знать

Изначально раскладка была разобрана со сдвигом на 4 байта: каталог считался
начинающимся с 0x21C, а поля шли как сумма, смещение, размер, имя. Смещения,
размеры и имена при таком чтении получались верными — сдвиг компенсировался, —
а вот сумма каждой записи читалась от предыдущей.

Это давало два ложных следствия. Во-первых, будто у 45 файлов `.plz` с
идентичным содержимым 45 разных сумм, откуда делался вывод, что поле не зависит
от содержимого. Во-вторых, будто за каталогом лежат ещё 4 загадочных байта — на
самом деле это сумма последней записи, из-за чего пересборка не была побайтной.

Оба следствия исчезли после исправления. Проверка «одинаковое содержимое —
одинаковая сумма» отличает верную раскладку от сдвинутой, и её стоит применять
при разборе подобных структур.
