# Разбор навигационной базы MMI 3G / 3G+

Реверс-инжиниринг формата навигационных данных Audi/VW MMI 3G(P) (вендор Becker
Automotive). Всё получено чтением файлов; оригиналы никогда не изменялись.

Разобранный набор: **8R0060884KL, ECE 6.36.0, «EUR 2023»**, 22 ГБ.
Для сверки привлекался второй набор: 8R0060884HS, ROW 5.13.4, покрытие
Австралия и Новая Зеландия (VW Touareg RNS 850).

## Устройство набора

Три слоя, снаружи внутрь:

1. **Метаданные SWDL** — `config.nfm`, `DBInfo.txt`, `metainfo2.txt` плюс копии
   в каталогах релизов. Обычный текст. Здесь регион, версия, список вариантов
   головного устройства, к которым база применима.
2. **Манифест пакета** — `pkgdb/*.pkg` (текст) и по `*.conf` на каждый компонент
   с именем, размером, MD5 и контрольной суммой. Рядом `*.pkg.sig` — 128 байт,
   то есть подпись RSA-1024.
3. **Данные** — контейнеры FLDB и файлы ATLAS, GDB, PIT, XAR, ISO.

Код региона протянут через всё: `GDB_ECE`, `XAC_ECE`, `MMI3G_ECE_Hi_R_6_36_0.pkg`,
метка носителя `DB_ECE_PDU2`. В наборе ROW рынок и код компонентов расходятся:
`market=ROW`, а компоненты `_AN`. Есть и числовой идентификатор в `userflags`:
`region@1` для Европы, `region@10` для ROW.

## Что за что отвечает

Столбец «статус» отражает степень разобранности: **разобран** — формат описан
и читается кодом, **опознан** — назначение установлено, внутренности нет,
**не трогали** — руки не дошли.

### Внутри контейнеров XAC

Три контейнера — части одной базы (`DB=1/3`, `2/3`, `3/3`), суммарно 4,5 ГБ.

| Файл | Метка в начале | Назначение | Статус |
|---|---|---|---|
| `<П>_<CC><TT>_<n>.xac` | `XAC HEADER` | дорожный тайл: CC — код страны, TT — номер тайла | разобран |
| `<П>.xah` | `XACDB HEADER` | общий индекс всей базы XAC | частично |
| `<П>.ras` | `DB RASTERINFOS` | пространственный индекс, 191 МБ | не трогали |
| `<П>_<i>.ort` | `ORTSNAMEN` | названия населённых пунктов, по файлу на страну; номер страны лежит как u16 BE по 0x16 | разобран |
| `<П>_<i>.plz` | `GR POSTLEITZAHL` | почтовые индексы, 104 байта | не трогали |
| `<П>_<i>.poi` | `GLOBAL POIS` | точки интереса, 148 байт | не трогали |
| `<П>_<i>_<L>.b` | `VERYSMART XAC HD` | геометрия укрупнённого уровня L: внутри `SMART XAC HEADER` × 586 и `VEKTORBLOCK` × 581 | структура да |
| `<П>_<i>_<L>.v` | `VERYSMART XAC HD` | ссылки того же уровня: `LAYER 1 VERWEISE` × 581 | структура да |

Уровни `L` равны 3 и 4, и это согласуется с разделами `XAC-STRUKTUR L1…L4`
в общем индексе: база многоуровневая, детальные тайлы дополнены укрупнёнными
для дальней маршрутизации.

#### Раздел XAC HEADER — разобран

Заголовок тайла, 196 байт. Разобран сравнением по 121 тайлу с известными
величинами; смещения от начала раздела:

| Смещение | Значение |
|---|---|
| +0x18 | код тайла, 4 символа |
| +0x1C | имя файла без расширения |
| +0x2C | время сборки тайла, `ГГГГММДДччммсс` |
| +0x3C | время сборки базы, одно на все тайлы |
| +0x4C | u16 — номер тайла в реестре `XAC-STRUKTUR` |
| +0x4E | u16 — индекс страны, он же номер справочника `.ort` |
| +0x54…+0x60 | рамка тайла: xmin, ymin, xmax, ymax — та же, что в таблице L1 |
| +0x70 | число разделов `VEKTORBLOCK` |
| +0x74 | смещение первого `VEKTORBLOCK` |
| +0x78 | суммарный размер всех `VEKTORBLOCK` |
| +0x7C…+0x88 | четыре границы уровней — те же, что в записи реестра |

Заголовок дублирует собственную запись реестра: при переносе тайла править
придётся оба места. Назначение полей +0x64, +0x68, +0x6C, +0x8C…+0x98, +0xA4
и +0xA8 не установлено; хвост +0xB0…+0xC0 постоянен у всех тайлов.

#### Раздел LAYER 1 VERWEISE — что известно

Лежит только в файлах уровней 2…4: `<П>_<код>_2.xac` и `.v`-файлах регионов;
в `_1.xac` его нет. «Verweise» — ссылки: связь укрупнённых уровней с уровнем 1.
Шапка `u32 0x00010000`, `u32` число записей (2 у Ватикана, 13 у региона 0),
дальше таблица смещений и короткие байтовые серии.

Главное для переноса тайла: **абсолютных координат внутри нет**. Перебор всех
i32 в разделах Ватикана не дал ни одного значения в диапазоне рамки тайла ни
по x, ни по y. Ссылки индексные, при сдвиге геометрии их менять не нужно.

### Общий индекс .xah

Обход находит 22 раздела и покрывает 1,6 МБ из 2,0 МБ, дальше обрывается.
Названия говорят сами за себя:

```
XACDB HEADER   STRING          BASIC NAME      LANGUAGE     COUNTRY
UNICODE INFO   UNICODE SORT    UNICODE COMBI   UNICODE CASE
ATTRIBUTE      ZF-TOKEN        ZF-LTMAP        ETA-KOSTEN   MAJOR ROAD
BUILD INFOS    XAC-STRUKTUR    XAC-STRUKTUR L1…L4
FE GRUPPEN     L3 GRUPPEN      FE_MIX_INFO     NACHBARN
VIA-LISTE      L4 LOAD TABLE
```

Всего 26 разделов, обход покрывает файл целиком. Последние четыре нашлись
поздно: разборщик спотыкался о подчёркивание в имени `FE_MIX_INFO`.

`NACHBARN` — «соседи», таблица смежности тайлов, разобрана ниже. Вместе с
`FE GRUPPEN`, `L3 GRUPPEN` и `L4 LOAD TABLE` это значит, что тайлы упоминаются
не только в `XAC-STRUKTUR`: индексных структур, ссылающихся на них, как
минимум шесть.

В заголовке `XACDB HEADER` по смещению **72** лежит число тайлов, `0x00000EC1`
то есть 3777. Рядом ещё несколько счётчиков неустановленного назначения:
44747 по смещению 76, 22 по смещению 80 (совпадает с числом разделов до
исправления разборщика), а также 14129, 26903, 43674 и 123843.

Практический вывод: **изымать тайлы из базы дорого**. Придётся согласованно
править шесть структур и неизвестное число счётчиков. Подменять содержимое
существующего тайла куда безопаснее — счётчики и таблицы смежности при этом
остаются верными.

Здесь стоит выделить три: `STRING` — тот самый всемирный словарь названий, где
рядом с CYPRUS лежат CALIFORNIA и COLOMBIA; `ETA-KOSTEN` — веса для расчёта
времени в пути, то есть часть маршрутизации; `MAJOR ROAD` — магистральная сеть.

#### Раздел NACHBARN — разобран

Таблица смежности. Шапка u32 `0x00010000`, дальше по записи на тайл в порядке
реестра: `u16` номер тайла, `u16` номера соседей, `0xFFFF`. После последней
записи ещё одно слово `0xFFFF`. Разбор в `parseNeighbors()` из `src/struktur.js`.

В европейском наборе 18 195 связей, в среднем 4,8 на тайл, больше всех — 22 у
GR36 в Эгейском море. Связь почти всегда взаимная: 5 исключений, все в России.
586 пар не касаются рамками — это паромы: BE0R–UK00, DM0V–UK02. 36 тайлов без
соседей — острова: Азоры PO1O и Русский Север.

Именно через соседей устройство добирается до анклавов, которых нет в общем
растре: VA00 — единственный сосед IT1H среди «чужих», VA01 — сосед IT3S.
Тайл, перенесённый на Кипр, соседей иметь не обязан: островных тайлов без
связей в базе достаточно.

#### Раздел COUNTRY — разобран

Реестр стран. Записи по 10 байт, начинаются со смещения 64 в разделе:

| Поле | Размер | Пример |
|---|---|---|
| внутренний код | 2 | `DM` |
| ISO 3166-1 alpha-2 | 2 | `DK` |
| ISO 3166-1 alpha-3 | 3 | `DNK` |
| код автомобильной регистрации | 3, дополнен нулями | `DK` |

Записей 216 — реестр всемирный и одинаков во всех региональных наборах: там же
штаты США, провинции Канады, страны Африки. Дорожные данные в европейском
наборе есть только у 46 из них, так что наличие записи покрытия не означает.

Таблица закрывает вопрос о внутренних кодах, которые до неё приходилось выводить
по топонимам: `MJ` — Мальта (MLT), `M1` — Черногория (MNE), `MB` — Молдова (MDA),
`KO` — Косово (XK), `DM` — Дания, `SW` — Швеция, `SP` — Испания, `AU` — Австрия,
`IR` — Ирландия. Отдельными записями идут Англия, Шотландия и Уэльс — с пустыми
кодами ISO и автомобильным `GB`.

**Кипр в реестре есть**: запись 112, внутренний код `CY`, `CY` / `CYP` / `CY`.
Турция — запись 108. То есть слот под страну заводить не нужно, он уже занят.

#### Раздел XAC-STRUKTUR — разобран

Реестр тайлов. Записи по 84 байта со смещения 24, в европейском наборе их
**3777** — ровно столько тайлов лежит в контейнерах XAC. Разбор в
`src/struktur.js`.

| Смещение | Значение |
|---|---|
| +0x00 | код тайла, 4 символа: две буквы страны и две цифры номера |
| +0x04, +0x08, +0x0C, +0x10 | накопленные размеры групп `VEKTORBLOCK` — границы уровней |
| +0x14, +0x18 | смещение и размер раздела `ZE-NAMEN` в файле тайла |
| +0x1C, +0x20 | то же для `ZE-NAMEN-MMI` |
| +0x24, +0x28 | то же для `HAUSNUMMERN`, нули если раздела нет |
| +0x2C, +0x30 | то же для `LOCAL POIS` |
| +0x3C, +0x40 | то же для `RASTERINFOS` |
| +0x44, +0x48 | ещё две границы групп `VEKTORBLOCK` |

Соответствие проверено на 151 тайле: все пять разделов совпали по смещению и
размеру в 100% случаев. Границы уровней проверяются иначе — например у тайла
`AB03` поля дают 26696, 42500, 44700, 45356, а это в точности суммы первых
одного, двух, трёх и четырёх блоков `VEKTORBLOCK`.

Назначение полей +0x34, +0x38, +0x4C и +0x50 не установлено — везде нули.

Практический вывод для добавления страны: тайл существует для устройства
постольку, поскольку он записан здесь. Запись описывает разделы своего файла,
поэтому новый тайл требует не только самого файла, но и строки в этом реестре.
Тайлов `CY**` в реестре нет.

#### Разделы XAC-STRUKTUR L1…L4 — разобраны

Четыре поуровневые таблицы по 166 212 байт. Записей в каждой **3777**, столько же
и в том же порядке, что в главном реестре, — то есть на каждый тайл приходится
по строке на уровень.

Заголовок таблицы: по +0x10 длина, по +0x14 номер уровня (`0x00010001`…`0x00010004`).
Записи идут с 24, по 44 байта:

| Смещение | Значение |
|---|---|
| +0x00…+0x0C | рамка: xmin, ymin, xmax, ymax; `0x7FFFFFFF` означает, что данных на уровне нет |
| +0x14 | смещение области `VEKTORBLOCK` в файле уровня |
| +0x18 | суммарный размер этой области |
| +0x1C | размер раздела `XAC HEADER` |
| +0x20 | размер раздела `ZF-NAMEN` |
| +0x24 | суммарный размер данных тайла на уровне (для уровней 2…4) |

Уровень 1 — это файл `<П>_<код>_1.xac`, уровень 2 — `<П>_<код>_2.xac`.
Уровни 3 и 4 отдельными файлами не лежат: они кусками внутри укрупнённых
`<П>_<регион>_3.b` и `_4.b`, и смещения там отсчитываются от начала куска.
Сходится и арифметика: смещение `VEKTORBLOCK` равно сумме размеров `XAC HEADER`
и `ZF-NAMEN`, а поле +0x24 — сумме этого смещения и размера области.

Проверка на 120 тайлах: L1 против файлов `_1` и L2 против `_2` совпали полностью,
расхождений нет. Пример для Монако — рамка уровня 1 читается как
43.7248…43.7515 с.ш., 7.4094…7.4386 в.д., то есть ровно те границы, которые
независимо получаются разбором самого тайла.

Практический смысл: именно здесь записано, в каких координатах искать тайл.
Файл тайла и строка в главном реестре без записи здесь бесполезны — устройство
не поймёт, к какому месту карты они относятся.

### Растровый индекс RASTERINFOS — заголовок разобран

Один и тот же формат у общего `<П>.ras` на 191 МБ и у разделов `RASTERINFOS`
внутри тайлов, где они занимают десятки-сотни байт. Различаются меткой
(`DB RASTERINFOS` против `RASTERINFOS`) и полем версии: `0x00010000` у общего
индекса, `0x00020000` у тайловых. Разбор в `src/raster.js`.

| Смещение | Значение |
|---|---|
| +0x00 | метка, 16 байт |
| +0x10 | длина полезной части |
| +0x14 | версия |
| +0x18…+0x24 | рамка растра: xmin, ymin, xmax, ymax |
| +0x28, +0x2C | число ячеек по горизонтали и вертикали |
| +0x30, +0x34 | шаг ячейки, всегда 1000 по обеим осям |
| +0x38 | упаковка длинами серий, слова u16 BE |

Шаг 1000 единиц — это километр по меридиану и около 1,2 км по долготе на
широте 40°. Размеры сетки связаны с рамкой как `размах / 1000 - 2`: рамка шире
растра ровно на одну ячейку с каждой стороны.

Полезная часть — поток слов, где младшие 15 бит задают длину серии, а старший
бит хранит значение ячейки. Сумма длин серий в точности равна числу ячеек
сетки: проверено на 40 тайлах, совпадение 40 из 40.

**Что означает значение ячейки — не установлено.** Очевидная догадка «в ячейке
есть дорожные данные» проверена и отвергнута: узлы, декодированные из
`VEKTORBLOCK`, попадают в помеченные ячейки в 42,7% случаев при доле помеченных
ячеек 43% — то есть ровно как при случайном совпадении. Перебирались обе
развёртки сетки, оба направления строк и сдвиг на ячейку; лучший вариант от
случайного не отличается.

#### Глобальный `.ras` — разобран

Общий растр устроен иначе, чем тайловые: это **плотная сетка по u16 на ячейку**,
без упаковки. Заголовок тот же, но рамка со знаком: западный край −31,4°,
восточный 179,9°, широта 27,3…83,8° — Европа и вся Россия до Тихого океана.
Сетка 15212 × 6280 километровых ячеек, 95,5 миллиона; размер файла делится на
неё ровно — 2,00 байта на ячейку.

Значение ячейки — **номер тайла в реестре `XAC-STRUKTUR`**, покрывающего эту
клетку; `0xFFFE` — тайла нет. Порядок хранения **по столбцам**: индекс ячейки
равен `cx × ny + cy`. Проверка по центрам рамок всех 3744 тайлов с данными L1:
2556 совпали, 530 указали на соседний тайл (рамки перекрываются), 658 дали
«пусто» — прибрежные тайлы, у которых центр рамки в море. При порядке по
строкам совпадает 1 из 535 проверенных.

Это и есть механизм поиска тайла по координате. Чтобы устройство нашло тайл в
новом месте, достаточно записать его номер в ячейки нового расположения.
Ячейки Никосии, Лимассола и Ларнаки сегодня пусты — писать в них можно.

Занято 38,5 миллиона ячеек из 95,5. **254 тайла в растре не упомянуты ни одной
ячейкой** — все крошечные, площадью до 0,009 кв. градуса: анклавы вроде
Ватикана и мелкие тайлы Греции, Финляндии, России, лежащие внутри чужой рамки.
Растр хранит один номер на ячейку, и достаётся он большему тайлу; малый
устройство находит через `NACHBARN`. Мальта в центре своей рамки даёт «пусто»
честно: там пролив между островами. Инструмент — `src/rasidx.js`.

## Контейнер FLDB

Файлы XAC, LIT, TMC, LABEL. Числа little-endian.

| Смещение | Размер | Значение |
|---|---|---|
| 0x00 | u32 | 0x220 — начало области каталога |
| 0x08 | u32 | Unix-время сборки |
| 0x0C | u32 | количество файлов |
| 0x10 | u32 | 0x24 = 36, размер записи каталога |
| 0x14 | 4 б | сигнатура `FLDB` |
| 0x20 | | текстовый блок `!dbinfo0001 ... !enddbinfo` |
| 0x220 | | каталог |

Запись каталога, 36 байт:

| Смещение | Размер | Значение |
|---|---|---|
| +0x00 | u32 | смещение данных |
| +0x04 | u32 | размер |
| +0x08 | char[24] | имя, дополнено нулями |
| +0x20 | u32 | контрольная сумма |

Данные выровнены по 2048 байт. Раскладка детерминирована: `src/repack.js`
пересобирает контейнер **побайтно идентично** — проверено на контейнерах TMC,
XAC3 и LABEL.

Начало каталога подтверждается полем 0x00, которое и содержит 0x220. Правильность
раскладки проверяется тем, что у файлов с одинаковым содержимым совпадает и
контрольная сумма: у всех 45 файлов `.plz` она одна, у всех 45 `.poi` тоже одна.

**Не разобрано:** алгоритм контрольной суммы. Проверены 75 вариантов (все
стандартные полиномы CRC32 во всех комбинациях init/reflect/xorout, Adler-32,
Fletcher-32, FNV, djb2, sdbm, Jenkins, суммы и XOR по словам) — совпадений нет.
Не подошла и атака по НОД на парах сообщений одинаковой длины: наибольший общий
делитель нулевой степени, то есть это не линейный CRC. То же поле встречается
как `checkcrc` в `.conf` и как `fdefcrc` в `.pkg`.

Практического препятствия это не создаёт: при установке поле не проверяется, а
при пересборке существующих данных переносится как есть.

### Ошибка, которую стоит знать

Изначально раскладка была разобрана со сдвигом на 4 байта: каталог считался
начинающимся с 0x21C, а поля шли как сумма, смещение, размер, имя. Смещения,
размеры и имена при таком чтении получались верными — сдвиг компенсировался, —
а вот сумма каждой записи читалась от предыдущей.

Это давало два ложных следствия. Во-первых, будто у 45 файлов `.plz` с
идентичным содержимым 45 разных сумм, откуда делался вывод, что поле не зависит
от содержимого. Во-вторых, будто за каталогом лежат ещё 4 загадочных байта — на
самом деле это сумма последней записи, из-за чего пересборка не была побайтной.

Оба следствия исчезли после исправления. Проверка «одинаковое содержимое —
одинаковая сумма» отличает верную раскладку от сдвинутой, и её стоит применять
при разборе подобных структур.

## Дорожный тайл .xac

Имена внутри контейнера: `<ПРЕФИКС>_<CC><TT>_<n>.xac`, где CC — внутренний код
страны, TT — тайл. Коды локальны для базы: в европейском наборе `AU` — Австрия,
в наборе AN `AT` — Австралия.

### Разделы

Сплошная последовательность: 16 байт имени, u32 BE длина полезной части,
полезная часть. Полный размер раздела равен длине плюс 20. Обход покрывает файл
ровно до конца. Встречаются `XAC HEADER`, `ZF-NAMEN`, `VEKTORBLOCK`, `ZE-NAMEN`,
`ZE-NAMEN-MMI`, `HAUSNUMMERN`, `LOCAL POIS`, `RASTERINFOS`.

### Заголовок VEKTORBLOCK

Смещения от начала раздела:

| Смещение | Значение |
|---|---|
| 0x14 | u16 BE — версия структуры: 3, 4 или 5 |
| 0x18 | 4 x i32 BE — границы: xmin, ymin, xmax, ymax |
| 0x28 | 2 x i32 BE — опорная точка блока |

Версия коррелирует с масштабом: медианный охват 2,5 км у v3, 3,5 км у v4,
24 км у v5.

### Проекция

Равнопромежуточная цилиндрическая:

```
долгота = X / 72000
широта  = Y / (40000000 / 360)     // 111111.111… — метры на градус
```

Y — метры по меридиану для сферы окружностью 40 000 км. X — угловая величина,
20 единиц на угловую секунду. Выведено по микрогосударствам с точно известными
координатами, проверено на Ватикане с точностью около 100 метров.

Побочная находка: у Ватикана два тайла — `VA01` это собственно Ватикан,
`VA00` — Кастель-Гандольфо, экстерриториальное владение Святого Престола.

### Записи, версии 3 и 4

Запись переменной длины. В хвосте лежит самоиндекс — слово u16 BE, равное
смещению записи, делённому на 2. Координаты хранятся дельтами от опорной точки
блока. Признак расширенной записи — старший бит первого байта.

```
обычная    : dx = u16BE(p)   - 0x4000     dy = u16BE(p+2) - 0x8000
расширенная: dx = i16BE(p+2)              dy = i16BE(p+4)
```

Связи между узлами: внутри записи слово с двумя старшими битами (`0xCxxx`)
ссылается на узел по идентификатору `w & 0x3FFF`. Засчитываются только взаимные
ссылки — у цели должно найтись слово `0x4000 | (q/2)`.

**Версия 3.** Одна сплошная секция записей с 0x60. Слово по смещению 0x4E — её
конец; ноль означает «до конца блока», ненулевое отделяет вторую секцию.

**Версия 4.** Блок нарезан на под-блоки. Каждый начинается с рамки — четырёх
u32 BE (xmin, ymin, xmax, ymax) внутри границ блока, затем идут записи того же
формата. Опорная точка при этом общая, блочная, а не своя у каждого под-блока:
с опорой на угол рамки попадает 50% записей, на центр 30%, на опору блока 100%.
Конец данных берётся из u32 по смещению 0x60.

### Анатомия записи: что известно и чего нет

Разбор записей Ватикана (`EJ211_VA01_1.xac`, 3 блока, все версии 3, 165 записей).
**Важная оговорка по разбору:** смещения в заголовке `VEKTORBLOCK` (`0x14` версия,
`0x18` рамка, `0x28` опора, `0x4E` конец секции записей) отсчитываются **от начала
раздела**, то есть включая 20-байтовую шапку «имя + длина». Если срезать блок после
шапки, получится «версия 13» и мусорные рамки.

Раскладка: `[dx u16][dy u16][слова середины…][самоиндекс u16 = смещение/2]`,
длина записи 8…56 байт. Слова середины: 225 связей (`0xCxxx` → узел `w & 0x3FFF`),
192 обратные ссылки (`0x4xxx`), 372 прочих. **Смысл слова зависит от позиции:**

| позиция | что стоит | толкование |
|---|---|---|
| 0 (сразу за координатами) | `0xC`×106, `0x4`×53 | почти всегда связь |
| 1 | `0x0`×95 (мелкие значения) | атрибут |
| последнее перед самоиндексом | только `0x4`×91 или `0x0`×74, никогда `0xC` | терминатор |

Самая частая запись (64 из 165) — три слова середины: `[связь][атрибут][терминатор]`.

**Проверенная и отвергнутая гипотеза.** Повторяющиеся значения `0x0169` (×27) и
`0x026d` (×23) выглядели как идентификаторы улиц, но группировка записей по ним даёт
разброс 562 м при габарите тайла 911 м, и точки не складываются в цепочку. Значит это
не имя улицы. Значения `0x8087` и `0x8095` (по 5 записей, разброс 89 и 125 м) остаются
правдоподобными кандидатами, но не доказаны.

**Следствие: побайтный round-trip XAC пока невозможен** — в отличие от элемента GDB,
который понятен целиком, здесь середина записи не расшифрована, и писать туда нечего.
Приём, доказавший энкодер GDB, здесь сработает только после разбора атрибутов.

### Записи v3 на большой выборке: структура групп

Ватиканский разбор опирался на 165 записей. Собран корпус побольше: из
контейнера `XAC` взяты 244 разреженных тайла, найдены **250 блоков v3** и
разобраны **29 045 записей** из 247 блоков.

**Где какая версия.** В разреженных тайлах v3 практически единственная: 250
блоков v3 против одного v4 и ни одного v5. В плотных городских тайлах наоборот
— почти всё v5 (у Праги 16 блоков, все пятой версии; у Больцано 16 блоков, из
них 13 — v5). Отсюда вывод для проекта: **Кипру с его редкой сетью нужен v3**,
и неразобранная v5 на пути не стоит.

**Структура слов середины.** Самые частые образы по старшим полубайтам:

```
c88244  3.4%     c8824   2.0%     44c882  1.7%
c88344  3.2%     c8804   2.0%     4c8824  1.6%
c88144  1.8%     c8814   1.7%     c883c8834  1.3%
```

Последний образ показателен: группа `c 8 8 x` **повторяется**. То есть запись —
это последовательность групп «связь + два слова `0x8xxx` + мелкое слово», а
в конце идут слова-терминаторы `0x4xxx` / `0x0xxx`. Позиционная статистика это
подтверждает: на позиции 0 преобладает `0xC` (52%), на позициях 1 и 2 — `0x8`
(48% и 65%), а последнее слово — `0x4` (50%) или `0x0` (28%), `0xC` там не
бывает.

### Слова `0x8xxx` — это данные, а не ссылки

Проверено прямым разрешением значений в номера узлов того же блока, с контролем
на случайных величинах в том же диапазоне:

| Слово | Сколько | Разрешается в узел |
|---|---|---|
| `0xCxxx` (связь) | 19 279 | **84.8%** |
| `0x8xxx` | 41 206 | 5.4% |
| `0x4xxx` | 18 721 | 0.5% |
| случайное (контроль) | 23 600 | 7.7% |

У `0x8xxx` доля **ниже случайной**, то есть это не ссылки. Значит именно в них
лежат атрибуты связи, и именно их надо понять, чтобы генерировать записи.

**Что про них известно.** Первое слово: 1558 различных значений, плотно жмётся
к полосе `0x98…0xa8` (152–168), восемь самых частых покрывают 45%. Второе: 3387
различных, разбросано широко. Пара как 24-битное число почти уникальна — 20 362
различных на 30 092 групп.

**Что отвергнуто.** Длина отрезка: корреляция с расстоянием до целевого узла
0.028 у первого слова и 0.274 у второго — слишком слабо. Азимут: среднее
расхождение 56° при 90° у случайного — сигнал есть, но для настоящего азимута
ожидался бы почти ноль, так что это зацепка, а не разгадка.

### Первое слово `0x8xxx` — класс дороги (сопоставление с OSM)

Смысл вскрыт не угадыванием, а сопоставлением с известным ответом. Взят блок v3
`EJ211_FR9H_2.xac` (Франция, рамка 0.43–0.78° в.д., 46.28–46.64° с.ш., 250
узлов, 267 связей с атрибутами), для той же рамки скачан OSM (10 186 дорог).

**Строгое сопоставление:** связь засчитывается, только если **оба** её конца
ближе 60 м к **одной и той же** дороге OSM. Так сошлись 223 связи из 267.

| Класс OSM | n | Частые значения `w1` |
|---|---|---|
| primary | 50 | **2, 3, 4** |
| secondary | 26 | **51, 52, 53, 54** |
| tertiary | 51 | 57, 155, 156, 164 |
| unclassified | 60 | **154** (43 из 60) |
| residential | 22 | 152, 169, 170 |
| track | 7 | **168** (все семь) |

В шестнадцатеричном виде значения ложатся полосами `0x02–0x04`, `0x33–0x39`,
`0x98–0xAA`, и разрез по старшему полубайту это подтверждает:

```
w1>>4 = 0x00                 primary 83%
        0x01,02,05,06,11     primary 100% (выборки по 2–4 связи)
        0x03                 secondary 59%
        0x09                 unclassified 52%, tertiary 21%, residential 14%
        0x0a                 tertiary 33%, track 29%, residential 25%
```

**Чем важнее дорога, тем меньше значение.** То же видно и по скоростным
ограничениям OSM: 90 км/ч → медиана `w1` = 4, 70 → 52, 50 → 154, то есть
величина ведёт себя как стоимость проезда, а не как скорость.

**Рабочая таблица для генерации** (по этим данным, требует проверки на машине):

```
motorway, trunk, primary  ->  0x02…0x04
secondary                 ->  0x33…0x36
tertiary                  ->  0x39 или 0x9C
unclassified, residential ->  0x98…0x9A
track                     ->  0xA8
```

**Оговорки.** Выборка — один блок; сопоставление по геометрии шумит (в плотной
сети OSM рядом с главной дорогой часто лежит второстепенная). Значение второго
слова `0x8xxx` и мелкого слова группы по-прежнему неизвестны: у второго 3387
различных значений при широком разбросе. Перед генерацией таблицу надо
подтвердить на нескольких блоках из разных стран.

### Заголовок под-блока: 20 байт, а у v5 — 22

Из `FUN_08270da0`: читаются версия, смещение и **четыре `u32` рамки**
(xmin, ymin, xmax, ymax), после чего возвращается размер заголовка:

```c
if (версия > 4) { поле[0xc] = u16 по смещению 20;  return 22; }
else            { поле[0xc] = позиция + 20;        return 20; }
```

То есть у v5 в заголовке под-блока есть **лишний `u16`**, которого нет у v3/v4.
Это зацепка к границам записей v5, которые до сих пор не восстанавливались.

### Запись устроена по типу, а не по фиксированной раскладке

Это объясняет, почему «слова середины» выглядели произвольными. Из
`FUN_082740bc`:

```c
тип = первый байт & 0xc0;                 // выбор ветки
id  = ((байт2 & 7) << 8) | байт3;         // 11-битный идентификатор типа
опис = таблица + 0x1c + id * 4;           // запись описателя, 4 байта
b = опис[0];
if (b & 0x80) { b = следующий байт; смещение += 2; }   // переопределение
if (опис[2] & 0x80)      смещение += 2;
if (b & 0x40)            смещение += 4;
if (b & 0x10)            смещение += 4;
if (b & 0x20)            дальше идёт СПИСОК ССЫЛОК
```

**Состав записи задаётся описателем из таблицы**, а таблицу отдаёт
`FUN_08eb3874` — она берётся из загруженной структуры, не из самого блока.
Найти эту таблицу в данных — следующий шаг: без неё запись не разобрать, с ней
разбор становится детерминированным.

Есть и ветка косвенности: если у `байт2` взведён бит 3, разбор **уходит назад**
на `((байт2 & 7) << 8 | байт3) * 2 + 2` байт и читает описатель оттуда.

### Список ссылок: старшие биты — это флаги, а не типы

Цикл чтения списка:

```c
do {
  hi = байт[p]; знач = ((hi & 0x3f) << 8) | байт[p+1];  p += 2;
  if (знач != маркер) { … сохранить ссылку … }
} while (hi & 0x40);        // продолжать, пока взведён бит 6
```

Значение — **14 бит**, а два старших бита слова это признаки: **бит 6 означает
«дальше есть ещё»**. Отсюда `0xCxxx` — ссылка, за которой следуют другие, а
`0x8xxx` — последняя в списке.

**Расхождение, которое надо разрешить.** По корпусу из 29 045 записей слова
`0x8xxx` разрешались в номер узла лишь в 5.4% случаев (при 7.7% у случайного
контроля), тогда как `0xCxxx` — в 84.8%. Если бы все они были ссылками одного
вида, доли совпали бы. Значит встреченные нами `0x8xxx` лежат **не в списке
ссылок**, а в полях, которые идут до него и включаются битами описателя. Наша
плоская модель «слова середины» смешивала то и другое — отсюда и путаница.

Что при этом остаётся в силе: сопоставление с OSM показало осмысленную связь
первого слова `0x8xxx` с классом дороги. Теперь понятно, почему оно вообще
осмысленно, но толковать его надо уже в рамках описателя типа.

### Таблица описателей типа — это раздел `ATTRIBUTE`

Сходится арифметика: код читает описатель как `таблица + 0x1c + id*4`, где `id`
11-битный, то есть до 2048 значений. В разделе `(8200 − 0x1c) / 4 = **2043**`
записи по 4 байта — совпадает.

**Значащий байт — последний в четвёрке.** Записи в файле выглядят как
`00 08 48 b1`, и первый байт почти всегда нулевой; при чтении по первому байту
флаги не набираются вовсе. А если брать последний, распределение становится
осмысленным:

```
0x80 переопределение   1361  67%
0x40 +4 байта           712  35%
0x20 СПИСОК ССЫЛОК     1497  73%
0x10 +4 байта           549  27%
прочие биты: 0x02 — 1129, 0x01 — 840, 0x08 — 554, 0x04 — 391
```

Частые значения: `0xaa`, `0xb2`, `0xa2`, `0xa3`, `0x62`, `0xab`, `0xb3`.
У большинства типов список ссылок присутствует — чего и ждёшь от дорожной сети.

Объяснение простое: данные `u32` при загрузке переворачиваются (файл
big-endian, процессор little-endian), поэтому в памяти байт флагов оказывается
первым. **Это вывод, а не прочитанное в коде** — сам переворот мы не нашли, но
без него распределение флагов бессмысленно, а с ним осмысленно.

### Что это меняет

Разбор записи становится **однозначным**: из записи берётся 11-битный тип, по
нему из `ATTRIBUTE` читается описатель, а он говорит, какие поля присутствуют и
где начинается список ссылок. Больше не нужно угадывать раскладку по
статистике — а значит открывается и путь к записи, то есть к генерации.

**Проверено и не подтвердилось: описатель применяется не к нашим записям.**
Гипотезу «тип записи = `((b2 & 7) << 8) | b3`» прогнали на 13 214 записях
корпуса. Значение попадает в пределы таблицы у 99.8% записей, но выбирает
описатели **не лучше случайного**: бит списка ссылок оказывается взведён у
72.6% против 73.2% у контроля на случайных идентификаторах. Сигнала нет.

Причина видна в коде: в `FUN_082740bc` начальное смещение берётся **из
индексной таблицы** (`uVar9 = u16 по индексу * 2`), то есть разбор начинается
не с начала записи, а с произвольного места блока. Функция работает с
«вектором» (FE), а наш обходчик находит узлы по самоиндексу — это разные
сущности. Байты 2–3 в наших записях это `dy`, а не идентификатор типа.

Что остаётся в силе: сама таблица описателей и её раскладка (2043 записи,
значащий байт последний, распределение флагов осмысленное). Не установлено,
откуда берётся идентификатор для узловых записей.

Следующий шаг: разобрать реализацию обхода записей по адресу `0x08271c18` —
она подставляется в итератор функцией `get_firstvect` и является настоящим
пошаговым читателем v3. В Ghidra по этому адресу функция не создана.

### Настоящий читатель записей v3 — разобран по машинному коду

В Ghidra эти функции не оформлены, поэтому дизассемблированы напрямую:
`capstone` умеет SH-4 (`CS_ARCH_SH` + `CS_MODE_SH4A`), а отображение адреса в
смещение файла берётся из заголовков ELF (`LOAD vaddr=08040000 off=0`).

| Адрес | Роль |
|---|---|
| `0x08271c18` | реализация обхода, её подставляет `get_firstvect` |
| `0x08271bcc` | шаг «следующая запись» (тонкая обёртка) |
| `0x08271914` | **ядро чтения записи** |

### Два параллельных потока, а не один

Ключевое, чего не видно из данных: запись читается **из двух потоков сразу**.

* основной поток `r8 = контекст[32] + таблица[16]`, выровнен по 4 байта
  (в коде есть явное выравнивание `and #3` / `and #-4`);
* поток счётчиков `r11 = контекст[28] + блок[56]` — отдельный указатель,
  который идёт своим темпом.

Наша прежняя модель «запись это непрерывный кусок, а конец ищется по
самоиндексу» описывала только первый поток.

### Целые переменной длины

Обе ветки кода используют одну и ту же упаковку — по 7 бит на байт с двумя
расширениями:

```
b = байт;  v = b & 0x7F
v <= 125   ->  значение = v,                        длина 1 байт
v == 0x7E  ->  значение = 126 + следующий байт,     длина 2 байта
v == 0x7F  ->  значение = ((след & 0x7F) << 8) | ещё один,  длина 3 байта
```

Диапазоны: 0…125, затем 126…381, затем до 15 бит.

### Начало записи

```
u16 BE  — дельта, прибавляется к накопителю контекст[48], результат в контекст[52]
          0xFFFF означает КОНЕЦ записей (чтение возвращает -1)
u32 BE  — следующее поле, собирается четырьмя байтами со сдвигами
```

То есть идентификатор записи не абсолютный, а **накапливаемый**: каждая запись
хранит приращение к предыдущему. Это объясняет, почему самоиндекс в хвосте
вообще сходился — он и есть позиция, но получается она сложением.

Константы контекста: маска `0x0003FFFF` (18 бит), пороговые значения
`0x00097FFE` и `0x00008000`.

### Поправка: это индекс имён, а не разбор геометрии

Ядро дочитано до конца, и строки ошибок назвали функцию своим именем —
`get_firstvect_instreet`, «первый вектор в улице»:

```
XAC: NID ist kein ZEN bei get_firstvect_instreet(%08lx)
XAC: u_nid_ntab_infos()-Fehler bei get_firstvect_instreet(%08lx)
XAC: nid_nr>=name_anz==%ld bei get_firstvect_instreet(%08lx)
XAC: keine VReferenz bei get_firstvect_instreet(%08lx)
XAC: gar kein Vektor bei get_firstvect_instreet(%08lx)
XAC: blkp==NULL bei block_nidnr %ld und block_voffset %d
```

`NID` — идентификатор имени, `ZEN` — это `ZE-NAMEN`. То есть функция по имени
улицы находит её векторы, а два потока — это **поток приращений NID** и
**поток смещений векторов** (`block_nidnr` и `block_voffset` прямо из строки).
Геометрию она не разбирает.

### Зато вскрыт формат ссылки на вектор

В конце функция собирает `VReferenz`:

```
r1 = смещение & 0x7FFE          // чётное, 15 бит
r2 = (номер_блока << 16) | r1   // складывается в контекст[16]
```

То есть **ссылка на вектор = `(номер VEKTORBLOCK << 16) | (смещение & 0x7FFE)`**.
Это прямо объясняет флаг сборки `check16BitVBlocknr` из `BUILD INFOS`: номер
блока занимает старшие 16 бит.

### Ширина поля зависит от размера таблицы

```
если контекст[56] > 0x8000  ->  значение читается ТРЕМЯ байтами (24 бита)
иначе                       ->  ДВУМЯ байтами (15 бит)
```

`контекст[56]` берётся из таблицы блока. То есть при большом числе элементов
формат сам расширяется — это надо учитывать и при чтении, и при записи.

**Что остаётся неразобранным.** Собственно геометрия записи: найденный читатель
оказался индексом «имя → векторы». Разбор самих векторов лежит в
`get_names_of_vector` (`FUN_082740bc`) и в ветках, которые из него вызываются;
именно там работает таблица описателей `ATTRIBUTE`.

### Разбор вектора: точная раскладка из `FUN_082740bc`

Константы разборщика вытащены из пулов, поэтому раскладка записана не
приблизительно, а по значениям из кода.

```
p = смещение вектора (из VReferenz & 0x7FFE), отсчёт от начала блока

  требуется  (байт[p] & 0xC0) == 0xC0            // DAT_0827423e = 0xC0
  b2 = байт[p+2];  b3 = байт[p+3];  p += 4

  если (b2 >> 3) & 1:                            // косвенность: описатель лежит раньше
      назад = ((b2 & 7) << 8 | b3) * 2 + 2
      p = p - назад
      b2 = байт[p]; b3 = байт[p+1]; p += 2

  если (b2 >> 6) & 1:  p += 2

  опис = ATTRIBUTE[ ((b2 & 7) << 8) | b3 ]       // 11-битный тип
  f = байт флагов описателя
  если f & 0x80:  f = байт[p];  p += 2           // переопределение из потока
  если опис[2] & 0x80:  p += 2
  если f & 0x40:  p += 4
  если f & 0x10:  p += 4

  если f & 0x20:                                 // список ссылок
      повторять:
          hi = байт[p]
          v  = ((hi & 0x3F) << 8) | байт[p+1]
          p += 2
          если v != 0x3FFF:  записать ссылку     // DAT_082743c8 = 0x3FFF
      пока (hi >> 6) & 1                         // бит 6 — «дальше есть ещё»
```

**Две величины, которых не хватало раньше:**

* `0xC0` — обязательная метка начала вектора в старших двух битах первого байта;
* `0x3FFF` — маркер «ссылки нет»; такие значения в списке пропускаются, а не
  считаются узлами. Наш прежний подсчёт связей их не отфильтровывал.

**Формат хранимой ссылки** (складывается в выходной массив):

```
ссылка = 0x40000000 | (номер_блока & 0x0FFF) << 16 | v
```

То есть 12 бит на номер блока, 14 бит на значение, старшие биты — признаки.
Это согласуется с `VReferenz = (номер << 16) | (смещение & 0x7FFE)`: там номер
блока 16-битный, здесь при упаковке в ссылку он урезан до 12 бит.

**Косвенность — важная деталь.** Если у `b2` взведён бит 3, описатель типа
берётся не отсюда, а на `((b2 & 7) << 8 | b3) * 2 + 2` байт **раньше** по
блоку. То есть соседние векторы могут ссылаться на один общий описатель —
экономия, которая ломает любую попытку читать запись как самодостаточный кусок.

### Таблица смещений векторов в блоках v5 — подтверждена

Раньше про пятую версию было записано: «границы записей не восстанавливаются,
перебор длин 4…16 даёт максимум 44,8%». Причина была в том, что векторы там
**не лежат подряд — их адресует таблица**.

Из `FUN_082740bc`: при версии блока больше 4 и `u16 BE по +0x72 == 1`

```
u32 BE по +0x6c  — смещение таблицы (от начала блока)
u16 BE по +0x70  — число записей
таблица          — u16 BE, смещение вектора = запись * 2
```

**Проверка на данных.** Взяты три плотных тайла (Прага, Больцано, Греция), в
них 39 блоков v5:

* у **всех 39** поля правдоподобны: флаг равен 1, смещение внутри блока, число
  записей положительно и таблица помещается в блок;
* цели таблицы попадают на байт с меткой `0xC0` в **78.7%** случаев (12 249 из
  15 561) при **14%**, ожидаемых случайно, — превышение в пять с половиной раз.

Числа записей осмысленные: 5833, 3641, 6350, 9323 вектора на блок.

Для v3 и v4 таблицы нет (при версии ≤ 4 код обнуляет указатель), и смещение
вектора приходит прямо из `VReferenz`.

### Раскладка вектора: проверена на 11 661 настоящем векторе

Выписанная из констант раскладка прогнана по целям таблицы v5 (Прага, Больцано,
Греция).

```
разобралось без ошибки        8 299 из 11 661   71.2%
отказ «нет метки 0xC0»            2 526         21.7%
отказ «тип вне таблицы»             836          7.2%
```

Семь из десяти векторов разбираются до конца, не выходя за границы блока. Это
больше, чем дало бы случайное совпадение, но и не полное схождение.

**Слабое место — проверка ссылок.** Если значения в списке это номера векторов,
они должны попадать в диапазон таблицы. Попадают в 79.7% случаев (4 591 из
5 758). Но при среднем размере таблицы 8 960 записей **случайное 14-битное
значение попало бы туда с вероятностью 54.7%** — то есть превышение всего в
полтора раза. Как довод это слабо: возможно, ссылки устроены иначе, или их
надо толковать вместе с номером блока из старших битов.

### Отказы объяснились: это не сбои разбора

Первоначальные 21.7% «нет метки» оказались законным случаем. У всех таких целей
первый байт `0x40`, а в коде под него есть отдельная ветка с сообщением
`XAC: nicht hier get_names_of_vector` — «вектор не здесь», то есть ссылка в
другой блок. Распределение по 19 461 цели таблицы:

| Метка | Смысл в коде | Доля |
|---|---|---|
| `0xC0` | вектор лежит здесь | **78.9%** |
| `0x40` | `nicht hier` — вектор в другом блоке | **17.6%** |
| `0x80` | не истолкована | 3.6% |
| `0x00` | `kein Vektor` — ошибка | **0.0%** |

Вместе первые две дают **96.4%**. Отдельно показательно, что `0x00` не
встретился **ни разу**: в коде это признак «вектора нет вовсе», то есть ошибка.
Мы всегда попадаем на настоящую структуру — значит таблица читается верно.

### Раскладка подтверждена по машинному коду

Последовательность проверок сверена с дизассемблером инструкция за инструкцией
(`0x082742a8`…`0x08274314`) и совпала с выписанной ранее:

```
бит 6 у b2            -> p += 2
id = ((b2 & 7) << 8) | b3;   описатель = таблица + 0x1c + id*4
опис[0] со старшим битом  -> флаги берутся из потока, p += 2
опис[2] со старшим битом  -> p += 2
флаг & 0x40           -> p += 4
флаг & 0x10           -> p += 4
флаг & 0x20           -> дальше список ссылок
```

В списке ссылок обнаружена **проверка границы**, которой раньше не было:

```
v = ((hi & 0x3F) << 8) | lo
если v == 0x3FFF  -> пропустить
если v >= предел  -> ОШИБКА, разбор прерывается
ссылка = 0x40000000 | (номер_блока & 0x0FFF) << 16 | (признаки << 28) | v
```

**Итог.** Перечисление векторов через таблицу и раскладка разбора подтверждены.
Не истолкованы: метка `0x80` (3.6% целей), содержимое полей, которые описатель
пропускает по четыре байта, и сама геометрия. Смысл значений в списке ссылок
проверить не удалось: попадание в диапазон 79.7% при случайных 54.7% — слишком
слабо, и предел для проверки берётся не из таблицы, а из другого поля.

### Почему сканирование блока не работает

Проверено и отвергнуто: цепочка «разобрать вектор → его конец есть начало
следующего» рассыпается на 2–4 векторах в каждом из 40 блоков v3. Причина
видна из статистики: метка `0xC0` встречается у **14.4%** позиций на чётных
смещениях (распределение старших двух битов: `00` — 30%, `01` — 20%, `10` —
35%, `11` — 14%). Как признак начала вектора она слишком слаба, и векторы
подряд не упакованы.

Вывод: перечислять векторы можно только через таблицу (v5) или через ссылки
`VReferenz` из индекса имён (v3/v4). Сканирование не годится — это тупик,
который не стоит повторять.

### Декодер координат `u_get_koord_c` — прочитан из кода

Функция найдена по строке `XAC: Fehler bei u_get_koord_c(%p, %d)`
(`FUN_082727e8`). Алгоритм выписан по дизассемблеру вместе с константами, а не
выведен из данных.

```
w = u16BE(байт0, байт1)

(w & 0xC000) == 0xC000   ->  ошибка «Fehler bei u_get_koord_c»

(w & 0xC000) == 0x8000   ->  расширенная форма
    n = байт1 & 0x0F
    бит 5 байта0 == 0    ->  ШЕСТЬ байт
        x = n * 0x10000        + u16BE(б2,б3) - 524288
        y = ((w >> 4) & 0xF) * 0x10000 + u16BE(б4,б5) - 524288
    бит 5 байта0 == 1    ->  ВОСЕМЬ байт, 28-битные значения
        x = (((n << 8 | б2) << 8 | б3) << 8 | б4) - 134217728
        y = ((((w & 0xF0) << 4 | б5) << 8 | б6) << 8 | б7) - 134217728
    бит 4 байта0 == 1    ->  есть добавочный байт: (v & 0x1F) - 16
                             (диапазон -16…15, похоже на уровень/этаж)

иначе                    ->  КОМПАКТНАЯ форма, четыре байта
    x = (w & 0x7FFF) - 16384
    y = u16BE(б2,б3) - 32768

затем прибавляется опора блока:  X = x + i32BE(блок+0x28),  Y = y + i32BE(блок+0x2c)
```

**Поправка к прежней записи.** У нас было записано:

```
обычная    : dx = u16BE(p) - 0x4000       dy = u16BE(p+2) - 0x8000
расширенная: dx = i16BE(p+2)              dy = i16BE(p+4)
```

Первая строка верна почти полностью — не хватало маски `0x7FFF` для `x`.
А вот расширенная форма описана **неправильно**: это не два знаковых 16-битных
поля, а 20- или 28-битные значения со смещениями −524288 и −134217728, причём
выбор между шестью и восемью байтами делает бит 5 первого байта.

Опора блока по `+0x28`/`+0x2c` подтвердилась — она читается ровно так, как у
нас записано.

**Чего не хватает.** Где именно внутри вектора лежит поле координат — не
установлено. Вызов идёт не с начала вектора: при подстановке начального
смещения все 12 249 целей попадают в ветку ошибки, потому что там стоит метка
`0xC0`, которую декодер отвергает. Проверены поля, пропускаемые разборщиком
имён по четыре байта: при флаге `0x40` координата попадает в рамку блока у
47.2% векторов, при флаге `0x10` — у 15.4%. Ни одно не убеждает.

### Полная модель вектора — из `u_gvi` (`FUN_08272938`)

Функция найдена по строкам `XAC: kein Vektor u_gvi(%p, %d)` и
`XAC: nicht hier u_gvi(%p, %d)`. Это главный разборщик вектора, и он связывает
всё найденное раньше.

**Откуда берётся вектор.** При версии блока ≥ 5 и `u16BE(блок+0x72) == 1`
таблица лежит по `u32BE(блок+0x6c)`, число записей в `u16BE(блок+0x70)`, а
индексом служит `param >> 1`:

```
смещение = u16BE(таблица[param >> 1]) * 2
```

Это ровно та таблица, которую мы подтвердили на данных.

**Раскладка вектора.**

```
слово0 = u16BE(смещение)
    слово0 & 0xC000 == 0xC000  ->  вектор здесь
    слово0 & 0xC000 == 0x0000  ->  «kein Vektor» (ошибка)
    иначе                      ->  «nicht hier», вектор в другом блоке
    ссылка_на_узел = слово0 & 0x3FFF        <- 14 бит

слово1 = u16BE(смещение+2)
    бит 6 старшего байта  ->  следующее слово задаёт ДРУГОЙ БЛОК,
                              разбор продолжается в нём
    бит 3 старшего байта  ->  косвенность: описатель лежит раньше по блоку
    бит 14                ->  есть ещё одно слово
    тип = слово1 & 0x07FF                   <- 11 бит, индекс в ATTRIBUTE

описатель = ATTRIBUTE[тип]        // ЦЕЛИКОМ 32 бита, а не только байт флагов
    старший бит      ->  читается ещё слово и подмешивается в описатель
    бит 15           ->  читается ещё слово

FRC = описатель & 7               <- КЛАСС ДОРОГИ
```

Проверка `if (maxfrc < (описатель & 7)) return 2` — вектор отбрасывается, если
его класс хуже запрошенного. Это и есть тот самый класс, который мы раньше
выводили сопоставлением с OSM: младшие три бита описателя.

**Координаты берутся ДВАЖДЫ и не из вектора.**

```
u_get_koord_c(блок,  смещение_узла_откуда, результат+0x14)
u_get_koord_c(блок2, ссылка_на_узел,       результат+0x20)
```

То есть вектор — это ребро между двумя узлами, и он **ссылается** на их
позиции, а не хранит координаты внутри. Вот почему все попытки найти координаты
внутри вектора давали 47% и 15%: их там нет.

Для «куда» смещение получается так: в том же блоке при отсутствии таблицы это
`ссылка * 2`, а при наличии таблицы — через неё (`FUN_08272410`). Если взведён
бит 6 слова1, блок сначала меняется на другой по его номеру.

**Что это закрывает.** Связка собрана целиком: таблица векторов → вектор →
ссылки на два узла → декодер координат `u_get_koord_c` с тремя формами. Класс
дороги оказался младшими битами описателя, а не отдельным полем.

### Цепочка «вектор → узел → координата» замкнута и проверена

Недостающим звеном оказалась `FUN_08272410` — перевод ссылки на узел в
смещение. Сразу **за** таблицей `u16` в блоке лежит **байтовый массив**:

```
байты = таблица + число_записей*2 + 2
шаг   = байты[ссылка]
```

Разбор:

```
если ссылка == 0 или ссылка >= число_записей  ->  узла нет
пока шаг == 0:  ссылка--,  шаг = байты[ссылка]     // отход назад по группе
смещение = u16BE(таблица[ссылка]) * 2
если шаг == 1:    шаг = u16BE(смещение - 2)        // длинный отход, число перед вектором
если шаг == 255:  узла нет
смещение = смещение - шаг*2                        // ОТСТУП НАЗАД
если (байт[смещение] & 0xC0) == 0xC0:  смещение += 0x16   // попали на заголовок
                                                           // под-блока — пропустить 22 байта
```

Двадцать два байта — ровно тот размер заголовка под-блока v5, который был
найден раньше в `FUN_08270da0`. Всё сошлось само.

**Проверка на данных.** Три плотных тайла, 39 блоков v5, 12 249 векторов с
меткой `0xC0`:

```
ссылок переведено в смещение       11 926   (не перевелось 323 — нулевые и 0xFF)
координата попала в рамку блока    11 926   — 100.0%
```

**Сто процентов.** Ни одного промаха. Для сравнения: прямое толкование ссылки
как смещения давало 20.5%, как индекса таблицы — 7.7%.

Это уже не статистический довод, а точное воспроизведение кода: цепочка
таблица → вектор → ссылка → байтовый массив → отступ назад → пропуск заголовка
→ декодер координат работает ровно так, как в прошивке.

### Межблочные ссылки надо пропускать

Первая выгрузка дала 106 924 ребра, из них 9 254 длиннее пяти километров
(до 28 км) — явный брак. Разделение оказалось идеальным:

| | рёбер | длиннее 5 км |
|---|---|---|
| локальные (бит 6 слова1 снят) | 92 128 | **0  (0.0%)** |
| межблочные (бит 6 взведён) | 14 796 | 9 248 (62.5%) |

Среди локальных рёбер **нет ни одного** неправдоподобного. Весь брак — это

распределились бы поровну, а не собрались целиком в одной, заранее опознанной
по коду категории.

### Расхождение, которое надо разрешить

Записано, что обратная ссылка — это `0x4000 | (q/2)`, то есть значение должно
разрешаться в номер узла. На корпусе из 18 721 слова `0x4xxx` разрешается
**0.5%** — фактически никогда. Либо формула иная, либо эти ссылки указывают за
пределы блока. Прежнее утверждение опиралось на 192 слова ватиканской выборки и
требует перепроверки.

### Модуль чтения XAC: что найдено и где тупики

Строки разделов XAC лежат в `MMI3GApplication` (в `ndr` их нет вовсе), модуль чтения —
район `0x8cf0000…0x8d10000`. Терминология из кода: **FE = Fahrbahnelement**, дорожный
элемент, и на этом уровне он равен **одному `VEKTORBLOCK`**, а не одной записи.

Прослеженная цепочка:

1. `FUN_08cf473e` — **сканер разделов**: обходит разделы шагом `размер + 0x14`, узнаёт
   `SMART XAC HEADER` (номер блока — `u16` по смещению +2), `VEKTORBLOCK` (или
   `LAYER 1 VERWEISE`, если `*(this+0x20) == 0xe`) и `ZF-NAMEN`, заполняя две таблицы
   пар `{номер блока, адрес}` по `*(this+0x34)`; счётчики — `this+0x2c/0x2e/0x30`.
2. `FUN_08cf4a54` — **`XacDataBlock::getComponent(subType, feNum)`**: поиск
   интерполяцией по этим парам, возвращает адрес раздела.
3. Три его вызова (`FUN_08235194`, `FUN_0823538c`, `FUN_082355e8`) — слой загрузки NDL
   (`ndl_load_error_2_l1v/zfn`), разбора записей там нет.

Полезные строки проверок сборки (`FUN_0828223c`): `checkKlotoiden` (клотоиды),
`checkSpurinfos` (полосы), `checkVignette`, `checkScenic`, `checkNID_FE_Bits`,
`check16BitVBlocknr`, `checkVBIndexVersion`, `checkCharacterSet`.

> **Снято.** Тупик обойдён: библиотека найдена не по маскам, а по путям к исходникам
> (`NavCore\xaclib\private\xac_vect.cpp` и соседние) — см. «Библиотека `xaclib`».
> Маскирование сдвигами подтвердилось: значение ссылки собирается как
> `((hi & 0x3f) << 8) | lo`, константы `0x3FFF` в коде действительно нет.

**Тупики — чтобы не повторять.** В коде **ноль** пул-констант `0x3FFF`: SH4 маскирует
сдвигами, а не константой из пула, поэтому искать разборщик записей по характерным
маскам `0xC000`/`0x3FFF` бесполезно. Идти от вызовов `getComponent` тоже некуда — они
упираются в загрузчик. Следующая мысль: искать **потребителя** загруженного блока
(маршрутный/отрисовочный движок), а не цепочку загрузки.

Названия улиц лежат в `ZE-NAMEN` (в ватиканском тайле читаются `VATICANO`, `PIAZZA`,
`VIA SANT…`, `PELLEGRINO`, `OSSERVATORE`), но в сжатом чересстрочном подформате,
который тоже не разобран.

### Версия 5

Под-блоки размечаются рамками так же, как в v4. Координаты кодируются **теми же
биасами, что в v3 и v4, и тоже от опорной точки блока**:

```
x = origin_x + u16BE(p)   - 0x4000
y = origin_y + u16BE(p+2) - 0x8000
```

То есть кодирование координат едино для всех трёх версий; отличается только
разметка. Механизма самоиндекса в v5 нет (2 подходящих слова из 119), и записи
не фиксированной длины — перебор длин 4…16 даёт максимум 44,8%. Поэтому границы
записей не восстанавливаются, а координаты выбираются сканированием с проверкой
по рамке под-блока: рамка занимает считаные километры, вероятность случайного
попадания пары в неё порядка 1e-4 на позицию, ложных срабатываний практически
не бывает. Достижимость проверена: 147/148, 165/165 и 190/190 под-блоков лежат
в пределах 16-битной дельты от опоры блока.

Следствие: из v5 извлекаются точки, но не топология — связи `0xCxxx` без разметки
записей не привязать. Рёбра в выгрузке дают только блоки v3 и v4.

Заблуждение, которого стоит избегать: диапазон дельты нужно считать не против
границ блока, а против фактического размещения данных. Границы блока Мальты шире
достижимого диапазона, из-за чего v5 сперва была ошибочно признана
недекодируемой.

## GDB и GDB2 — устройство

`EJ211_v37a.gdb` (2,0 ГБ) и `EJ211_v37a.gd2` (1,4 ГБ) — **один логический файл**:
смещения внутри индекса 40-битные и сквозные, `.gd2` начинается там, где
кончается `.gdb` (адрес `0x7FFE4EFC` = размер `.gdb` + 1691). Австралийский
`DJ011_v36a.gdb` устроен так же, только без второго тома. Это не FLDB.

### Шапка

| Смещение | Значение |
|---|---|
| 0x00 | сигнатура `DEADBEEF` |
| 0x04 | версия формата: 37 у `_v37a`, 36 у австралийского `_v36a` |
| 0x14…0x24 | четыре i32: −8978432, −196608, 16850000, 11517028 — по x это ровно 360° (от 124,7° з.д.); смысл не установлен |
| 0x24 | число уровней: 12 у Европы, 8 у Австралии |
| 0x2D | таблица уровней: 12 пар `(смещение, размер)` |

### Big-endian и инструмент `src/gdb.js`

Ключ, без которого раздел не читался: GDB, как и XAC, **big-endian**. Сигнатура
`DEADBEEF`, версия `0x25`=37, а рамка на `0x14..0x20` даёт числа выше
(`−8978432, −196608, 16850000, 11517028`) только при BE-чтении; число уровней —
`u8` в `0x24`. `src/gdb.js` разбирает шапку и таблицу уровней и печатает их —
все 12 уровней сходятся с таблицей ниже байт в байт, это подтверждает раскладку
шапки на живом файле.

Каталог блоков и пространственный индекс — **ещё не переопределены**: смещение
`0x13F68E02` и «44 747 пар» из первого взгляда в этом файле (`_v37a`) не
воспроизводятся, сразу за таблицей уровней (кончается на `0x8D`) идут нули до
`~0x128`. Их предстоит вывести заново; `gdb.js` печатает их только по флагу
`--catalog`/`--index` и честно помечает как непроверенные.

Карта для разбора — из самого `MMI3GApplication` (импортирован в Ghidra):
структуры названы в отладочных строках — `CGdbLevel::kachel_zu_element_offset`
(тайл по смещению), `CGdbRefTableMainDirectory`/`CGdbRefTable` (таблицы ссылок),
`CGdbBlobDirectory`/`getBlob`, `CGdbCluster` (`kachel_header_zu_id`),
`CGdbTileElementBag`/`getElementInPaintOrder` (элементы тайла в порядке
отрисовки). Есть и отладочная команда «Dump static GDB tile contents». По этим
именам и пойдёт разбор содержимого.

### Что уже прочитано из кода `MMI3GApplication`

Ghidra на SH4 не превращает загрузки из пулов литералов в ссылки, поэтому
функции ищутся вручную: адрес строки → слово-указатель на неё → `mov.l`,
читающий это слово (не дальше 1020 байт до пула) → первый пуш пролога
`mov.l rN,@-r15` до него → `createFunction` и декомпиляция.

**Таблица assert'ов** (`0x981ed40…`): тройки `{строка, файл, имя метода}` —
готовая карта `CGdbCluster.cpp` с номерами строк: `kachel_header_zu_index`
(120/126), `create_header` (141), `init_nach_laden` (318),
`such_tabellen_eintrag` (444–484, поисковая таблица), `setze_such_tabellen_eintrag`
(501–536), `kachel_zu_index` (692), `loadObject` (736),
`berechne_kachel_bereich` (857–873), `berechne_kachel_indizes` (890–904).
Рядом — семь указателей на методы `CGdbBlobDirectory`.

**Blob Directory** (из декомпиляции `getBlob`/деструкторов): в памяти таблица
записей по **40 байт** (`obj+0x24` → таблица, `obj+0x28` → `m_numberOfBlobs`);
`getBlob(blobnr)` берёт `entry = table + blobnr*40` и читает файл как
`read(entry[0], 0, entry[1])` — **`entry[0]` = смещение, `entry[1]` = размер**
блоба. Assert'ы: `m_blobTableHeaderSize <= 640` (16 записей × 40), `blob
exceeds size of 64k` (блоб ≤ 64 КБ), `blobnr < m_numberOfBlobs`.

**Инварианты из assert'ов:** `(erg >= 0) && (erg < m_anz_kacheln)` — счётчик
тайлов кластера; `UInt16 CGdbRefTable::getOffsetOfLevelData(ebene)` — у RefTable
смещения данных по уровням хранятся как u16; `blocknr < m_numberOfRefTables`,
`blockIndex < m_numberOfLitBlocks`; на верхнем уровне `CGdb::kachel_zu_position`,
`kachel_id_zu_position`, `cluster_zu_kachel_id` — у тайла есть id и позиция,
кластер отображается в id тайлов. Помощник `FUN_08caef1c` считает размер как
`1 << (a + b + уровень)` по `u16` из заголовка — степени двойки в раскладке.

**Отброшено на данных L0** (плотный регион 431 КБ после шапки уровня):
это не поток 19-байтовых записей, не плоская таблица смещений, не пары
`(смещение, размер)` и не CIFF-блоки. Слепой перебор структур закончен —
дальше только по коду.

### Модель GDB из декомпиляции: уровень → сетка кластеров → тайлы (проверено на данных)

Из функций `CGdbCluster::init_nach_laden` (`FUN_08caf3c4`), `setze_such_tabellen_eintrag`
(`FUN_08caf140`), `CGdbLevel::loadObject` (`FUN_08cae6cc`), `CGdbTile::CGdbTile`
(`FUN_08cabdb8`) в `MMI3GApplication` (код — в проекте Ghidra `/tmp/ghp`). Реализовано
и проверено на данных в [`src/gdb.js`](src/gdb.js) — `node src/gdb.js maps`.

* **Уровень**: `+0 u32 cellX`, `+4 u32 cellY` — размер ячейки в мировых единицах;
  `+8 u8 pot_x`, `+9 u8 pot_y` — log2 числа ячеек в кластере (у L0 = 7 → 128×128).
  За областью рамки — **таблица кластеров** до конца уровня: массив **6-байтных
  записей `{u32 смещение, u16 размер}`**, ровно `W*H` штук.
* **Сетка кластеров** L0 — регулярная, `W=256 × H=280` (= 71 680 слотов). Кластер
  ячейки `(x,y)` лежит в слоте **`slot = (y >> pot_y)*W + (x >> pot_x)`** — проверено
  1500/1500 реальных кластеров L0. Смещение `0`/`16` — слот без данных; ~13 580
  «морских» слотов ссылаются на **один общий пустой тайл** (у нашего набора @334 925 620).
* **Кластер**: таблица тайлов из **19-байтных записей** (при версии ≥ 0x23, у нас 37):
  `u32 ключ` (`x = ключ & 0xFFFF`, `y = ключ >> 16`; старшие биты — подтайл), байты
  `lw@5`/`lh@7` (log2 размера тайла в ячейках), флаги `@8..10`, `u32 смещение данных @11`,
  `u32 размер данных @15`. За таблицей тайлов — **поисковая таблица** `2^(pot_x+pot_y)`
  элементов (u8/u16/u32 по числу тайлов) с индексом тайла для каждой ячейки; ширину
  задаёт `i16` в кластере (`0→u8, 1→u16, 2→u32`), значение `< m_anz_kacheln`.
* **Blob Directory** (`FUN_08cb0964`): на диске записи по **32 байта** (8×u32), в
  памяти 40; `entry[0]` — смещение, `entry[1]` — размер блоба; ≤ 16 записей, блоб ≤ 64 КБ.

Это исправляет «первый взгляд»: поток «19-байтных записей с 0x13F68E02» — не глобальный
индекс, а **таблицы тайлов кластеров** в области данных `.gd2` (19 байт — верный размер
записи, но лежат они по кластерам, а не сплошным индексом). «Каталог блоков на 44 747
пар» и «пространственный индекс с 0x13F68E02» из ранних заметок — это неверная привязка
того же участка; настоящий индекс — сеточные таблицы кластеров каждого уровня.

**Грубые уровни L1…L11** — таблицы находятся (`node src/gdb.js maps` печатает начало и
размер), но правило `slot = cy*W+cx` на них не сходится: похоже, они обрезаны по рамке
данных (иное начало отсчёта). Разбор их порядка — в работе.

### Привязка координат: клетка ↔ широта/долгота (решено по якорям)

Кипр, которого нет в покрытии, **всё же нарисован** — его берег лежит реальными
L0-тайлами, и рядом с геометрией стоит код страны `\x03CYP`. Тем же приёмом ищутся
метки других стран за краем покрытия (`MAR`, `DZA`, `TUN`, `LBY`, `EGY`, `TUR`, `SYR`).
Сопоставив смещения этих меток с тайлами и их клетками, получаем привязку:

| Страна | долгота | столбец кластера |
|---|---|---|
| MAR | −6° | 84 |
| DZA | 3° | 90 |
| TUN | 10° | 95 |
| LBY | 18° | 101 |
| EGY | 30° | 110 |
| CYP | 33,4° | 112 |
| TUR | 35° | 113 |
| SYR | 38° | 116 |

Наклон сквозной, отклонений нет — сетка **линейна по широте и долготе**
(равнопромежуточная, не Меркатор):

```
столбец кластера ≈ 88,0 + 0,727 · долгота      клетка_X ≈ 11264 + 93,1 · долгота
строка   кластера ≈  7,3 + 1,42  · широта      клетка_Y ≈   934 + 181,8 · широта
```

Кластер — 128×128 клеток, `slot = строка·256 + столбец`. Точность — **±1…2 кластера**
(метки стран стоят не в центроидах, а где карта их рисует), чего хватает, чтобы найти
нужный кластер, но не отдельный тайл. Проверка: Кипр (33,4°E; 35,1°N) → кластер
(112; 57) — ровно там, где лежат найденные тайлы берега. Ватикан (12,45°E; 41,9°N) →
кластер ≈ (97; 67).

Важное следствие для задачи: **клетки Кипра в GDB не пустые** — там есть тайлы с
береговой линией, уже учтённые в сетке кластеров и пространственном индексе. Значит
дороги нужно не «создавать тайл на пустом месте», а дописывать геометрию к уже
существующим и известным индексу тайлам.

### Единицы координат (частично)

Рамка шапки `@0x14` = `[-8 978 432, -196 608, 16 850 000, 11 517 028]`. Ширина по X
`16 850 000 − (−8 978 432) = 25 828 432` совпадает с `32768 ячеек × cellX 789 = 25 853 952`
с точностью 0,1 % — то есть **X-рамка = вся сетка L0**. Отношение `cellX/cellY = 789/546
= 1,445 = 1/cos(46°)** — ровно поправка на широту для квадратных на местности ячеек
лат/лон-сетки, центрированной на ~46° с.ш. (центр Европы). Это говорит, что ключи `x,y`
— **линейные лат/лон-ячейки**, но абсолютная привязка (какая ячейка = Ватикан/Кипр) ещё
не выверена по известной точке — следующий шаг перед любой записью в GDB.

### Растр занятости

За таблицей уровней — каталог из двух записей по 32 байта. Первая — растр
`19022002`, с той же рамкой и километровой сеткой 15212 × 6280, что у общего
`.ras`: таблица смещений по строкам (`u16`, в словах от начала блока), в строке
чередуются длины пустых и заполненных пробегов. Заполнено 38 460 812 ячеек
против 38 462 132 занятых в `.ras` — это та же карта покрытия. Вторая запись —
37 КБ шума, назначение не установлено.

### Что адресуют тайлы

Тот же поток «19-байтных записей» — это таблицы тайлов кластеров (см. модель
выше). Тайл пустой ячейки указывает на один общий блок в 40 байт; реальные тайлы
— на блоки в области данных `.gd2`. Метки-подсказки для будущей координатной
привязки: записи с подписью `CYP` лежат у ключа `(x=0x3880, y=0x1C80)`, с
подписями `MAR DZA MRT` — у `(x=0x27E0, y=0x16E0)`. Это метки соседних стран,
которые карта рисует за краем покрытия, а не центры стран — сверять по ним
абсолютную привязку надо осторожно.

**Сгенерировать блоки GDB сегодня нельзя**: сама структура (уровень → сетка
кластеров → тайлы) разобрана и читается `src/gdb.js`, но формат *содержимого*
блока тайла (`CGdbTileContent`/`CGdbTileElementBag` — геометрия дорог) разобран
лишь начерно (ниже) и требует ещё нескольких сессий.

### Формат содержимого тайла (первый разбор)

Данные тайла (блоб `@смещение`, `размер` из записи тайла) начинаются с заголовка,
который читает конструктор `CGdbTile` (`FUN_08cabdb8`): четыре `u32` BE, из них
`hdr[3] = m_size_daten < 0xFFFF`. В памяти тайл держит смещения частей относительно
`base+0x1c`: индекс (`+0x1e` его размер), поток элементов, вторичный поток точек
(`+0x26`), таблица строк. Пустой «морской» тайл — 40 байт, только заголовок.

Геометрию раскодирует **`CGdbTileElementIterator::next` (`FUN_08cb3f90`)** —
потоковый декодер с дельта-кодированием. Каждый элемент предваряют **управляющие
байты `≥ 0x80`** (константы подтверждены: `C1 = 0xC0`, `C2 = 0xE0`):

* `0xC0…0xCF` — слой/уровень: `layer = байт & 0x0F`;
* `0xE0…0xE3` — метаданные: `0xE0/0xE1/0xE2` кладут следующий байт в поля `+9/+10/+11`
  элемента, `0xE3` — `u16` в поле `+3`;
* `0xA0…0xBF` — дельта аккумулятора `param[5]` (id имени/строки): `& 0x1F` == 0 →
  читать полное значение, `< 0x10` → `+=`, иначе `+= (−0x20)`.

Первый байт `< 0x80` — **головной байт элемента**; тип элемента (0/1/2 =
точка/линия/полигон, `getType` возвращает `& 0x3F`) берётся из отдельного текущего
байта. Биты головного байта: `биты 0–1` — режим дельты X (0 повтор, 1 константа,
2 `+ i16`, 3 полное), `биты 2–3` — режим дельты Y (аналогично, с обращением во
вторичный поток точек через `base+0x1c+idx+0x26`), `биты 4–6` — число точек
(при `==1` читается байтом, `0xFF` → расширенное; assert «Polygon with 0 points»).
Дальше идёт поток точек (`FUN_08cb4518`) и bounding-box (4×`i32`, поля `+0x28…`),
после чего указатель сдвигается на `*(base+0x3a)`.

`CGdbTileElementBag::fillWith` (`FUN_08cab654`) прогоняет `next` по всем элементам
и раскладывает их по массивам порядка отрисовки и порядка имён (switch по типу 0/1/2,
плюс диапазон `0x43…0x4A` — особый класс). Строки — отдельная таблица
(`createStringTable`, `get_string`, `uncompressString`), индекс строки `+0x88`,
данные `+0x84`.

**Точки элемента — прочитаны и проверены географией.** На береговой линии Кипра
формат вскрыт и сошёлся побайтно на трёх тайлах. В конце потока элементов лежит узор

```
1d  <u32 Y>  <u8 N>  8f 00 00 00 00   затем ровно N × u32
```

`0x1d` — это головной байт по модели выше: `&3 = 1` (X — константа), `&0xC = 0xC`
(Y — читать `u32`, здесь 0x50), поле счётчика `(b>>4)&7 = 1` → **счётчик точек берётся
следующим байтом**. Каждый `u32` — одна точка: старшие 16 бит — `x` (беззнаковый),
младшие — `y` (**знаковый** `i16`), в мировых единицах **от начала тайла**.

Проверка (`node src/gdb.js maps --tile 346900808:178 --cell 14336,7392`): длина данных
совпала точно (16, 36 и 12 точек в трёх тайлах), а переведённые в градусы точки легли
на северное побережье Кипра и состыковались между собой:

| тайл | долгота | широта |
|---|---|---|
| (14304,7424) | 32,653…33,340 | 35,380…35,742 |
| (14336,7392) | 32,997…33,684 | 35,252…35,566 |
| (14368,7392) | 33,340…34,028 | 35,218…35,794 |

Реальный Кипр — 32,27…34,60° в. д., 34,56…35,70° с. ш. Все точки внутри. Реализовано
как `tilePoints()` в [`src/gdb.js`](src/gdb.js).

**Что ещё не декодируется:** это лишь один вариант элемента (последний в тайле).
Прочие режимы головного байта и предшествующие элементы потока (там иная, более узкая
бит-упаковка) пока не разобраны. Перебор гипотез фиксированной ширины для них отсеян
строгой проверкой: у настоящей ломаной отношение «медианный шаг / диагональ рамки»
равно 0,064, а лучший кандидат перебора даёт 0,252 — вчетверо хуже, то есть там
действительно дельты с переменной шириной.

**Для задачи это и не нужно.** Чтобы рисовать свои дороги, достаточно **писать** один
понятный вариант, а не читать все. Узкая упаковка — оптимизация размера компилятора
HERE; наши тайлы просто будут чуть крупнее.

### Запись геометрии: round-trip доказан

`encodePoints()` — обратная операция к `tilePoints()`. Проверка не подгонкой под
кипрские тайлы, а сплошняком по карте:

```
кипрские тайлы A/B/C      ✓ идентично (16, 36, 12 точек)
60 000 тайлов L0:  узор распознан в 809 → round-trip идентичен в 809 (100,00 %)
                   прочие варианты 59 191 (узкая упаковка)
```

То есть мы умеем производить байты геометрии GDB, неотличимые от выданных штатным
компилятором карт. Это первая возможность **записи** в проекте.

### Подмена геометрии в тайле — сделано

[`src/gdbwrite.js`](src/gdbwrite.js) правит ломаную внутри тайла. Приём, снимающий
почти весь риск: **сохранить число точек** — тогда длина элемента не меняется и правка
идёт строго на месте, не трогая ни заголовок тайла, ни таблицу кластеров, ни смещения
томов. Координаты задаются в градусах и переводятся по калибровке выше.

```
node src/gdbwrite.js maps --tile 346900808:178 --cell 14336,7392 \
     --road "33.05,35.30 33.088,35.316 … 33.62,35.54" \
     --apply out/gdbtest/pkgdb/GDB/EJ211_v37a.gdb
```

Проверено сквозным циклом на клоне тома (на APFS `cp -c` копирует 2 ГБ мгновенно):
берег Кипра в тайле заменён прямой «дорогой», изменено ровно 64 байта из 75
(16 точек × 4), и **обычный ридер читает из изменённой карты именно наши координаты**.
Структура цела: `DEADBEEF`, 12 уровней, сетка L0 256×280, формула слотов 1500/1500,
заголовок тайла валиден, round-trip проходит.

Оригинальный `maps/` при этом не трогается никогда — инструмент пишет только в файл,
явно указанный в `--apply`.

### Наращивание тайла — снято ограничение по числу точек

Правка на месте ограничена длиной уже лежащей ломаной. Чтобы положить больше точек,
тайл **не раздвигается**: запись тайла в кластере — это указатель
(`u32 смещение @11`, `u32 размер @15`), поэтому новый блоб дописывается **в конец
`.gd2`**, а в кластере правятся только эти 8 байт. Ни одно другое смещение не двигается.

```
node src/gdbwrite.js maps --tile 346900808:178 --cell 14336,7392 --road "…" \
     --grow out/gdbtest/pkgdb/GDB2/EJ211_v37a.gd2 \
     --gdb  out/gdbtest/pkgdb/GDB/EJ211_v37a.gdb
```

Новый блоб = заголовок + [старый поток элементов + наш элемент] + хвостовые секции;
счётчик элементов растёт на единицу, три `u16`-смещения пересчитываются (предел —
65 535 байт на блоб). Проверено: 178 → 589 байт, элементов 2 → 3, тайл уехал в `.gd2`,
и ридер достаёт оттуда все 100 наших точек, структура тома цела.

> **Поправка.** Этого мало для отрисовки. Хвостовые секции здесь копировались без
> изменений, а элемент рисуется, только если на него есть запись в S1 — см.
> «Реестр элементов». Написанное выше верно про геометрию и про наш ридер, но
> на экране такой элемент не появлялся. Исправлено в `gdbroads.js`.

После наращивания **меняется размер `.gd2`**, поэтому в `GDB2.conf` нужно обновить
`size=`, `MD5` и пробы `check=qa` (механика пересчёта уже есть в `relocate.js`).

### Реестр элементов: S1 и S2 — почему геометрии мало

Элемент рисуется, только если на него есть запись в хвостовой секции **S1**.
Одной геометрии недостаточно: дописанные элементы отрисовщик не видит.

Правило проверено на **4000 тайлов L0 без единого исключения**:

```
счётчик в начале S1  ==  число элементов в заголовке − 1
```

Минус один — потому что первый элемент тайла служебный (одна и та же рамка
`4d 00 00 00 50 8f 00 00 00 00 …` встречается и в пустом тайле, и в городском),
записи он не имеет.

**Раскладка секций.**

```
S1: u16 счётчик, 0x02, u16 ноль, затем записи из полей с тегами
      16 <u32> <u16>   идентификатор и порядковый номер
      21 <u8>          необязательное поле
      32 <u16>         номер строки в S2, отсчёт ОТ НУЛЯ
      f0               конец записи
S2: u16 счётчик, u16 ноль, затем строки: байт длины, затем байты
      значащие — младшие 4 бита длины (все встреченные длины ≤ 15),
      старшие биты помечают продолжение имени
S3: необязательна; у кипрских и пустых тайлов её нет вовсе
```

Арифметика сходится точно: у кипрского тайла S1 = 5 байт заголовка + 13 байт
записи = 18; у римского 5 + 72 = 77.

**Формы записей** (15 082 записи из 3010 тайлов, разбор сошёлся точно на границе
секции у 2966 из них):

| форма | доля |
|---|---|
| `32` | 37.2% |
| `16 + idx + 32` | 36.9% |
| `16 + idx + 21 + 32` | 23.3% |

То есть **минимальная запись — `32 <u16> f0`, четыре байта**, и поле `32` есть
всегда. Что оно индексирует именно строки S2 и отсчёт идёт от нуля, проверено
на 1207 тайлах: сошлось у 1197, у 7 похоже на отсчёт от единицы, 3 не разобраны.
Тайлов, где записи S1 есть, а строк в S2 нет, не встретилось ни одного.

Содержимое S2 подтверждает смысл: у кипрских тайлов там `CYP`, у римского
прибрежного — названия паромных линий (`NAPOLI-CAGLIARI`, `PALERMO-GENOVA`,
`LIVORNO-TRAPANI`).

**Что делает `gdbroads.js`.** На каждую дорогу дописывает запись в S1 и заводит
имя в S2 (берётся `ref` или `name` из OSM, иначе `CY`), пересчитывает оба
счётчика и три смещения заголовка. Собранный тайл выходит структурно
неотличимым от настоящего: у пустого кипрского тайла S2 получается байт в байт
таким же, как у соседних непустых — `00 01 00 00 03 "CYP"`.

### Кипр в L0: что там было до нас

Остров покрывают 4 кластера, 64 тайла, и **данные были только в трёх** (максимум
354 байта). Зелёный остров с рельефом и берегом, который видно на экране,
рисуется не из GDB, а из `TER`/`CTY`. Дорожного слоя у Кипра нет вовсе — это и
есть исходная беда проекта.

### Укладка дорожной сети в GDB — и путь к согласованности с XAC

Ключевое наблюдение, снявшее тупик: **`relocate.js` никогда не писал записи XAC**.
Он правит только абсолютные координаты обвязки — рамку тайла, **опору блока**
(`VEKTORBLOCK +40/+44`), `LOCAL POIS`, рамки уровней, `NACHBARN`, растр и суммы.
Координаты узлов хранятся *дельтами от опоры*, поэтому сдвиг опоры переносит все
узлы разом, а сами записи остаются байт в байт. Отсюда точная формулировка:

* **двигать существующие дороги XAC — умеем** (семь сборок ставились на машину);
* **создавать новые записи XAC — нет**, для этого нужен смысл атрибутных слов.

А раз мы теперь умеем писать геометрию GDB, связка складывается уже из готового:
`relocate.js` двигает XAC Ватикан→Кипр, а мы кладём **те же самые связи** в GDB на
те же координаты.

> **Поправка, важная.** Здесь стояло: «оба контейнера согласованно говорят "дороги
> на Кипре" — исчезает ровно то рассогласование, из-за которого висит 28 %». Это
> **неверно**. Зависание на 28 % вызывал пропадающий `acios_db.ini`, а не
> рассогласование XAC и GDB: сборка с оригинальным XAC и одним лишь изменённым GDB
> висела точно так же. Согласованность контейнеров нужна для осмысленной карты,
> но к зависанию отношения не имеет.

[`src/gdbroads.js`](src/gdbroads.js) кладёт набор ломаных в тайлы. В отличие от
`gdbwrite.js`, который пишет одну ломаную, дорожная сеть — это много отдельных
отрезков, и склеивать их нельзя: получился бы зигзаг через несвязанные улицы.
Поэтому каждая дорога пишется своим элементом, а счётчик элементов растёт на их число.

```
node src/gdbroads.js maps --roads va01.geojson --shift 20.90482,-6.73359 \
     --gdb <копия .gdb> --gd2 <копия .gd2>
```

Проверено сквозным циклом на клоне: 168 связей ватиканского графа (из `src/nodes.js`)
разложились по двум тайлам и записались:

```
тайл (14368,7296): 102 дороги, блоб   40 → 1978 б, элементов 1 → 103
тайл (14368,7328):  66 дорог,  блоб   40 → 1294 б, элементов 1 →  67
обратное чтение: 102 и 66 ломаных, 204 и 132 точки
география: lon 33,357…33,363  lat 35,167…35,173 — район Никосии ✓

Оба тайла раньше ссылались на **общий пустой тайл**; `--grow`-подход это учитывает:
новый блоб дописывается в конец `.gd2`, правятся только 8 байт записи тайла, а общий
пустой тайл остаётся нетронутым для остальных морских клеток.

> **Поправка.** Эта проверка подтверждала только запись и обратное чтение. На машине
> дороги не появились: записи в S1 не добавлялись, и отрисовщик их не видел. Причина
> найдена позже — см. «Реестр элементов»; `gdbroads.js` теперь ведёт S1 и S2.

### Урезанный том «только Кипр» — для быстрых проверок

Полный набор — 3,6 ГБ на два тома, и каждый цикл проверки на машине упирается в
копирование. Структура позволяет это обойти: большинство клеток и так ссылаются на
**один общий пустой кластер**, а таблица кластеров лежит в области уровней (751 КБ)
и переписывается целиком. [`src/gdbstrip.js`](src/gdbstrip.js) собирает том, где
реальные данные оставлены только вокруг заданной точки:

```
node src/gdbstrip.js maps --out out/cyprus-only --around 33.36,35.17 --radius 3
```

Состав: область уровней как есть → общий пустой кластер → общий пустой тайл →
сохраняемые кластеры и их тайлы; затем вся таблица кластеров переписывается на новые
смещения, а несохраняемые записи — на общий пустой кластер. `.gd2` становится нулевой
длины (сквозных ссылок за границу не остаётся).

Результат и проверка:

```

L0: сохранено 49 кластеров, перенесено 789 тайлов; L1…L11 пусты
DEADBEEF, версия 37, 12 уровней              ✓
сетка 256×280, формула слотов 49/49          ✓

```

Грубые уровни L1…L11 пока обнуляются целиком: там правило `slot = cy·W+cx` не сходится,
и выбрать «кипрские» кластеры нечем — карта будет рисоваться только на мелком масштабе.

**Чего это ещё не решает.** Примет ли движок такую разреженную базу — вопрос
открытый, и урезать разумно оба контейнера согласованно.

> **Поправка.** Здесь стояло, что рассогласование XAC↔GDB и есть причина зависания
> на 28 %. Это неверно: причина — пропадающий `acios_db.ini`. Рассогласование
> контейнеров даёт бессмысленную карту, но не зависание.

### Сколько дорог Кипра и куда они лягут

Выгрузка OSM (Overpass, магистрали + трассы + главные дороги в рамке острова) —
7172 дороги, 51 329 точек, `lon 32,41…34,38`, `lat 34,65…35,60`. Раскладка по сетке:

* затронуто **24 тайла — и все они уже есть в карте**, создавать тайлы с нуля не нужно;
* точек на тайл: медиана 1250, максимум 5332 — правки на месте (12…36 точек) не хватает,
  отсюда и понадобилось наращивание;
* только магистрали (A1/A2/A6): 5818 точек на 10 тайлов, после упрощения ~2220.

**Второй проход (суб-читатели, подтверждено).** Все чтения потока — big-endian и
работают над курсором `{char* ptr; int remaining}`: `FUN_080b615c` = `u32` BE (+4),
`FUN_080b611c` = `u16` BE (+2), `FUN_080b625e` = seek. Инициализация итератора
(`FUN_08cb3e70`): начало потока элементов = `tile+0x1c + u16(tile+0x1e) + u16(tile+0x20)`;
число элементов — `u16` BE (`FUN_08cb3f24`). Читатель точек `FUN_092526f0`:
координаты **бит-упакованы**, ширина на компоненту `∈ {8,12,16,24,32} бит`
(assert «Illegal tile coordinate width»), длина массива = `(N·width + 7) >> 3` байт;
головной байт задаёт режим стартовой координаты (повтор / константа / `+i16` / полное),
ширина — биты на дельту.

**Заголовок блоба тайла — вскрыт, проверено на 20 001/20 001 тайлов L0** (читается
`node src/gdb.js maps --tile <смещение>:<размер>`). Блоб начинается с 16-байтного
заголовка (все поля big-endian):

```
+0  u16 off0     +2  u16 off1     +4  u16 off2 (≈ размер тайла)
+6  u16 счётчик  +8  u16 0xE028 (константа-магия)   +14 u16 m_size_daten
```

`off0 ≤ off1 ≤ off2 ≤ размер` — это границы **хвостовых секций**: поток элементов
занимает `[16 … off0)`, дальше S1 `[off0…off1)`, S2 `[off1…off2)`, S3 `[off2…размер)`
— индекс / порядок отрисовки / порядок имён / строки. Магия `0xE028` в `+8` — у всех
20 001 тайлов, это надёжная сигнатура тайла.

Раннее «`hdr[0..1]` высокоэнтропийны → возможно сжатие» оказалось миражом: `0xE076` —
это просто `off0 = 57462` в 59 816-байтном тайле, не случайные байты. **Тайл НЕ сжат**:
`next()` читает поток элементов напрямую BE-курсором, без распаковщика; заголовок
самоописывающий через таблицу смещений. Сжатие (`uncompressString`) относится только к
таблице строк (названия улиц). **Осталось до записи**: единицы координат в бит-упакованном
потоке точек (суб-ячейки относительно клетки тайла).

### Что внутри блоков

В блоках читаются подписи: названия улиц (`CALLE GENERAL SERRADOR` на Канарах),
паромные линии (`BREVIK-IMMINGHAM`, `GOTEBORG-ZEEBRUGGE`) и трёхбуквенные коды
стран с байтом длины впереди. Коды принадлежат странам **вне покрытия**: `DZA`
2514 раз, `TUR` 1664, `LBY` 1576, `MAR` 872, а покрытых почти нет — `MLT`,
`AND`, `SMR` не встречаются ни разу. Это контуры соседних стран, которые карта
рисует за краем покрытия с подписью. **`CYP` встречается 46 раз**: Кипр на
карте нарисован — как чужая страна без дорог.

### Следствие для Кипра

Если GDB рисует карту, а XAC считает маршрут, то перенесённый в XAC тайл даст
ведение по маршруту без нарисованных дорог, а заполненный GDB — нарисованные
дороги без маршрута.

Вторая половина с тех пор сделана: в GDB пишутся ломаные вместе с записями
реестра, и в L0 уложена дорожная сеть Кипра из OSM целиком (7175 линий, 23
тайла). Первая половина — генерация записей XAC — упирается в неразобранные
атрибутные слова, см. «Анатомия записи».

## TMC

Реестр таблиц локаций лежит в `EJ211_global.tlt`: метка `TMC-LOC-TABLE OV`,
u16 BE число записей по 0x1A, записи по 36 байт с 0x20.

| Смещение | Значение |
|---|---|
| +0x04 | ISO-код страны, 2 байта |
| +0x06 | u8 ECC, расширенный код страны RDS |
| +0x07 | u8 код страны RDS |
| +0x08 | u8 LTN, номер таблицы локаций |
| +0x1C | код языка, 2 байта |

Имена файлов таблиц: `<ПРЕФИКС>_<код RDS>_<LTN>.tlt`. В европейском наборе
27 таблиц на 22 страны, у России шесть.

## Покрытие

Европейский набор: 46 кодов стран с дорожными данными при 216 записях в реестре
`COUNTRY`, и 45 справочников названий `.ort`. Расхождение между 46 и 45
объясняется Черногорией (`M1`) — дорожные данные есть, а её топонимы лежат в
файле Сербии, наследие единого государства; в файле Сербии находятся Улцинь и
Тиват.

Кипра в данных нет: ни тайлов, ни городов, ни справочника. Поиск по всем 22 ГБ
не дал ни одного настоящего совпадения — LIMASSOL, LEMESOS, LARNAKA, PAPHOS,
KYRENIA отсутствуют. То, что находится, посторонее: LEFKOSIA и AMMOCHOSTOS —
улицы материковой Греции, названные в честь кипрских городов; NICOSIA — городок
на Сицилии; единственный LIMASSOL — бар в Ростове-на-Дону из базы точек интереса.

При этом сам Кипр зарегистрирован в реестре `COUNTRY` под кодом `CY`, а строка
CYPRUS есть в словаре `STRING`. Ни то ни другое покрытия не означает: реестр и
словарь всемирные и одинаковы во всех региональных наборах.

## Референс: минимальная конфигурация

Австралийский набор (8R0060884HS, ROW 5.13.4, VW Touareg RNS 850) ценен не
покрытием, а тем, что показывает, какую конфигурацию производитель считает
допустимой. Это серийный работающий продукт, и по нему видно, что обязательно,
а что нет.

| | Европа | Австралия |
|---|---|---|
| Объём | 22 ГБ | **3,1 ГБ** |
| Компонентов в `.pkg` | 18 | **7** |
| Контейнеров XAC | 3, суммарно 4,3 ГБ | 1, **298 МБ** |
| GDB | 2,0 ГБ | **335 МБ** |
| Стран с дорожными данными | 46 | 2 |

Состав австралийского пакета целиком:

```
LABEL_AN   XAC_AN   GDB_AN   TMC3GP_AN   LIT3GP_AN   LIT3GP2_AN   SDS3GP_AN
```

### Что необязательно

Четыре категории отсутствуют целиком, то есть без них устройство работает:

| Отсутствует | В европейском наборе весит |
|---|---|
| `CTY`, `CTY2`, `CTY3` — трёхмерные города | 5,0 ГБ |
| `TER`, `TER2` — рельеф | 2,1 ГБ |
| `GDB2` | 1,4 ГБ |
| `PIT` | 9 МБ |

Снятие этих компонентов уменьшает европейский набор с 22 до **13,4 ГБ** без
потери стран.

### Чего убирать нельзя, хотя выглядит похоже

`XAC2`, `XAC3`, `LIT3`, `LIT4` в австралийском наборе тоже отсутствуют, но это
не признак необязательности. Европейский XAC разбит на три части (`DB=1/3`,
`2/3`, `3/3`) — это одна база, поделённая по объёму, а не три независимых
компонента. У Австралии контейнер один потому, что стран две, а не сорок шесть.
Убрать их можно, но вместе с ними уедет покрытие.

### Где на самом деле лежит объём

В австралийском наборе на дороги приходится 298 МБ, а на точки интереса —
2,5 ГБ, то есть **80% объёма**. Это стоит держать в уме: набор, где нужны только
дороги, получается на порядок легче.

### Различие во флагах

Блоки `[common]` на уровне релиза различаются:

```
maps_small/VW/metainfo2.txt    EnableUserDefinedSWDLMode = "true"
                               skipMetaCRC = "true"

maps/MMI3G/metainfo2.txt       этих строк нет
```

В европейском наборе флаги стоят только на уровне носителя, в австралийском —
и на уровне релиза тоже. Если `skipMetaCRC` действительно отключает сверку
`MetafileChecksum`, дописать эти строки в `MMI3G/metainfo2.txt` — способ
получить право править метаданные. Блок `[common]` идёт в начале файла, так что
разборщик прочтёт флаг раньше, чем стал бы сверять сумму. Проверяется только
на устройстве.

Подписи устроены одинаково: в обоих наборах восемь значений `[AudiSignature]`
и `.pkg.sig` на 128 байт.

### Оговорка

Австралийский набор — MMI3GP, вариант 9478. На блок MMI3G он не встанет, списки
вариантов не пересекаются. Ценность его исключительно справочная.

## Проверки целостности при установке

Проверено на живом устройстве: Audi MMI 3G High, вариант 9307/9308, режим
user-defined SWDL с принудительной перезаписью. В этом режиме компоненты
отмечаются вручную и ставятся выборочно, так что каждый опыт занимает секунды —
`DBInfo.txt` весит 206 байт, каталог `LABEL` 2521 байт.

### Алгоритмы

| Поле | Где | Алгоритм |
|---|---|---|
| `CheckSum` у записи File | `metainfo2.txt` | **обычный CRC-32** (полином 0x04C11DB7, init и xorout 0xFFFFFFFF, отражённый) |
| `CheckSum`…`CheckSumN` у записи Dir | `metainfo2.txt` | **несколько CRC-32 по кускам** — правило ниже |
| `MD5` | `*.conf` | обычный MD5 всего файла |
| `check=qa` | `*.conf` | **три MD5 по 102 400 байт** со смещений 0, `size/2` и `size − 102400 − 1`; файл короче пробы читается целиком, и все три значения совпадают |
| `MetafileChecksum` | `metainfo2.txt` | не опознан |
| `checkcrc` = `fdefcrc` | `*.conf`, `*.pkg` | **одно и то же значение в двух местах**, алгоритм не опознан |

Формула проверена сплошь: `src/checksum.js` сверяет **все 24 компонента**
европейского набора, и все сходятся — и суммы, и размеры.

**У каталога сумм несколько.** Запись Dir несёт `CheckSum`, `CheckSum1`,
`CheckSum2`… — по одной на кусок `CheckSumSize` (в наборе везде 209 715 200,
то есть 200 МБ). У GDB их одиннадцать, у GDB2 восемь, у SDS две.

Правило, по которому куски нарезаются, выведено и проверено на нетронутом
наборе — сходятся **все 18 каталогов и каждый их кусок**:

> файлы в порядке имён без учёта регистра читаются **одним потоком**, CRC копится
> сквозь них; кусок закрывается, когда от **текущего файла** прочитано
> `CheckSumSize` байт; конец файла сбрасывает этот счётчик, но кусок **не**
> закрывает; последний неполный кусок пишется в конце.

Отсюда две неочевидности, на которых ломаются правдоподобные модели:

| Каталог | Что получается |
|---|---|
| `GDB`, `XAC`, `LIT` (большой файл первым) | кусок 0 обрывается ровно на 200 МБ образа, а `.conf` попадает в **последний** кусок |
| `SDS` (`.conf` сортируется первым) | кусок 0 **длиннее предела**: 478 байт `.conf` плюс полные 200 МБ образа |
| `TMC`, `LABEL`, `PIT` | один кусок — оба файла целиком, они меньше предела |

Две модели, которые сюда не подходят и были отброшены: «склеить всё и нарезать
по 200 МБ» (совпадает только когда большой файл идёт первым — то есть на GDB
случайно сходится, а на SDS нет) и «окно на каждый файл со стопом на обрезанном»
(верно для первых кусков, неверно для последнего везде).

Практическое следствие: **правка в глубине тома меняет не первую сумму.** Наши
изменения записей тайлов GDB лежат на ~347 МБ, то есть в `CheckSum1`. Пока
`mkmeta.js` и `checksum.js` считали только `CheckSum`, такая правка проходила
мимо проверки и сорвалась бы уже на устройстве.

Последний случай и вывел правило: сумма `SDS` сходится ровно на длине
209 715 200 + 478, где 478 — размер `SDS.conf`.

`filesize` при этом всегда полный, без обрезания.

### Три пробы `check=qa`

Смещения выведены перебором и сходятся на всех 19 компонентах с `.conf`:

```
#1  0
#2  size / 2                (целочисленно)
#3  size − 102400 − 1
```

У третьей пробы чтение кончается за байт до конца файла. Это ошибка на единицу
в коде производителя, но воспроизводить её обязательно — иначе значение не
сойдётся. Единственный файл короче пробы — `Label.DB` на 2048 байт; у него все
три значения равны MD5 целого файла.

До этого `relocate.js` писал в `.conf` первое значение трижды. Исправлено, но
на исход установки это не повлияло (см. раздел о переносе).

### `checkcrc` и `fdefcrc` — одно число

В `.pkg` есть секция `[crcs]` со строкой на компонент:

```
fdefcrc=XAC_ECE,11cca311
```

и в `XAC.conf` стоит `checkcrc=11cca311`. Это одно значение, продублированное
в манифесте и в описании компонента. Алгоритм не найден. Проверено и не
подошло: CRC-32 всего файла данных, первых и последних 100 КБ, склейки трёх
проб `check=qa`, строки MD5; CRC-32 самого `.conf` целиком, без строки
`checkcrc`, без `\r`; варианты CRC-32 bzip2, MPEG-2, POSIX, JAMCRC. При
переносе тайлов оба значения остаются старыми.

Зато известно, **как** они используются при установке: сверяются друг с другом.
Оригинальные данные с одним лишь испорченным `checkcrc` в `.conf` дают
`Errorcode 141` на 99%; изменённые данные при нетронутых `.conf` и `.pkg`
ставятся без вопросов. То есть установщик требует `checkcrc == fdefcrc`, но ни
одно из них с данными не сличает. Сверяет ли их с данными движок при работе —
открыто, и чисто проверить это нельзя: правка `fdefcrc` в `.pkg` рушит
`.pkg.sig`, а судьба подписи для загрузчика базы не выяснена.

Отсюда же: `Errorcode 141` — не только «не сошёлся `CheckSum`», как записано в
таблице ошибок ниже, а любая из установочных сверок.

### Что проверяется, а что нет

| Проверка | Соблюдается? | Чем установлено |
|---|---|---|
| `CheckSum` компонента | **да** | изменённый `DBInfo.txt` со старой суммой — Errorcode 141 |
| Целостность `metainfo2.txt` | **да**, по умолчанию | правка 8 байт суммы — «Meta info could not be opened» |
| `skipMetaCRC` на уровне релиза | **отключает** её | те же файлы плюс флаг в `[common]` — установка прошла |
| `[AudiSignature]` | **нет** | `metainfo2.txt` изменён, подпись осталась старой, всё встало |
| `skipFileCopyCrc` на уровне носителя | не действует | флаг стоит в корневом `metainfo2.txt`, но `CheckSum` всё равно проверился |
| `skipFileCopyCrc` на уровне релиза | **снимает проверку данных** | пересобранный контейнер XAC3 давал 141 на 100% установки; с флагом в `[common]` ветки релиза встал |
| `MD5`, `check=qa`, `checkcrc` в `.conf` против данных | **нет** | `Label.DB` изменён, `LABEL.conf` оставлен оригинальным, сумма каталога пересчитана — установка прошла |
| `checkcrc` в `.conf` против `fdefcrc` в `.pkg` | **да** | данные и `metainfo2.txt` оригинальные, в `XAC3.conf` изменены только восемь символов `checkcrc` — `Errorcode 141` на 99% |

Errorcode 141 означает несовпадение контрольной суммы компонента. Нарушение
целостности самого метафайла даёт другую ошибку, ещё на этапе открытия.

### Практический вывод

Метаданные и данные можно править — на уровне установки достаточно держать в
блоке `[common]` ветки релиза три строки:

```
EnableUserDefinedSWDLMode = "true"
skipMetaCRC = "true"
skipFileCopyCrc = "true"
```

Первые две есть в австралийском наборе, третью пришлось добавить самим. Все три
работают только на уровне релиза: те же флаги в корневом `metainfo2.txt` ни на
что не влияют.

После этого `MetafileChecksum` не сверяется, подпись роли не играет, а суммы
компонентов пересчитываются обычным CRC-32. Значит доступны и правка состава
`filedef` в `.pkg`, и изменение размеров компонентов, и подмена данных.

Подгонять байты под старую контрольную сумму, как я предполагал до опытов,
не требуется.

На уровне **установки** действующие проверки — `CheckSum` компонента в
`metainfo2.txt` и равенство `checkcrc`/`fdefcrc`. Но это не значит, что данные
можно править как угодно: при **чтении** движок сверяет контрольную сумму каждой
записи каталога FLDB (см. ниже), и правка файла по месту без её пересчёта
подвешивает инициализацию. Установка пройдёт, база — нет.

## Что даёт MMI3G-Toolkit

Сторонний проект `dspl1236/MMI3G-Toolkit` формат карт не разбирает — там нет
ни XAC, ни GDB. Но три его вывода прямо касаются нашей задачи.

### Активация FSC — это гонка, а не взлом подписи

Общинный «активатор» (Keldo 2015, DrGER2 2022) не подделывает подпись. Он
дописывает в `/mnt/efs-system/usr/bin/manage_cd.sh` одну строку:

```
(waitfor /mnt/lvm/acios_db.ini 180 && sleep 10 && slay vdev-logvolmgr) &
```

`vdev-logvolmgr` создаёт описатель базы `acios_db.ini`, а затем сверяет базу с
файлом FSC. Патч убивает процесс в промежутке: описатель уже есть, проверка не
успела. Отсюда важный вывод для нас: **проверка FSC и инициализация карт — разные
вещи**. Активация снимает блокировку доступа, но не заставляет движок принять
данные. Наша остановка на 25% — это движок, а не активация; её уже проходили.

### На устройстве доступна оболочка

Прошивка уже содержит `inetd`, `telnetd`, `io-pkt-v4-hc` и драйвер
USB-Ethernet `devn-asix.so`. Четыре строки в `start_network.sh` дают root по
telnet на `172.16.42.1` через переходник D-Link DUB-E100. Без переходника
остаётся механизм SD-скриптов (`copie_scr.sh`) — им пользуются все 26 модулей
проекта, в том числе для снятия `sloginfo`.

Это ровно то, чего нам не хватало: **увидеть, на что жалуется движок**, вместо
того чтобы гадать по проценту на экране. Слепая зона всё это время была здесь.

### Наш разбор контрольных сумм подтверждён независимо

Их `research/FIRMWARE_UPDATE_FORMAT.md` описывает тот же CRC-32 (полином
0xEDB88320, начальное 0xFFFFFFFF, финальный XOR — то есть `zlib.crc32`) и тот
же принцип обхода через флаг. Речь у них о прошивке (`ifs-root`, `efs-system`),
у нас о картах, но алгоритм и логика SWDL общие. Заодно подтверждается, что
подписей у прошивки нет вовсе, а `.sig` рядом с `TMCConfig.dat` — RSA-1024,
как и наш `.pkg.sig`.

Файлы FSC, признанные недействительными, устройство переносит в
`/mnt/efs-persist/FSC/illegal/signature/` — оттуда их можно вернуть обратно.

## Что даёт Java-on-Audi-MMI-3G

Заброшенный любительский проект (автор продал машину): попытка запустить свой
Java-код, в идее — Doom, на встроенной в MMI виртуальной машине J9. Из 379 МБ
около 370 занимает IBM WebSphere Real Time для i386, положенный туда лишь
потому, что J9 иначе не найти. Не заработало: в логах
`Unable to find and initialize required class java/lang/Object` и SIGSEGV —
библиотеки классов собирались из несовместимых сборок.

### Java — это оболочка, но не навигация

Меню и зелёные инженерные экраны действительно на Java: J9 исполняет `lsd.jxe`,
каркас `de.dreisoft.lsd.LSD` от 3Soft. Но список процессов, снятый с живой
машины, показывает, что навигация — родной код QNX:

```
/usr/bin/ndr           -hfs=/etc/hfs.cfg -rev=wheel -e=lvm -e=disChina
/sbin/mme-becker       -c /etc/mme.conf          (2 МБ, SH4 ELF)
/usr/bin/srv-hddmgr    -c /usr/bin/hddmgr.cfg
/usr/bin/vdev-logvolmgr -p SDS,MAPSTYLES -A -B acios_db.tmp -vvrml -f
```

Разбор карт живёт здесь, а не в Java. Декомпиляцией срезать путь не получится —
наш разбор XAC и GDB заменить нечем.

Заодно видно, что `-p` защищает именно `SDS` и `MAPSTYLES`, а не `XAC`.

### Оболочку можно подменить без перепрошивки

Настоящий пусковой скрипт `lsd.sh` со всеми ключами показывает два места, куда
стоит смотреть:

| Ключ | Что даёт |
|---|---|
| `-Dde.audi.tghu.engineering.base_dir=/HBpersistence/engdefs` | инженерные экраны — просто файлы `.esd` в доступном на запись каталоге |
| `-DLOG=all=0,Fw.Storage.Provider=2`, `-DSLOG=`, `-Ddsi.debuglevel=2` | уровни протоколирования |
| `-Dde.audi.tghu.traceConfig=/lsd/traceConfig.properties` | настройка трассировки |
| `-Dstartup.max.prepare.wait`, `-Dstartup.max.domain.wait` | таймауты запуска доменов, по 10 с |

Сам `lsd.jxe` берётся из `/HBextended/lsd.jxe`, затем `/HBextended/lsd2.jxe`,
затем `/HBpersistence/lsd.jxe` и лишь потом `/lsd/lsd.jxe` — то есть оболочку
подменяют файлом, не трогая флеш.

## Что даёт audi-c7-4g-tools

Набор SD-скриптов для MMI 3G+ (Audi A6 C7, кузов 4G). Четыре части,
включаются переменными в начале `run.sh`. **Машина не наша**: 3G+ против нашего
3G High 9308, пути и имена процессов могут отличаться.

### Зелёное инженерное меню включается без VCDS

Самое ценное. MMI3G-Toolkit утверждает, что бит GEM ставится только
диагностикой (адрес 5F, канал 6). Здесь то же делается записью в SQLite:

```
sqlite3 <база> "insert into tb_intvalues (pst_namespace, pst_key, pst_value)
                 values (4,4100,1)"
```

Сразу в три базы: `/mnt/efs-persist/DataPST.db`, `/HBpersistence/DataPST.db`,
`/mnt/hmisql/DataPST.db`. Это подтверждает форумную реплику про то, что
хранилище Java-оболочки оседает в `DataPST.db`.

**В скрипте опечатка.** Удаление вызывает `$SDPath/_utils/sqlite3`, а вставку —
`$SDPath/utils/sqlite3`, без подчёркивания; каталог называется `_utils`. То есть
значение удаляется и не возвращается: запуск с `GEM=1` меню не включит, а
выключит. Каталогов `db/efs-persist/old/` в наборе тоже нет, так что резервные
копии не сделаются. Брать оттуда стоит идею и запрос, но не файл.

### Сочетания клавиш

| Сочетание | Что делает |
|---|---|
| CAR + Back | красное инженерное меню |
| CAR + Menu | зелёное инженерное меню |
| Menu + колесо + правая верхняя | перезагрузка MMI |
| **Media + TEL** | **снимок экрана на SD-карту** |

Последнее пригодится сразу: снимки экрана вместо съёмки телефоном.

### Активатор карт — тот же приём, но грубее

Гонка со `vdev-logvolmgr` та же, что в MMI3G-Toolkit, но старым способом:
через подмену `mme-becker` на `mme-becker.sh` в `/etc/mmelauncher.cfg`. Тулкит
называет этот путь устаревшим и предпочитает дописывать в `manage_cd.sh`.

Две вещи там опасные:

* `rm -R -f /mnt/efs-persist/FSC/*` — **стирает все файлы FSC**, а не только
  навигационный. Если в машине активированы другие функции, их коды тоже
  пропадут.
* в наборе лежит чужой `0004000B.fsc` на 202 байта. Ставить чужой код
  активации — обход лицензии, помогать с этим не буду; он к тому же привязан к
  своему выпуску базы и на наш `8R0060884KL` не подойдёт. Законный путь —
  дилер по VIN.

### Имя процесса навигации на 3G+

В конце активатор делает `slay -9` процессу **`navcore`**. У нас на 3G High в
снятом списке процессов такого нет — там `ndr`, `mme-becker`, `srv-hddmgr`.
Похоже, `navcore` — имя из 3G+; на 9308 не проверено.

### Мелочи, которые совпали с нашим опытом

Порядок обновления: красное меню, карта в первый слот, «Обновление», после —
продолжить и пропустить документацию. Время: прошивка 20–30 минут, карты **3
часа**, скрипты — секунды. Совпадает с тем, что вы видели.

Часть `GFS=1` просто пишет `find / -print` на карту — самый безопасный способ
получить дерево файлов устройства.

## Что дают форумные SD-скрипты

Четыре набора с форума, все на одном механизме: `copie_scr.sh` в корне карты,
устройство расшифровывает и исполняет его при вставке. Разобраны все четыре,
в проекте оставлены два.

### Шифр разбирается на Маке

`copie_scr.sh` — XOR с потоком PRNG, начальное значение `0x001be3ac`, первое
значение отбрасывается, операция симметричная. Реализация лежит в тулките:

```
python3 MMI3G-Toolkit-main/builder/encoder.py decode copie_scr.sh out.sh
python3 MMI3G-Toolkit-main/builder/encoder.py encode in.sh copie_scr.sh
```

Двоичный `DecodeScript` под QNX, который возят с собой все эти наборы, не нужен.
Отсюда правило: чужой скрипт читается до запуска, а не после.

Обратная сборка проверена: `decode` и следом `encode` дают исходный файл байт в
байт. Значит правку зашифрованного скрипта можно вносить без опаски — и значит
расшифровке можно верить.

У трёх наборов `copie_scr.sh` — заглушка `cd $dstPath; ./run.sh`, вся логика в
открытом `run.sh`. У «Dump Capture» `run.sh` нет вовсе, код целиком внутри шифра.

### Маркерные файлы

Общее место у всех: `.started` перед работой, `.done` после, у слепка ещё
`.fs0`/`.fs1`/`.fs4` по ходу. По ним видно, отработал скрипт вообще и докуда
дошёл, без экранов и без съёмки телефоном. Приём стоит перенять — при
диагностике зависшей инициализации это единственный способ отличить «скрипт не
запустился» от «запустился и ничего не нашёл».

### Каталоги назначения надо создавать руками

Ни один из скриптов не делает `mkdir`, а пишет в подкаталог карты: слепок в
`dump/`, `DataPST.db` в `read/`. Если каталога нет, перенаправление не
выполнится — но `scriptDone.png` всё равно покажется и `.done` запишется. То
есть отказ молчаливый, как и всё остальное на этой машине.

В хранимых копиях наборов эти каталоги заведены, так что при копировании папки
на карту они приезжают вместе с ней.

### Слепок флеша

```
cat /dev/fs0 > $dstPath/dump/fs0.dump
cat /dev/fs1 > $dstPath/dump/fs1.dump
cat /dev/fs4 > $dstPath/dump/fs4.dump
```

Сырые образы разделов F3S, около 128 МБ, порядка 15 минут. Ценность в том, что
разбираются уже имеющимися средствами: `tools/extract_f3s_efs.py`,
`walk_f3s_efs.py` и `research/F3S_FORMAT.md` из тулкита. То есть это не только
резервная копия, но и материал для чтения офлайн.

### DataPST.db

Хранилище Java-оболочки, то самое, где живёт бит зелёного меню
(`tb_intvalues (4,4100,1)`). Выгрузка — одна строка:

```
cp -v -r /mnt/efs-persist/DataPST.db $dstPath/read/
```

Скачанная база открывается обычным `sqlite3` на компьютере.

Обратная заливка в форумном виде **не работала**: в ней было `cp -v
$SDPath/read/DataPST.db /mnt/efs-persist`, тогда как переменная в скрипте
называется `dstPath`. `$SDPath` не определён нигде, команда разворачивалась в
`cp -v /read/DataPST.db /mnt/efs-persist` и падала, а скрипт рисовал «готово».
Тот же класс ошибки, что и `_utils`/`utils` в `audi-c7-4g-tools`. В хранимой
копии слово исправлено; перешифровывать `copie_scr.sh` не потребовалось, он тут
только заглушка.

Заявленная польза — обход ошибки `03175 Invalid data set` после обновления ПО.
Это про прошивку, не про карты; проверить не на чем.

### Удаление ключей FSC

Против ошибки `03623 - неверный код разблокировки`. Скрипт целиком:

```
rm -f /mnt/efs-persist/FSC/*.fsc
rm -f /mnt/efs-persist/FSC/cache/*.fsc
```

В описании сказано «неиспользуемых, старых и не рабочих» — никакого отбора в
коде нет, сносится всё, включая ключи других функций. Третий по счёту найденный
скрипт, который так делает, после активатора `r_Q7` и предупреждения в
`audi-c7-4g-tools`. Заодно видно, что у ключей есть кэш в `FSC/cache/`, — этого
каталога `map_parse.sh` из тулкита не смотрит.

Из проекта набор удалён — держать двадцать двоичных файлов ради двух строк `rm`
незачем, а сами строки записаны выше. Если понадобится, он восстанавливается из
истории: коммит `b519767`.

## Правила работы с устройством

Список выстрадан опытами на живой машине. Каждое правило стоило отдельного
захода, а нарушение первых двух вывело навигацию из строя на вечер.

### `DBInfo.txt` не трогать никогда

Файл задаёт идентификатор базы: парт-номер, версию ПО и `SystemName`. К этой
паре привязана активация FSC (`userflags=fsc@40025` в манифесте пакета). Правка
`SystemName` — даже с сохранением обязательной длины в 13 символов — срывает
активацию, и карты блокируются примерно через десять минут работы.

Отсюда же понятно, зачем поле объявлено как «mandatory 13 characters»: длина
фиксирована именно ради сверки.

Для любых опытов идентификатор базы должен оставаться байт в байт прежним.
Менять можно только содержимое компонентов.

### `DBInfo.txt` и `config.nfm` не ставить выборочно

У всех компонентов стоит `DeleteDestinationDirBeforeCopy = "true"`, и у
большинства назначение — собственный каталог:

```
XAC3  ->  /mnt/nav/db/pkgdb/XAC3
GDB   ->  /mnt/nav/db/pkgdb/GDB
```

Но у этих двух файл лежит **в корне базы**:

```
DBINFO  ->  /mnt/nav/db/DBInfo.txt
CONFIG  ->  /mnt/nav/db/config.nfm
```

Если устройство понимает «удалить каталог назначения» буквально, установка любого
из них сносит `/mnt/nav/db/` целиком вместе со всем `pkgdb`. На устройстве это не
проверялось, но поведение согласуется с наблюдаемым. Ставить их только в составе
полной установки.

### Реестр тайлов обязан совпадать с данными

Изъятие тайлов из контейнера без правки `XAC-STRUKTUR` в `.xah` **подвешивает
инициализацию**: прогресс доходит примерно до четверти и замирает.

Наблюдение верное, а первое объяснение («загрузчик ждёт данные по смещениям из
реестра») — нет. Как выяснилось позже, любая правка содержимого контейнера по
месту делает устаревшей контрольную сумму записи в каталоге FLDB (`+0x20`), и
движок отвергает файл при чтении — см. «Алгоритм суммы каталога FLDB». Изъятие
тайлов меняет контейнер точно так же. Согласовывать `.xah` с данными всё равно
нужно, но одного этого мало: суммы каталога надо пересчитывать.

### Автоотметка в меню ничего не проверяет

В режиме user-defined блок сам отмечает часть компонентов. Сравнивает он поле
`version` из `metainfo2.txt`, а не содержимое, поэтому изменённый компонент с тем
же номером версии не отметится. Проверять факт записи на носитель надо размером
файла, а не отметкой. Нужный компонент отмечается вручную.

### При активаторе standard mode не ставит базу вовсе

Активатор снимает не только проверку FSC. Он убивает `vdev-logvolmgr` через
десять секунд после появления `/mnt/lvm/acios_db.ini`, и описатель до сверки не
доживает. Побочно это лишает SWDL источника сведений о версии установленной
базы: сравнивать не с чем.

На экране это «?» напротив `AUDI_MMI3G_ECE` вместо `Y` или `N` — состояние
неизвестно. **В режиме СТАНДАРТ такой пакет пропускается целиком.** Отказа нет,
установка проходит и рапортует об успехе, но на раздел не попадает ничего — ни
XAC, ни GDB, ни LIT.

Дальше это неотличимо от рассогласования реестра с данными: свежий раздел после
`delNavHDD.sh`, пустой `pkgdb`, инициализация замирает на четверти. Три захода
подряд с одинаковым симптомом оказались одним отказом, а не тремя.

Значит с активатором ставить только в user-defined, руками проставив `Y` на
`Application` во **всех** подпунктах четырёх пакетов:

```
AUDI_MMI3G_ECE   NaviPersistence   MapStyles   TMCConfig
```

После перевода всех подпунктов в `Y` «?» у верхнего уровня сменится на `Y`.

Две оговорки по этим четырём:

* у `TMCConfig` в ветке MMI3G файловых записей нет вовсе — только
  `DeviceDescription`, `VendorInfo` и `updateOnly`. Пункт пустой, отмечается для
  порядка и ничего не пишет;
* `NaviPersistence` и `MapStyles` объявлены `updateOnly = "true"` и потому не
  отмечаются сами никогда. При этом релиз объявляет
  `scriptPost = "/HBpersistence/navi/db/clearLastCityHistory.sh"` со своим
  `scriptPostCRC` — то есть скрипт из `NaviPersistence` вызывается после
  установки. Назначение у него в `/HBpersistence`, который переинициализация
  раздела не трогает, так что от прошлой установки он остаётся; но в полную
  установку включать его надо.

Механика «?» выведена из действия активатора и согласуется с наблюдаемым; само
поведение стандартного режима взято из форумного руководства и совпало с тремя
нашими заходами.

### Ошибки

| Что на экране | Когда | Значение |
|---|---|---|
| `Errorcode 141` | на 100% копирования | не сошлась `CheckSum` компонента |
| `Errorcode 140` | во время обновления | по форумному руководству — обновление поверх старой базы; предотвращается удалением раздела заранее, значение точно не выяснено |
| `Errorcode 150` | сразу, до начала копирования | **файловая система в режиме read-only** (форумная трактовка, «unqualified SSD» — про внутренний nav-раздел, не про карту). Точная причина read-only у нас **не установлена**. Отброшено: замок LOCK на карте (`XAC3` записался, а установщик на карту и не пишет) и нехватка места (у компонента `DeleteDestinationDirBeforeCopy` — старый каталог сносится до записи, объём тот же). Первое, что пробовать, — перезагрузка (раздел монтируется заново на запись); при повторе — `delNavHDD.sh` |
| `Meta info could not be opened` | до начала | нарушена целостность `metainfo2.txt`, нет флага `skipMetaCRC` |
| «?» напротив пакета | в списке компонентов | стоит активатор, версия установленной базы не читается; в режиме СТАНДАРТ пакет будет пропущен молча |
| инициализация замирает | после установки | `NDL Initialisation` начинается и не заканчивается: движок не принял базу. Причины разные — от пустого `XAC` до перенесённых тайлов; различать по `sloginfo` |

### Восстановление

В инженерном меню есть консоль `main/nav/databaseupdate/Console` с диагностикой
и обслуживанием базы. Два пункта, которые стоит знать:

**Список сведений о базе** показывает, видит ли устройство базу вообще:

```
no valid acios_db found on DVD-drive
no valid acios_db found on HDD
no valid acios_db found on SD0
no valid acios_db found in HBpersistence
Database info 01/01/70.00:03:36
```

`acios_db` — внутреннее имя навигационной базы в прошивке, в файлах набора
такого слова нет. Нулевая дата означает, что база не опознана вовсе, а не
повреждена частично.

**`delNavHDD.sh`** переинициализирует раздел навигации:

```
starting navigation partition reinit...
stopping application...
please reboot to read new initialized partition
afterwards install navigation database
```

Это и есть правильное восстановление: раздел создаётся заново, после чего
**обязательна перезагрузка**, и только потом установка базы. Удаление базы через
обычный пункт меню такого эффекта не даёт — остатки в корне `/mnt/nav/db/`
могут сохраняться.

Форумное руководство советует нажимать `Delete Nav HDD Partition` дважды — выйти
по `return` и повторить, — затем подождать минуту и только тогда перезагружаться.
Зачем нужен второй заход, не выяснено; вреда от него нет.

После переинициализации может потребоваться заново применить FSC.

## Перенос тайлов: первый заход на живой машине

Опыт, к которому шла вся работа: два тайла Ватикана `VA00`/`VA01` перенесены
в Никосию (33.36 в.д., 35.17 с.ш.) инструментом `relocate.js`, набор собран
`mkmeta.js`, на устройство поставлены только `XAC` и `XAC3` поверх рабочей
базы. Три сборки подряд, все три — **инициализация замирает на 28%**:

| Сборка | Что менялось | Итог |
|---|---|---|
| 1 | инструмент как был | 28% |
| 2 | исправлены три пробы `check=qa` в `.conf` | 28% |
| 3 | то же плюс растр `.ras` не трогается (`--no-ras`) | 28% |
| 4 | то же, но назначение — 25 км внутри Италии, а не Кипр | 28% |
| 5 | `--zero`: сдвиг 0, растр не тронут, переписаны только две связи `NACHBARN` — контейнер отличается от рабочего на 4 байта | 28% |
| 6 | Кипр с исправленными суммами каталога FLDB (`out/cyprus`) | 28% |
| 7 | то же, но `--no-nachbarn`: соседи не тронуты, граф симметричен (`out/cyprus-nonb`) | 28% |

Четвёртая сборка закрыла самую неприятную версию: дело **не в том, что на
Кипре пусто у GDB, LIT и CTY**. Тайлы, переехавшие внутрь плотного итальянского
покрытия, замирают так же.

> **Поправка, отменяющая вывод этого раздела.** Здесь стояло: «значит базу ломает
> сама правка, и дорога через один XAC не закрыта принципиально». Это неверно.
> Все семь сборок — **частичные установки** (только `XAC` и `XAC3`), а такая
> установка сносит `/HBpersistence/navi/db/acios_db.ini` и не создаёт его заново.
> Без описателя навигация встаёт на 28 % при любом содержимом. Сборка 5 это и
> показывала: контейнер отличался от рабочего на **четыре байта** — и всё равно
> 28 %. Тогда это выглядело как «ломает любая правка», а на деле правка была ни
> при чём. Разгадка — в разделе «Разгадка: зависание на 28%».

Откат каждый раз — те же два компонента с оригинальной карты, двадцать минут.
Ни раздел, ни остальная база не страдают.

### Где именно замирает

Это выяснилось не по данным, а по `sloginfo`, снятому в сломанном и рабочем
состояниях. Рабочее:

```
00:00:15  start: NDL Initialisation
00:00:18  mark: StateOfOperation FULLY_OPERABLE
00:00:19  end: NDL Initialisation
00:00:44  [Startup] OperationManager#setNavigationInitialized( true )
00:00:47  [Startup] OperationManager#setMapInitialized( true )
```

Сломанное:

```
00:00:14  start: NDL Initialisation
          — и всё. Ни mark, ни end.
00:00:25  [Startup] OperationManager#setNavigationInitialized( false )
```

`NDL Initialisation` — навигационный слой данных в родном коде QNX. Он
начинает инициализацию и не заканчивает её никогда; всё, что дальше, не
наступает. В рабочем состоянии этот шаг занимает четыре секунды. Полоса на 28%
— это Java-оболочка, которая ждёт событие от NDL. Загрузка процессора при
этом 6%: NDL не крутится, а ждёт.

Пара строк `start`/`end: NDL Initialisation` — самый быстрый способ понять,
дошла ли база до движка. Их достаточно грепнуть.

### Что отсеяно

Два полных дампа, сломанный и рабочий, отличаются ровно одним: в рабочем
смонтирован `/SDS` и движок держит открытыми 30 файлов базы, в сломанном —
`/SDS` нет и открыты два файла, каталог и стили карты. Оба различия — следствие
незавершённой инициализации, не причина. Всё остальное одинаково:

| Версия | Чем закрыта |
|---|---|
| активатор мешает | `vdev-logvolmgr` получает `Signal (15)` ровно через 10 с после старта в обоих состояниях |
| нет `acios_db.ini` | нет и на рабочей базе — норма при активаторе |
| потерян FSC | нет и на рабочей базе |
| nav-раздел переполнен | 97% в обоих состояниях |
| `/mnt/lvm` не смонтирован | не смонтирован и на рабочей базе |
| `check=qa` испорчен | исправлен — сборка 2, тот же исход |
| лишние ячейки в `.ras` | не пишутся — сборка 3, тот же исход |

Про открытые файлы одна оговорка: `pidin` — снимок через десять минут после
загрузки. «Открыл, прочитал и бросил» выглядит в нём так же, как «не открывал».

### Что при этом узнали о данных

**254 тайла из 3777 не имеют ни одной ячейки в общем растре `.ras`.** Растр
хранит один номер тайла на ячейку, и ячейку забирает сосед. Ватикан целиком
внутри римских тайлов, поэтому `VA00`/`VA01` — среди этих 254. Первая версия
`relocate.js` дописывала им десять ячеек на новом месте; это единственная
правка переноса, которая создавала ссылку, а не двигала существующую. На исход
не повлияла.

**Соседство почти всегда взаимно.** Из 18 195 направленных связей `NACHBARN`
односторонних пять, и все пять — российские тайлы на краю покрытия:
`RU0M -> RU8D`, `RUB3 -> RUBW`, `RUBN -> RUBL`, `RUC6 -> RUC2`, `RUCC -> RUCB`.
Перенос добавляет ещё две: у `IT1H` и `IT3S` остаются ссылки на уехавшие
`VA00`/`VA01` без обратных. Инструмент оправдывает это 586 «паромными» парами
с несоприкасающимися рамками — но те взаимны, а эти нет.

**Уровни `XAC-STRUKTUR L1..L4` — степени детализации одного тайла, а не
пространственная иерархия.** Рамки одного тайла на разных уровнях почти
совпадают, на L3/L4 просто меньше объектов. Значит переносить все уровни
тайла разом — правильно, вложенность этим не ломается.

**Ватикан — анклав в буквальном смысле данных.** Рамка `VA00` целиком лежит
внутри рамки `IT1H` (тайл около градуса на градус). Перенос вынимает вложенный
тайл из накрывающего, оставляя у накрывающего ссылку на него.

### Четыре байта — и тот же отказ

Пятая сборка меняет картину. От рабочей базы она отличается двумя номерами
соседей в `.xah`; граф с пятью односторонними связями движок терпит, а от двух
новых валится намертво — в это не верится. Зато так ведёт себя проверка
целостности: ей безразлично, четыре байта или четыре мегабайта. И все косвенные
признаки те же: ни одного открытого файла базы, спокойные потоки `ndr`, ЦП 6%.
Это не разборщик, споткнувшийся о данные, это отказ на входе.

Значит где-то есть сумма, которая накрывает содержимое `.xah` и которую мы не
пересчитываем. И она давно на виду: **в каждой записи каталога FLDB поле
`+0x20 u32` — контрольная сумма файла**, алгоритм не опознан (см. `src/fldb.js`).
`relocate.js` правит байты файлов по месту и каталог не трогает — после любого
переноса сумма у `.xah` и у четырёх тайлов устаревает. Единственная из наших
правок, которую мы даже не считали правкой.

Поле зависит от содержимого: у 45 одинаковых `.plz` сумма одна при разных
именах и смещениях, у четырёх тайлов Ватикана — четыре разные. Перебор
стандартных алгоритмов на 18 образцах из трёх контейнеров не дал ни одного
совпадения: CRC-32 с восемью полиномами × отражение × четыре затравки × два
финала × вход как есть / байты словами наоборот / полубайтами / задом наперёд;
CRC-16 в старшей и младшей половине; FNV-1/1a, djb2, sdbm, Jenkins OAAT, ELF,
SuperFastHash, MurmurHash2/2A; Adler-32, Fletcher-32, суммы байт/слов, XOR.
Либо алгоритм собственный, либо на входе не только содержимое.

Прежде чем лезть в код — проверка, нужно ли: оригинальный контейнер `XAC` с
одним изменённым битом в поле суммы записи `EJ211.xah` (`out/fldbtest`).
Данные нетронуты; повисло — поле сверяется; поднялось — поле инертно, и
виновата семантика правок.

### Разбор бинаря: что уже видно

Прошивка распакована (`fw/`, поезд K0257_6_D1, вариант 41). `tools/extract_ndr.sh`
достаёт `ndr` (413 КБ, SH-4 ELF) и `MMI3GApplication` (30 МБ) из
`ifs-root.ifs` без потерь.

Что прочитано прямо из кода:

* **База проверяется поблочно.** В `MMI3GApplication` строки
  `CIFFDataBlock::CreateForDecoding: illegal Checksum / illegal Header /
  %ld Elements`. Значит у каждого блока данных своя контрольная сумма, и
  движок сверяет её при чтении. Это объясняет, почему падают все сборки, включая
  правку соседства на 4 байта: правим содержимое блока, сумма остаётся старой.
* **Сумма — не табличный CRC.** В `ndr` по адресу `0x807a0c8` — процедура
  контрольной суммы: побитовый шаг с полиномом `0x04C11DB7` вперемешку со
  сложением-накоплением, по 4-байтовым словам плюс хвост побайтно. Стандартные
  CRC (все полиномы × отражения × затравки × финалы) её не воспроизводят —
  проверено на 18 образцах из трёх контейнеров; собственный CRC-32 бинаря
  (не-отражённый, тот же полином) тоже мимо.
* Процедура вызывает методы C++-объектов, поэтому по статическому дизассемблеру
  (capstone в SH-режиме к тому же путает пулы литералов с кодом) её надёжно не
  восстановить. Нужен декомпилятор SuperH — Ghidra (ставится `brew install
  ghidra`).

Открыто: какой именно уровень сумм держит инициализацию — поле в каталоге FLDB
(`+0x20`, тоже не опознано) или внутренняя сумма блока CIFF. Разделяет их опыт
`out/fldbtest`: оригинальный контейнер с одним изменённым битом в поле каталога.

### Важная поправка: сумму каталога движок при загрузке не проверяет

Установка исправленной сборки (оба компонента, суммы каталога верны) — и всё
равно 28%. Разбор `ndr` объясняет почему: функцию суммы `FUN_0807a0b8` вызывают
ровно два места, оба CIFF — кодирование (`FUN_0807a16c`) и декодирование
(`FUN_0807a1e0`). Больше никто. То есть сумму записи каталога FLDB (`+0x20`)
пишет офлайновый сборщик базы тем же алгоритмом, но `ndr` при чтении её **не
сверяет**. А тайлы, как показал поиск, не обёрнуты в CIFF.

Значит контрольные суммы к зависанию на 28% отношения не имеют. Пересчитывать
их всё равно правильно (для установки `CheckSum` компонента в `metainfo2.txt`
проверяется — иначе Errorcode 141), но преградой на загрузке была не они.
Зависание **смысловое**: нав-ядро не принимает тайл, перенесённый с исходного
места. Подтверждается сборкой 4 — перенос на 25 км внутри Италии висел так же,
то есть дело не в пустом Кипре, а в самом переносе. Следующий шаг — снять
`sloginfo` уже с этого состояния (есть строки вида `ndl load error 2: ...`) и
проверить, не рассогласование ли это XAC с GDB: GDB со своим пространственным
индексом остался на старом месте, а мы ставим только XAC.

загрузчик там, и его на эту сумму мы не проверяли.

### Алгоритм суммы каталога FLDB — восстановлен

Ghidra декомпилировала `ndr`, функция `FUN_0807a0b8` — это и есть контрольная
сумма записи каталога (поле `+0x20`):

```
acc = 0
для каждого 4-байтового BE-слова W:
    step = acc << 1;  если acc & 0x80000000 → step ^= 0x04C11DB7
    acc = (0xC7 + step + W) mod 2^32
для каждого хвостового байта b:
    acc = (acc + b) mod 2^32
вернуть acc
```

Гибрид: побитовый шаг CRC с полиномом `0x04C11DB7` плюс аддитивное накопление,
константа шага `0xC7`, начальное `0`. Сверено со **всеми 7852** записями, у
которых сумма считается целиком; сошлись все записи XAC, XAC2, XAC3. Три
исключения — гигабайтные индексы `LIT2/3/4`, у них сумма, видимо, с ограничением
длины; к переносу тайлов это не относится.

Код в `src/fldb.js` (`checksum`, `refreshChecksum`). `relocate.js` теперь
пересчитывает сумму каждой тронутой записи — четырёх тайлов в XAC3 и `.xah` с
`.ras` в XAC — потому что правит файлы по месту, а каталог этого сам не
замечает. Это и была единственная правка, которую мы раньше вовсе не делали.

**Слой CIFF — это та же сумма, но не в тайлах.** Ghidra декомпилировала
`CIFFDataBlock::CreateForDecoding` (`ndr` `FUN_0807a1e0`). Раскладка блока:
сумма u32 в `+0x00`, длина u32 в `+0x10` (>= 0x14, <= размера буфера), сама
сумма считается по `[блок+4, длина−4]` — и вызывает **ровно ту же**
`FUN_0807a0b8`, что и каталог FLDB. То есть отдельного алгоритма тут нет.
Но поиск самосогласованных CIFF-блоков в тайлах `.xac` и в `.xah` не дал ни
одного: эти файлы не обёрнуты в CIFF, CIFF живёт в других данных (GDB/LIT). Для
переноса тайлов, значит, достаточно суммы каталога — второго слоя внутри тайлов
нет.

**Разрешено позже.** Вопрос стоял так: не устаревшая ли сумма каталога держит
инициализацию на 28%. Ответ — **нет**. Ни сумма каталога, ни поблочная сумма
`CIFFDataBlock::CreateForDecoding: illegal Checksum` к зависанию отношения не
имеют: его вызывал пропадающий при частичной установке `acios_db.ini`. Сборка
`out/limassol` с оригинальным XAC и правильными суммами висела точно так же,
а после возврата описателя навигация поднялась без единой правки данных.

### Откуда взять алгоритм

Из кода. FLDB читает `ndr`, он лежит в `ifs-root.ifs`. Прошивка блока —
**`HNav_EU_K0257_6_D1`** (строка `Train` в `sloginfo`; `sw_trainname.txt`

Цепочка извлечения тулкита собрана на Маке: `tools/qnx_ifs_decompress` и

для K0257 формат IFS тот же QNX, но это ещё предстоит увидеть.

Урок, оплаченный одной установкой: при нескольких сборках подряд на одной карте

## Где лежат данные

Сам навигационный набор в репозиторий не входит — это 22 ГБ, и он неизменен,
так что версионировать в нём нечего. Целостность проверяется без git: в каждом
`.conf` лежит MD5 своего бинарника.

Скрипты ищут каталог набора сами — тот, внутри которого есть `pkgdb`. Порядок:
явный аргумент, переменная окружения `MMI3G_MAPS`, каталог `maps` рядом с
репозиторием, корень репозитория, текущий каталог. Раскладка по умолчанию:

```

  pkgdb/
  metainfo2.txt
  ...
src/            скрипты
tools/          SD-скрипты для машины
out/            выгрузки GeoJSON и собранные наборы (пересоздаются, в git не входят)
logs/           дампы с устройства (в git не входят)
fw/             пакет прошивки MU для извлечения ndr (в git не входит)

В `logs/` лежит то, что снимают SD-скрипты тулкита, и оно не для репозитория
не только из-за объёма: `sysinfo_dump.sh` забирает `passwd`, `shadow`,

### Итог фазы: перенос через один XAC упирается в GDB

Семь сборок и три снимка с машины дали ответ, хотя и не тот, на который
рассчитывали.

**Решено полностью — установка.** Контейнер FLDB пересобирается побайтно, все
суммы, которые сверяет установщик, считаются верно: `CheckSum` компонента,
`MD5`, три пробы `check=qa`, сумма записи каталога (`+0x20`, восстановлена из
`ndr`). Изменённые `XAC`/`XAC3` ставятся без ошибок. Это готовый результат:
редактировать и пересобирать существующий набор мы умеем целиком.

**Зависание — не целостность.** Пункт «Recheck database» инженерного меню
(`reCheckNavDV.sh`) отвечает `database checking is not enabled`: сверка базы на
устройстве выключена. В `sloginfo` ни одной жалобы ядра. Значит никакую
контрольную сумму удовлетворять не нужно — и `checkcrc`, который так и не
опознан, к 28% отношения не имеет.

**Висит `ndr` на перенесённом тайле.** Единственный поток `MMI3GApplication`,
ждущий ответа, ждёт его от `ndr`; `ndr` жив и крутится. Достаточно сдвинуть
рамки тайла: сборки 6 и 7 двигают координаты и виснут, `nonb` снял подозрение
с соседей, `--no-ras` (сборка 3) — с растра.

> **Поправка.** Здесь раньше стояло «`acios_db.ini` не появляется как
> следствие». Это неверно: проба смотрела в `/mnt/lvm/acios_db.ini`, а этого
> пути нет и на **исправной** машине. Настоящий файл лежит в
> `/HBpersistence/navi/db/acios_db.ini` и на рабочем эталоне присутствует —
> см. раздел про `acios_db.ini` ниже. С зависшей машины его не снимали.

**Почему — предположение того времени, не подтверждённое.** Тогда считали так:
положение тайла зашито не только в `XAC`, свой пространственный индекс есть у
`GDB`, есть индексы LIT, и `ndr` при инициализации не может их согласовать —
молча.

Позднейший разбор `MMI3GApplication` этого не подтверждает и не опровергает, но
показывает другое место остановки: автомат инициализации NDL не доходит до
состояния 3, где ожидается готовность, и стоит в 0, 1 или 2 (см. «Инициализация
NDL» ниже). Ближайший к этому подозреваемый — получение итератора по
навигационному тому в состоянии 1, но какое из трёх состояний на деле, по
журналу неразличимо.

**Решение:** зафиксировать достигнутое (этот раздел), вернуть машине
оригинальные `XAC`/`XAC3`, и следующей фазой разбирать GDB. Если тела блоков
и пространственный индекс GDB поддадутся — перенос станет полным: XAC даёт
маршрут, GDB — рисунок.

## Разгадка: зависание на 28% — это пропавший `acios_db.ini`

**Подтверждено на машине.** После частичной установки файл
`/HBpersistence/navi/db/acios_db.ini` отсутствует. Кладём его обратно —
навигация инициализируется и карта работает.

### Как выяснилось

Сборка `out/limassol` (только GDB/GD2, XAC и XAC3 — оригинальные, побайтно)
дала то же зависание на 28%. Это сняло подозрение с XAC: дело не в переносе
маршрутных данных. Проба на зависшей машине против эталона исправной:

| | Исправная | Зависшая |
|---|---|---|
| `/HBpersistence/navi/db/acios_db.ini` | есть, 923 байта, 17 записей | **отсутствует** |
| `/HBpersistence/navi/nobss/` | `AUDIMMI3G.swap`, 3.2 МБ | пусто |
| состав `/mnt/nav/db/pkgdb` | 20 каталогов | 20 каталогов, одинаково |
| `end: NDL Initialisation` | есть | нет |

Данные на разделе целы — уничтожен только описатель баз в персистентности и
кэш драйвера.

### Почему это даёт ровно такую картину

Смыкается с разбором `MMI3GApplication` до последнего звена:

```
частичная установка
 └ acios_db.ini не создан (nobss пуст)
    └ getDatabasesFromIniFile: can't open ini-file
       └ список баз пуст → каталог тома пуст
          └ FUN_08e983f4 вернёт 0 → createIterator вернёт -101
             └ «no iterator for nav cd 1» (в отключённый канал)
                └ NDL стоит в состоянии 1 и ждёт вечно
                   └ нет end: NDL Initialisation → полоса на 28%
```

Молчаливость объясняется тем же разбором: все сообщения этой ветки идут в
канал, который печатает только при ненулевом указателе, а он закрыт.

### Починка

`tools/write_fixacios.sh` кладёт на карту `tools/fixacios/run.sh` и побайтную
копию описателя, снятую с исправной машины (923 байта, проверяется при записи).
Скрипт на машине:

* не трогает файл, если тот уже есть, — только сохраняет копию;
* пишет только если **все** пути из описателя существуют;
* выставляет права 666, как на эталоне;
* `nobss` не трогает — кэш пересобирается сам.

Карту вставлять **без захода в меню обновления**, затем перезагрузить голову.

### Что это меняет

Частичная установка теперь работоспособна. Цикл проверки сокращается с
трёхчасовой полной установки до примерно получаса: правим GDB, ставим два
компонента, подкладываем описатель, перезагружаемся.

И задним числом: все прежние неудачи с переносом XAC объясняются этим же —
они все были частичными установками. Вывод прошлой фазы, будто `ndr` не может
согласовать индексы XAC и GDB, к делу отношения не имел.

## Кто в прошивке читает какой файл

Собрано через GhidraMCP по путям к исходникам. Это опора для проверки
генерации: чтобы сверять наши файлы, надо знать, каким кодом они разбираются.

| Наш компонент | Формат | Модуль-читатель в прошивке |
|---|---|---|
| XAC, XAC2, XAC3, `.xah` | FLDB + VEKTORBLOCK | `NavCore\xaclib\private\` — 17 файлов |
| GDB, GD2 | контейнер `DEADBEEF`, тайлы | `devctrl\collect\hydra\server\src\gdb\private\` (управление) + декодер геометрии `FUN_092526f0` |
| CTY, TER (`.ATLAS`) | Orion | `common\isdb\orion\main\private\COrionDatabase.cpp` |
| TMC | | `NavCore\tmc\private\t_daten.cpp`, `xaclib\xac_tmc.cpp` |
| контейнеры, каталог | FLDB | `NavCore\cdm\private\` |
| открытие базы | | `NavCore\dbm\private\dbm_opendb.cpp` |
| загрузка в движок | | `NavCore\ndl\private\` — `XacInterface.cpp`, `Loader.cpp`, `CDMLoader.cpp` |
| маршрутизация | | `NavCore\scout\private\scout509\` — `_KOSTEN`, `_SCOUT`, `_TW`, `_SW`, `Vias` |

Модуль `isdb` объясняет и сообщение `IsDb layer does not accept loaded data`,
которое встречалось при разборе инициализации NDL: это слой Orion-баз.

Читатели `LIT` и `PIT` по строкам не нашлись — поиск по `.LIT`, `lit` и
`Orion` их не дал. Возможно, они разбираются тем же `isdb` или лежат в модуле
без характерных строк.

### `xaclib` покрывает все разделы `.xah`

Имена файлов ложатся на разделы один в один, что подтверждает разбор `.xah`:

```
xac_string.cpp      -> STRING          xac_country.cpp     -> COUNTRY
xac_basic_name.cpp  -> BASIC NAME      xac_language.cpp    -> LANGUAGE
xac_build_infos.cpp -> BUILD INFOS     xac_neighbour.cpp   -> NACHBARN
xac_poi.cpp         -> POI             xac_name.cpp        -> имена
xac_vect.cpp, xac_vect_iter.cpp, xac_vtre.cpp  -> векторные блоки
xac_fe.cpp (Fahrbahnelement), xac_glob.cpp, xac_korr.cpp, xac_dbm.cpp
```

### Кодирование точек в тайле GDB — из `FUN_092526f0`

Декодер геометрии найден по строке проверки `Illegal tile coordinate width!`.
Что из него читается:

**Ширина координаты тайла** — только `8, 12, 16, 24, 32` бита, иначе
срабатывает проверка. Это подтверждает прежнее наблюдение про бит-упаковку.

**Головной байт элемента** раскладывается так:

```
бит 7      признак полигона   (проверки «Polygon flag set» / «not set»)
биты 6..5  формат упаковки 0/1/2   (иначе «Illegal bitpack format»)
биты 4..0  разрядность дельты
```

Остальные проверки называют ограничения формата прямо:

* `illegal use of 2 point encoding` — формат 2 допустим только при ровно двух точках;
* `Point has illegal number of coordinates` — у точечного объекта координат ровно одна;
* `Point has z coordinates` и `Polygon has z coordinates` — поле `zCoordFormat` должно быть нулевым;
* `Default case in switch statement` — иных типов объектов нет.

Наш `encodePoints` реализует один из этих вариантов (тот, что round-trip
проходит побайтно на 809 тайлах). Теперь видно, какие ещё варианты существуют и
чего они требуют.

## Инициализация NDL: автомат разобран по бинарю

Разобрана `MMI3GApplication` (SH-4 LE, 27 МБ кода, Ghidra). Код инициализации
NDL автоанализатором пропущен — туда попадают только по указателям, поэтому
функции пришлось поднимать вручную: найти строку, найти слот литерального пула
с указателем на неё, от него — инструкцию `mov.l @(disp,PC)` и уже от неё
раскрутить пролог назад. Скрипты в `scratchpad/gs/Ndl*.java`.

### Автомат `FUN_08238080`

Бесконечный цикл `do { ... } while(true)` с опросом и нарастающей паузой
(счётчик растёт до 100 и передаётся в задержку; единица измерения из кода не
видна). Пять состояний:

| Состояние | Что делает | Куда уходит |
|---|---|---|
| 0 | ждёт, пока глобальный статус (`FUN_08eb2664`) станет 3, и пока `FUN_08236070` не захватит объект | → 1 |
| 1 | `FUN_08236b50`: >0 — готово, 0 — надо открывать БД, <0 — молча ждать | → 3 / → 2 |
| 2 | печатает `opening databases...`, зовёт открытие баз | → 3 |
| 3 | опрашивает готовность, ведёт таймаут | печатает `end:` |
| 4 | `starting loadtest` — похож на отладочный; встречается ли в работе, по журналу сказать нельзя (сообщение подавлено) | → 3 |

### Главное следствие для диагностики

`end: NDL Initialisation` печатается **только в состоянии 3** — и оттуда оно
печатается при любом исходе: либо по общему таймауту (вместе со строкой
`The NDL reached a timeout during start up`), либо когда прогресс затих дольше
100 тиков. Поэтому:

> **нет `end:` в журнале ⇒ автомат не дошёл до состояния 3.**

Это и есть точный смысл нашего сигнала «прошло / не прошло»: зависание сидит в
состояниях 0, 1 или 2. Какое из трёх — по журналу неразличимо, все переходы
между ними молчаливые.

### Почему в журнале ничего не видно

Логгеров два. `start:` и `end:` идут через `FUN_08e89ac0` — он виден в
`sloginfo`. А `opening databases`, `enter state %d, leave state %d` (пишет
`setState`, `FUN_08237fa8`) и `no iterator for nav cd 1` идут через
`FUN_08e832b0`, который печатает только если указатель на канал не NULL:

```c
if (param_9 != 0) { ... }        // канал не зарегистрирован — сообщения нет
```

На машине этот канал закрыт, поэтому различить состояния 0/1/2 по журналу
нельзя. Судя по самой проверке, включить его — значит сделать указатель канала
ненулевым в памяти процесса; способа сделать это извне не найдено.

Рядом есть рантайм-ручка `/hbsystem/multicore/navi/dbglvl`: её отдаёт
`multicored -D1`, файл размером 1 байт с правами `r--r--r--`. Его содержимое
наш `cat` вернул пустым (байт непечатаемый), так что значение неизвестно —
`1` только в аргументе демона. Влияет ли она на этот канал, не проверено.

### Шлюз, на котором всё стоит

Состояние 1 уходит в молчаливое ожидание ровно в одном месте:

```c
iVar1 = (*PTR_FUN_08236bbc)();     // FUN_08236ab4
if (iVar1 == 0) return 0xffffffff; // -1 → ждать и повторить
```

`FUN_08236ab4` — это «дай итератор по nav cd 1»; при отказе она пишет
(в закрытый канал) `no iterator for nav cd 1` и возвращает 0. Дальше:

* `FUN_08e8c364` — таблица навигационных дисков **ровно на две записи** (0 и 1),
  по 0x50 байт, заполняется один раз; для номера <2 указатель всегда есть;
* значит отказ даёт создание итератора — перечисление тома.

### Что именно перечисляется

`FUN_082368f0` обходит каталог по маске `*`, берёт имя (до 0x50 байт), ищет в нём
последнюю точку и раскладывает файлы по типам:

```
.GDB → тип 0
.LIT .LI2 .LI3 .LI4 .LI5 .LI6 .LI7 .LI8 .LI9 → список, индексы 0..8
.BLB .DON → пропускаются
.GD2 → отдельный тип
```

**XAC в этом перечислении нет** — расширения `.XAC` в таблице диспетчера просто
не существует. Рядом в бинаре есть отдельный набор сообщений `cdm_loader`
(`cdm_loader: error finding xac-header file!`,
`Failed to load %s, offset=%i, size=%i`), поэтому похоже, что XAC грузится
своим путём, но связь не прослежена. В журналах зависания ни одно из этих
сообщений не встречалось — правда, канал их вывода мы тоже не проверяли, так
что это ничего не доказывает.

### Цепочка отказа прослежена до конца

```
NDL, состояние 1
 └ FUN_08236ab4 — «дай итератор по nav cd 1»
    │  при отказе пишет (в закрытый канал) no iterator for nav cd 1 и вернёт 0
    └ FUN_08e8becc — менеджер дисков → запись таблицы → метод +8
       │  драйвер тома выбирается в FUN_08e8c2d4:
       │    multi db file driver  /  iso9660 driver  /  «No valid driver configuration!»
       └ FUN_08e98538 createIterator
          │  iterState[0]=запись диска, iterState[1]=*(том+4), iterState[2]=-1
          └ FUN_08e983f4 — три условия, все обязательны:
               1. *(байт)(том + 0x90348) != 0
               2. iterState[1] == *(том + 4)
               3. *(том + 8) != 0
             нарушено любое → 0 → createIterator вернёт -101 (0xffffff9b)
                             → итератора нет → NDL ждёт вечно
```

Сами условия прочитаны из кода дословно. **Что означают эти три поля — не
установлено**, имена им не присвоены: правдоподобно, что это признак готовности
тома, его идентификатор и число записей каталога, но подтверждения нет. Ясно
одно и без имён: любое из трёх даёт молчаливое вечное ожидание.

Структура тома большая — проверяемый байт лежит по смещению 0x90348, то есть
внутри неё кэшируется что-то объёмное.

Побочно: в `FUN_08e983f4` есть верхняя граница `iterState[2] < 0x20`, иначе
`invalid file handle, handle > nr1…`. Похоже на предел в 32 дескриптора, но
что именно считается — не проверено.

### Откуда берётся каталог тома: `acios_db.ini`

Список баз строит слой CDM из ini-файла. Имена функций дали строки в бинаре:

Сам файл снят с **исправной** машины — `/HBpersistence/navi/db/acios_db.ini`,
17 активных записей и 2 закомментированные:

# This file has been generated by the LVM (epoche 37)

ANY: /mnt/nav/db/pkgdb/XAC/kN221EUx01_0.db      (XAC2, XAC3)

**Файл генерирует LVM** — так написано в его собственной первой строке
(«epoche 37»), и в `logvolmgr` есть `res_if_update_acios_db`,
`res_if_replicate_acios_db` и сообщения `acios_db.ini update OK/failed`.
Переписывается ли он при каждой установке и при каких условиях — по коду пока
не прослежено.

### `checkForConsistency` (FUN_08e93f6c)

```c
if (*(param_1 + 0x10) - 1U < 0x20) { ... }      // записей должно быть 1..32
```

Проход по записям: у кого есть расширение — определяется тип (db или образ);
у кого двоеточие — путь вида `\\.\C:`; остальное даёт `unhandled file type: %s!`.
В конце:

```c
if (((flagA | flagB) & flagC) != 0)   // сообщение: одновременно iso и db
    log("iso and db file mismatch!!!!"), return 0;
```

Какой из трёх признаков какому типу файла соответствует, по декомпиляции
однозначно не разделяется; достоверно только само правило «нельзя мешать».

Отсюда жёсткие рамки набора: **не меньше одной и не больше 32 записей**, и
нельзя мешать образ с обычными файлами. У рабочей машины 17 — запас есть.

### Драйвер баз `nobss` и описатель тома

В бинаре есть драйвер `cdm_nav_db_driver_nobss` (имя из пути к исходнику), и его
сообщения говорят о чтении заголовка и каталога db-файла и о текстовом блоке
`!dbinfo0001 … !enddbinfo`, который он зовёт «db-header»:

```
DBDRV: reading header of db-file (%ld Byte)
DBDRV: reading directory of db-file (%ld Byte)
DBDRV: found db-header '%s'
DBDRV: illegal header
found dbinfo label '%s'   /   no dbinfo label found!
nobss - no dbinfos found. generate dbinfos!
```

В первых 512 КБ файлов набора блок есть **только у LABEL и XAC/XAC2/XAC3**;
у GDB, GD2, LIT, PIT, TER, CTY его там нет. Строка
`nobss - no dbinfos found. generate dbinfos!` намекает, что для таких файлов
описатель создаётся на ходу, но код этой ветки не разбирался.

`Label.DB` — всего 2048 байт, FLDB с **нулём файловых записей**, то есть чистый
описатель тома, и он первым идёт в `acios_db.ini`:

```
!dbinfo0001
cdtype navcd              ← объявляет: это навигационный диск
cdlabel DB_ECE_PDU2
date 01.04.2009
cdtitle DB_ECE_PDU2
!enddbinfo
```

У XAC блок другой — про части набора:

```
!dbinfo0001
skip_db update
PPD XACDB=EJ211
DB=1/3                    ← XAC2: 2/3, XAC3: 3/3
!enddbinfo
```

Отсюда рабочее правило для урезанных наборов: считать компонент LABEL паспортом
тома и не выбрасывать его, сохраняя `cdtype navcd` и метку. **Опытом это не
подтверждено** — набор без LABEL мы не ставили.

### Типы дисков и два слота таблицы

`CCdmNavMediaRecognition` различает:

```
standard_navcd (first time seen) / (already known)
stdnavcd or updnavcd, tag 'cdtype navcd%s' found
cdm_cdst_external_navcd, tag 'cdtype %s' found
no tag cdtype found
already other navcd active
no match to internal label
```

То есть видов носителя как минимум три: `standard_navcd`, `updnavcd`
(обновление) и `external_navcd`. Заманчиво связать их со слотами таблицы
`FUN_08e8c364`, но **сходимости нет**: видов три, а записей в таблице ровно две.
Чему соответствует номер 1, который спрашивает шлюз, пока неизвестно.

Сообщение `no match to internal label` говорит, что метка с чем-то сверяется.
Догадка (не проверенная): это то же сравнение, что и строковое в состоянии 1
автомата NDL (`FUN_08236b50`, поле +0x28), где совпадение уводит в состояние 3,
а несовпадение — в состояние 2.

Есть и функции про сквозной номер изделия:
`cdm_get_nav_cd_db_part_number_of_cd_set`,
`dbm_mount_navcd_of_same_set fakes db_part_number %ld`. Похоже, части набора
как-то сверяются по номеру (у нас `PartNumber="8R0060884KL"` в `DBInfo.txt`),
но сама проверка не найдена.

### Чего не хватает для доказательства

`acios_db.ini` снят только с исправной машины. С зависшей его не снимали ни
разу: строка `acios_db.ini not found` в старых снимках — это наш же
sysinfo-скрипт смотрел не туда, она есть и в рабочих логах.

Ближайший решающий замер: снять `/HBpersistence/navi/db/acios_db.ini` с
зависшей машины и сравнить с эталоном. Проба `tools/baseline/run.sh` его уже
берёт (`acios_2`), отдельный инструмент не нужен.

### Тома и их имена: откуда берутся расширения `.LIT`/`.LI2`

Установлено по отдельности две вещи, связь между ними — пока догадка.

Из кода: диспетчер `FUN_082368f0` берёт имя записи (до 0x50 байт), ищет в нём
последнюю точку и сравнивает расширение с `.GDB`, `.GD2`, `.LIT`, `.LI2`…`.LI9`,
`.BLB`, `.DON`.

Из данных: на разделе файлы называются иначе (`EJ211Ga_L1.db`), но **внутри
FLDB-контейнеров** лежат записи ровно с такими расширениями:

| Компонент | Файл на разделе | Формат | Запись в каталоге | Индекс у NDL |
|---|---|---|---|---|
| LIT  | `EJ211Ga_L1.db` | FLDB | `EJ211Ga.LIT` | 0 |
| LIT2 | `EJ211Ga_L2.db` | FLDB | `EJ211Ga.LI2` | 1 |
| LIT3 | `EJ211Ga_L3.db` | FLDB | `EJ211Ga.LI3` | 2 |
| LIT4 | `EJ211Ga_L4.db` | FLDB | `EJ211Ga.LI4` | 3 |

Совпадение расширений один в один — сильный довод, что диспетчер перечисляет
именно записи контейнеров, но **доказательства нет**, и против него есть факт:
у GDB/GD2 никакого FLDB-каталога нет вовсе, а `.GDB` в таблице диспетчера
присутствует. Значит имена как минимум частично собираются самой прошивкой.

Диспетчер знает до `.LI9` — формат допускает девять томов; в наборе их четыре.
Что `LIT` это база подписей — вывод по читаемому внутри тексту
(`Europa NavTeq Q1/2022 MMI3G`, `ECE2022 MMI3G`, `© 2005-2022 Harman`, `"DVD"`),
а не по разбору формата.

Твёрдо: **LIT — это те же FLDB-контейнеры, что и XAC**, они открываются готовым
`src/fldb.js`, и в каждом ровно одна запись на весь том.

### Три части одной базы

Шапки XAC несут текстовый описатель:

```
!dbinfo0001
skip_db update
PPD XACDB=EJ211
DB=1/3            ← XAC2: DB=2/3, XAC3: DB=3/3
!enddbinfo
```

То есть XAC/XAC2/XAC3 — не три базы, а **три части одной**. С таблицей
навигационных дисков это не сходится: там ровно две записи, а частей три, —
значит `DB=n/3` нумерует что-то своё, а не слоты той таблицы.

### Прочие форматы

| Компонент | Магия | Что это |
|---|---|---|
| GDB, GD2 | `DEADBEEF`, v37 | отрисовка; внутри имя тома `EJ211` и метка сборки `20220218092956` |
| LIT…LIT4 | `FLDB` | подписи |
| XAC…XAC3 | `FLDB` | маршрутизация |
| PIT | `Lit\x02` … `HBIS` | назначение не установлено (магия совпадает с «Lit») |
| CTY, CTY2, CTY3, TER, TER2 | `\x06HEADER` + `Orion` + `Atlas` | формат Orion Atlas, не разбирался |
| SDS | ISO | голосовые данные |

Имён вида `*.GDB`/`*.GD2` ни в одном контейнере нет — устройство синтезирует их
само из `type=` в `.conf` и имени тома. Размеры томов внутри шапок GDB/GD2 тоже
не продублированы (проверен первый мегабайт обоих на все варианты BE/LE и
посекторные), поэтому рост `.gd2` при `--grow` перечисление не ломает.
